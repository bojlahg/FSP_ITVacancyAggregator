Проверенная версия: `master`, коммит `b4556fa`. Требования сверялись с `docs/implementation.md`.
Ревью охватывает основные сценарии кандидата и работодателя, приватность, адаптивный тест,
категории, matching и проверки сборки. Это снимок состояния проекта на указанном коммите;

## 1. [P1] Удалённый аккаунт продолжает работать по старому JWT

Место: [backend/app/core/deps.py:31](../../backend/app/core/deps.py#L31).

Авторизация проверяет JWT и роль, но не проверяет `User.deleted_at`. При удалении аккаунта
отзываются refresh-токены, однако уже выданный access JWT сохраняет доступ до истечения срока.

Воспроизведение:

1. Создать кандидата с категорией и сохранить его access JWT.
2. Удалить аккаунт через `DELETE /api/v1/candidates/me`.
3. С тем же JWT запросить профиль, повторно дать согласие на публикацию и сменить статус поиска на `active`.

Все три запроса после удаления вернули `200`; профиль снова появился в поиске работодателя.
Это противоречит отзыву сессий и удалению профиля из выдачи в §13 ТЗ.

Исправление: проверять существование и состояние пользователя в общей зависимости авторизации;
запросы удалённого пользователя должны отклоняться до вызова бизнес-логики.

## 2. [P1] Контакты раскрываются через текст регулярного задания

Место: [backend/app/modules/tasks/service.py:240](../../backend/app/modules/tasks/service.py#L240).

`_submission_out()` отдаёт работодателю исходный `AnswerPayload`, включая свободный текст,
без проверки `contact_unlocks` и без обезличивания контактов.

Воспроизведение: кандидат отправляет решение задания на подход, содержащее email и телефон;
работодатель запрашивает `/api/v1/employer-tasks/{task_id}/submissions`.
API вернул `200` с исходным email, хотя записи в `contact_unlocks` не было.

Это нарушает инвариант раскрытия контактов из §13 ТЗ. Исправление: до раскрытия контактов
применять такое же обезличивание текста, как в карточке кандидата, включая ответ метода оценки решения.

## 3. [P1] Удаление аккаунта оставляет персональные данные в решениях

Место: [backend/app/modules/candidates/privacy.py:132](../../backend/app/modules/candidates/privacy.py#L132).

Процедура удаления очищает профиль, резюме, опыт, данные ФСП и некоторые снимки,
но не очищает текст ответов регулярных заданий. Работодатель продолжает получать эти ответы
через список решений после удаления аккаунта кандидата.

Воспроизведение: отправить решение с email, удалить аккаунт и повторно запросить решения
от имени работодателя. Email остался в ответе API. Проверка выполнена до повторного включения
публикации из замечания №1, то есть проблема воспроизводится независимо от возврата профиля в поиск.

Это противоречит обезличиванию персональных данных в §13 ТЗ. Исправление: очищать или обезличивать
копии свободного текста кандидата при удалении аккаунта. Отдельно проверить другие места хранения
такого текста: ответы теста, сопроводительные письма и комментарии к отказам.

## 4. [P1] Параллельные запросы создают два текущих вопроса

Место: [backend/app/modules/testing/service.py:228](../../backend/app/modules/testing/service.py#L228).

Чтение состояния и создание следующего вопроса не сериализованы по попытке.
Для позиции вопроса в БД нет ограничения уникальности.

Воспроизведение: два параллельных запроса
`GET /api/v1/tests/attempts/{attempt_id}/current` читают одну и ту же историю до записи нового вопроса.
В проверке это пересечение запросов было обеспечено барьером после чтения истории.
Оба запроса вернули `200` с разными `item_id`; в БД появились две строки с `position = 0`.

Это нарушает последовательную выдачу заданий из §10 и §13 ТЗ и допускает повторные задания
в одной попытке. Исправление: сериализовать изменения попытки блокировкой строки и добавить
уникальность `(attempt_id, position)`. Тем же подходом проверить старт попытки и приём ответа.

## 5. [P2] Поиск теряет статус «проверено тестом»

Место: [backend/app/modules/matching/service.py:104](../../backend/app/modules/matching/service.py#L104).

При сборке индекса первый найденный подтверждённый источник навыка сохраняется,
а более сильный источник не заменяет его. Порядок чтения строк не задаёт приоритет источников.

Воспроизведение: сохранить для одного навыка сначала источник `task`, затем `test`
и пересчитать индекс. Профиль показал `verified`, индекс сохранил `task_confirmed`,
а поиск с `skills=python&verified_only=true` исключил кандидата.

Это создаёт расхождение между профилем, фильтрами и оценкой навыков в §8.3 ТЗ.
Исправление: выбирать источник по явному общему приоритету, согласованному с `skill_states()`.

## 6. [P2] Шорт-лист исчезает при изменении требований

Место: [backend/app/modules/matching/service.py:520](../../backend/app/modules/matching/service.py#L520).

Шорт-лист в ответе строится только из кандидатов новой подборки. Закреплённый кандидат,
который перестал попадать в неё после правки требований, не возвращается в шорт-листе.

Воспроизведение: закрепить кандидата Backend · Middle, затем изменить специализацию потребности
на Frontend и грейд на Senior. Новая версия потребности показала `stats.shortlisted = 1`,
но её подборка вернула `shortlist: []`.

Это противоречит §8.1 п.4 ТЗ: кандидат должен оставаться в шорт-листе при любой правке.
Исправление: формировать шорт-лист из закреплённых id отдельно от отбора кандидатов новой подборки,
с сохранением проверок приватности.

## 7. [P2] Истёкшую категорию нельзя подтвердить повторным тестом

Место: [backend/app/modules/categories/rules.py:66](../../backend/app/modules/categories/rules.py#L66).

Правило безусловно запрещает тест на текущий грейд и не учитывает окончание срока действия категории.

Воспроизведение: установить `valid_until` текущей категории в прошлом и начать тест на тот же грейд.
API вернул `409 same_grade`.

В §6.3 ТЗ результат действует 12 месяцев, после чего требуется подтверждение.
Исправление: учитывать срок действия категории в правилах допуска и разрешать её повторное подтверждение.
