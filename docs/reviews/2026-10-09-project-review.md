## P1 — исправить в первую очередь

### 1. Поиск раскрывает скрытую дисциплину ФСП

Место: [matching/service.py:1070–1075](../../backend/app/modules/matching/service.py#L1070-L1075),
функция `_search_conditions`.

При `show_fsp=false` основной индекс скрывает ФСП, но фильтр `fsp_discipline` читает
`FspAchievement` напрямую и не проверяет видимость ФСП. Работодатель может определить наличие
достижений и их дисциплину, перебирая значения фильтра. Это противоречит §6.4 ТЗ: скрытый ФСП
должен считаться отсутствующим и для фильтров поиска.

**Воспроизведение:** у кандидата с согласием на публикацию и выбранной специализацией добавлено
достижение по дисциплине «алгоритмы», затем установлен `show_fsp=false` и пересчитан индекс.
Поиск с `fsp_discipline=алгоритмы` вернул кандидата, хотя его карточка поиска содержала `has_fsp=false`.

**Исправление:** фильтр дисциплины должен учитывать видимость ФСП, например через
`CandidateSearchIndex.has_fsp`. Добавить регрессионный тест для `show_fsp=false`, включая сочетание
`has_fsp=false` и `fsp_discipline`.

### 2. Один refresh-токен можно одновременно обменять дважды

Место: [auth/service.py:205–218](../../backend/app/modules/auth/service.py#L205-L218), функция `refresh`.

Токен читается без блокировки. Два параллельных запроса видят `revoked_at=NULL`, оба проходят
проверку повторного использования и оба выпускают новые refresh-токены. Ротация перестаёт быть
одноразовой, а одновременное повторное использование не запускает предусмотренный §6.1 и §13
отзыв сессий.

**Воспроизведение:** два вызова `refresh` с одним токеном в отдельных сессиях остановлены перед
`_issue_session`, чтобы оба успели прочитать старый токен до коммита. Оба вызова завершились успешно;
в БД остались два новых активных refresh-токена.

**Исправление:** сделать потребление токена атомарным — блокировкой строки или условным
`UPDATE ... WHERE revoked_at IS NULL ... RETURNING`. Проверка и отзыв должны выполняться в одной
транзакции. Добавить тест параллельного использования одного токена и проверки последующего отзыва.

## P2

### 3. Параллельный старт создаёт два экспресс-теста

Место: [testing/service.py:141–144](../../backend/app/modules/testing/service.py#L141-L144), функция `start`.
Связанный код: `_check_express` и `core/ratelimit.py::hit`.

После блокировки кандидата и проверки незавершённой попытки `start` вызывает `_check_express`.
Внутри `ratelimit.hit` выполняется `commit`, который снимает блокировку до создания попытки.
Второй запрос успевает пройти ту же проверку. Нарушается правило §6.3 о единственном незавершённом
тесте; новый обычный тест затем блокируется оставшимися попытками.

**Воспроизведение:** два параллельных старта остановлены после настоящего `_check_express`.
Оба создали разные попытки; в БД оказалось две попытки `in_progress` одного кандидата.

**Исправление:** выполнить лимитер до блокировки кандидата либо отделить его транзакцию так,
чтобы проверка незавершённой попытки и создание новой оставались под одной блокировкой.
Дополнительная защита — частичный уникальный индекс на кандидата при `status='in_progress'`.
Добавить тест параллельного старта.

### 4. Параллельные правки потребности разветвляют историю версий

Место: [needs/service.py:242–260](../../backend/app/modules/needs/service.py#L242-L260), функция `update_need`.

Проверка последней версии и создание потомка не защищены общей блокировкой, а уникального
ограничения на `parent_id` нет. Два запроса создают двух потомков одной версии с одинаковым
номером. Если потребность была опубликована, обе новые версии тоже публикуются: вакансии
дублируются, а `latest_version`, выбирающий одного потомка через `limit(1)`, становится неоднозначным.
Это нарушает последовательную историю версий и правило единственной опубликованной версии (§8.1, §8.7).

**Воспроизведение:** две правки одной опубликованной потребности остановлены после
`_get_latest_own`. Оба вызова успешно создали разные строки с `version=2`, одинаковым `parent_id`
и `published=true`.

**Исправление:** блокировать исходную версию перед проверкой актуальности и создавать потомка
в той же транзакции. Добавить ограничение уникальности `parent_id`, обработку конфликта как
доменной ошибки и тест параллельных правок.

### 5. Один ФСП ID одновременно привязывается к двум профилям

Место: [fsp/service.py:214–225](../../backend/app/modules/fsp/service.py#L214-L225), функция `_link`.
Связанный код: `candidates/models.py::Candidate.fsp_id` — индекс без уникальности.

Проверка владельца и сохранение привязки неатомарны. Два запроса для разных кандидатов могут
оба не найти владельца и сохранить одинаковый ФСП ID. Правило §9.3, по которому уже занятый ID
должен давать `fsp_id_taken`, обходится. Общий путь используется и для ручной, и для OIDC-привязки.

**Воспроизведение:** два вызова общего пути привязки в отдельных сессиях использовали одинаковый
ID и метод `oidc`. Ответ реестра был подменён пустыми списками, а пауза после проверки владельца
позволила обоим запросам пройти её до записи. В БД сохранились два профиля с одинаковым ID
и `fsp_link_method=oidc`. Полный вход через внешний IdP в этом воспроизведении не выполнялся.

**Исправление:** добавить уникальное ограничение на `candidates.fsp_id` и переводить конфликт
записи в `fsp_id_taken`. Добавить конкурентный тест привязки одного ID к разным кандидатам.
