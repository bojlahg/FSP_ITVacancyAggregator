# ФСП / ЛЦТ 2026 — разбор спецтрека

Дата: 01.10.2026
Задача: платформа-агрегатор ИТ-вакансий с верифицированным профилем достижений участника ФСП.
Разработка: 5–11 октября. Доработка: 19–21 октября. Питч: 24 октября (офлайн).

---

## 1. Оценка сложности

Технически задача средняя. По сути это CRUD-сервис: профили, вакансии, LLM-парсер, детерминированный скоринг и форма оффера. С coding agents и жёстким scope её реально закрыть за 7 дней силами 1–2 человек.

Сам код почти не даст преимущества: job board + LLM + match % соберут многие команды. Выделиться можно на двух вещах:

1. честная модель доказательности навыков;
2. обратная механика: работодатель находит кандидатов через категории.

Главный реальный риск — данные ФСП. Это не код.

---

## 2. Ключевая проблема текущей идеи: ложная объективность

Дисциплины ФСП (по имеющимся сведениям; уточнить у экспертов): алгоритмическое программирование, продуктовое программирование, информационная безопасность, программирование БАС, программирование робототехники.

Место на алгоритмическом контесте **не доказывает** владение Python, FastAPI или Docker. Поэтому строки вида `Python — 91 / Verified` будут атакованы жюри первыми: эксперты ФСП лучше всех знают, что их данные подтверждают, а что нет.

### Решение: уровни доказательности вместо процентов

| Статус | Что означает | Пример |
|---|---|---|
| **Заявлено** | навык из резюме, без внешнего подтверждения | «FastAPI» в резюме |
| **Подкреплено** | навык косвенно связан с событием ФСП | роль backend в продуктовом хакатоне |
| **Подтверждено** | то, что результат ФСП действительно измеряет | алгоритмика, CTF, командная продуктовая разработка, спортивный разряд |

Разряд — особенно сильный сигнал: это официальная спортивная квалификация, а не наша метрика.

Числа используются только там, где их можно честно посчитать и объяснить одной фразой:

- перцентиль места с учётом числа участников;
- уровень соревнования (региональное / всероссийское и т.д.);
- затухание по давности результата.

---

## 3. Центр продукта — категории, а не парсинг вакансии

Постановка прямо требует: «соискатели автоматически категоризируются, работодатель сам находит нужную категорию». В текущей идее центральным стал сценарий «вставил текст вакансии → LLM → shortlist». Его сделает большинство команд.

### Предлагаемый первый экран работодателя

Каталог категорий, построенный детерминированно из данных ФСП. Примеры:

- «Алгоритмисты — топ-10% всероссийских соревнований»
- «Продуктовый backend — командный опыт»
- «CTF / web security»

У каждой категории есть счётчик кандидатов и медианный уровень.

### Сценарий демо (20–30 секунд)

```text
Каталог категорий
    ↓
категория
    ↓
кандидаты с evidence
    ↓
карточка кандидата
    ↓
персональный оффер с зарплатной вилкой
```

Парсинг текста вакансии остаётся вторым путём входа, не главным.

---

## 4. Холодный старт

У большинства ИТ-специалистов нет достижений ФСП. На защите это почти наверняка спросят.

Ответ должен быть заложен в продукт: платформа работает на заявленных данных, а ФСП даёт буст доверия и попадание в категории.

---

## 5. Что убрать

- **pgvector и embeddings** — не нужны. Хватит структурированного матчинга по онтологии примерно из 150 навыков со словарём алиасов.
- **Verified Skill Graph в виде дерева** — красиво, но дорого, и усиливает псевдообъективность. Лучше карточка кандидата с блоками evidence.
- Всё из списка «не делать» в исходном handoff остаётся в силе: чат, ATS, coding interview, AI coach и т.п.

---

## 6. Архитектура

Схема правильная:

```text
LLM-парсер → структурированные данные → детерминированный скоринг → объяснение
```

Уточнения:

- LLM извлекает данные **строго в enum** из онтологии навыков, без свободного текста.
- Объяснение собирается шаблоном из компонентов скоринга, LLM только перефразирует. Так объяснение гарантированно совпадает со score.
- Стек — тот же, что в DealDojo, чтобы переиспользовать VDS, домен и CI/CD через GitHub без потери дня.
- LLM — Yandex AI Studio. Это ещё и аргумент для защиты: резюме являются персональными данными (152-ФЗ), и они не уходят за рубеж.

## 7. Ресурсы

| Ресурс | Оценка |
|---|---|
| Люди | 1 человек + агенты — справится, 2 — комфортно. Дизайнер не нужен (брендбук и макеты от ФСП) |
| Объём | ~10–14 человеко-дней сфокусированной работы |
| Инфраструктура | переиспользование от DealDojo: VDS, CI/CD, Yandex AI Studio |
| LLM-расходы | незначительные |
| Данные | генератор синтетики: 300–500 кандидатов с правдоподобными достижениями по реальным дисциплинам ФСП |
| Консультации ФСП | выяснить, есть ли в данных роль участника в команде и поле «задачи/категории» — от этого зависит слой «Подкреплено» |

### Риски по ресурсам

- Загрузка: если DealDojo (основная задача ЛЦТ) в эти даты активна, неделя 5–11 октября делится на две задачи.
- Единственная точка отказа: только Дмитрий может чинить прод.

---

## 8. Команда

План: Дмитрий разрабатывает с Claude Code и, возможно, лёгкой моделью (Gemini Flash), участник из Москвы закрывает офлайн-защиту.

### Роль участника из Москвы

Подключить с первого дня в продуктовой роли, а не только на питч. Тот, кто защищает, должен отвечать на уточняющие вопросы без подготовки. Его задачи:

- консультации с экспертами ФСП и выяснение реальной структуры данных;
- проверка правдоподобия синтетических кандидатов;
- демо-сценарий и регулярный прогон на проде (роль тестировщика);
- документация и питч.

### Проверить до 4 октября

- можно ли добавить участника после регистрации;
- должен ли выступающий на питче числиться в команде с начала.

### Разделение между агентами

- **Claude Code** — ядро: модель данных, расчёт evidence и категорий, скоринг.
- **Лёгкая модель** — изолированные задачи: страницы UI по макетам, генератор синтетики, описание API, инструкция по деплою. Насколько она справится, станет понятно по первому дню.
- **Правило против конфликтов:** сначала фиксируются схема БД и OpenAPI-контракт. Фронт и бэк пишутся против контракта разными агентами, каждый в своей папке.

### Страховка на день питча

- у участника из Москвы есть доступ, чтобы хотя бы перезапустить контейнеры;
- записанное видео демо на случай проблем с продом или сетью на площадке.

## 9. План на 7 дней

| День | Результат |
|---|---|
| 1 | модель данных, генератор синтетики, пустой сервис задеплоен |
| 2 | онтология навыков, импорт ФСП, расчёт evidence и категорий. **Контрольная точка: на проде открывается каталог категорий с кандидатами** |
| 3 | парсер вакансий, скоринг |
| 4 | шортлист, карточка кандидата с evidence |
| 5 | оффер с вилкой, входящие у кандидата |
| 6 | документация API, инструкция по развёртыванию, прогон демо |
| 7 | буфер |

## 10. Вероятные вопросы жюри

- Что именно доказывает результат ФСП, и почему вы считаете навык подтверждённым?
- Что видит работодатель, если у кандидата нет достижений ФСП?
- Откуда берётся число в match score и как его проверить?
- Почему разряд или всероссийское соревнование весит больше регионального?
- Как кандидат связывает профиль с ФСП, где согласие на обработку данных, как исключить чужие достижения?
- Куда уходят резюме при LLM-обработке?
- Чем это отличается от HH + ChatGPT?

## 11. Итог

Задача реалистична для маленькой команды с coding agents. Призы для спецтрека хорошие, конкуренция, вероятно, ниже, чем в основных задачах ЛЦТ.

Исход определит не объём фич, а то, насколько честно и наглядно команда покажет, что именно доказывают данные ФСП и как работодатель находит через них кандидатов.
