# ФСП / ЛЦТ 2026 — предложение по реализации MVP

Дата: 01.10.2026
Связанный документ: `fsp_lct_review.md` (продуктовый разбор и выводы).
Срок разработки: 5–11 октября. Исполнители: Дмитрий + coding agents; участник из Москвы — продукт, данные, тестирование, питч.

Все числа (веса, пороги, коэффициенты) ниже — стартовые значения. Их нужно сверить с экспертами ФСП и с реальной структурой данных, когда придёт спецификация API.

---

## 1. Принципы

1. **Детерминированное ядро.** Evidence, категории и score считаются кодом. LLM только извлекает структуру из текста и перефразирует готовое объяснение.
2. **Словарь первым, LLM вторым.** Навыки сначала ищутся по словарю алиасов, LLM обрабатывает только остаток. Если LLM недоступен, система работает на словаре.
3. **Не зависеть от спецификации ФСП в первые дни.** Доступ к данным ФСП идёт через интерфейс провайдера; первым реализуется mock на синтетике.
4. **Честность доказательности.** У каждого навыка есть статус (Заявлено / Подкреплено / Подтверждено) и список evidence. Число без evidence не показывается.
5. **Один демо-сценарий работает всегда.** Каждый день заканчивается тем, что сценарий из раздела 11 проходит на проде.

## 6. Расчёт evidence

### 6.1. Сила одного результата

```text
percentile = 1 − (place − 1) / max(participants − 1, 1)

strength = percentile × level_weight × recency
```

| Уровень соревнования | `level_weight` |
|---|---|
| международное | 1.00 |
| всероссийское | 0.90 |
| межрегиональное | 0.75 |
| региональное | 0.60 |
| муниципальное / отборочное | 0.40 |

```text
recency = 0.5 ^ (возраст_результата_в_годах / 3)     # полураспад 3 года
```

Командный результат: место команды засчитывается каждому участнику; роль участника определяет, к каким компетенциям он относится (через `by_role`).

### 6.2. Компетенция из нескольких результатов

Несколько независимых результатов накапливаются, но не превышают 1 (noisy-OR):

```text
competency_score = 1 − Π (1 − strength_i)
```

Для связей типа `role` (а не `direct`) сила умножается на 0.7: роль в команде говорит о навыке слабее, чем прямое измерение.

### 6.3. Спортивный разряд

Разряд по дисциплине даёт нижнюю границу компетенции:

| Разряд | Минимальный score |
|---|---|
| МС | 0.95 |
| КМС | 0.85 |
| I разряд | 0.70 |
| II разряд | 0.55 |
| III разряд | 0.40 |
| юношеские | 0.25 |

```text
competency_score = max(competency_score, rank_floor)
```

### 6.4. Статусы

| Статус | Условие |
|---|---|
| Подтверждено (компетенция) | есть `direct`-evidence и `score ≥ 0.5`, или есть разряд по дисциплине |
| Подкреплено (компетенция) | есть только `role`-evidence |
| Подкреплено (навык) | навык заявлен, и его `family` совпадает с `supports_family` хотя бы одного evidence |
| Заявлено (навык) | всё остальное из резюме |

Технологические навыки (Python, Docker) никогда не получают «Подтверждено» только из данных ФСП. Это сознательное ограничение и аргумент на защите.

### 6.5. Тесты

`tests/evidence/` — набор «золотых» кейсов в YAML: входные достижения → ожидаемые scores и статусы. Любое изменение весов прогоняет эти кейсы.

## 7. Категории

Правила в `categories.yaml`, движок — простой интерпретатор условий:

```yaml
- id: algo_top10_national
  title: Алгоритмисты — топ-10% всероссийских
  rule:
    any_achievement:
      discipline: algorithmic
      level_min: national
      percentile_min: 0.90

- id: product_backend_team
  title: Продуктовый backend — командный опыт
  rule:
    all:
      - competency: { id: backend_dev, score_min: 0.4 }
      - competency: { id: product_team_dev, score_min: 0.5 }

- id: ctf_strong
  title: CTF / информационная безопасность
  rule:
    competency: { id: infosec_ctf, score_min: 0.6 }

- id: ranked_athletes
  title: Спортсмены-разрядники ФСП
  rule:
    rank_min: III
```

Поддерживаемые операторы: `all`, `any`, `competency`, `any_achievement`, `rank_min`, `skill` (с минимальным статусом). Больше не нужно.

Для каталога у категории считаются: число кандидатов, медианный score ключевой компетенции, распределение по грейдам. Пересчёт категорий — при любом изменении профиля кандидата (синхронно, данных мало).

Целевое количество категорий в демо: 8–12.

## 8. Matching

### 8.1. Жёсткие фильтры (до скоринга)

- формат работы несовместим (только офис ↔ только удалёнка);
- город не совпадает, и кандидат не готов к релокации, и вакансия не удалённая;
- ожидание кандидата выше верхней границы вилки более чем на 20%.

Кандидаты, отсеянные фильтром, не пропадают: показываются в отдельном свёрнутом блоке с причиной. Это помогает работодателю увидеть, что вилка занижена.

### 8.2. Покрытие навыков

Значение навыка кандидата для требования:

| Ситуация | Значение |
|---|---|
| навык Подтверждено | 1.00 |
| навык Подкреплено | 0.85 |
| навык Заявлено | 0.65 |
| есть только родительский навык (FastAPI → Python) | 0.30 |
| нет | 0 |

```text
coverage = Σ (w_req × value_req) / Σ w_req
    w = 1.0 для required, 0.3 для optional
```

### 8.3. Итоговый score

```text
match = 0.50 × coverage
      + 0.20 × role_match        # 1 совпадает, 0.5 смежная роль, 0 нет
      + 0.15 × grade_match       # 1 совпадает, 0.5 соседний грейд, 0 дальше
      + 0.15 × trust             # доля required-навыков со статусом Подкреплено и выше,
                                 # плюс компетенции из категорий, связанных с ролью вакансии
```

`trust` — то место, где данные ФСП влияют на ранжирование. Его вес сознательно небольшой: ФСП повышает доверие, но не перекрывает отсутствие нужного стека.

### 8.4. Что показывать работодателю

Не одно число, а разложение:

```text
Иван Петров · Middle Backend · 84

Обязательные навыки: 4 из 5
  ✓ Python        Подкреплено   (продуктовый хакатон ФСП, роль backend)
  ✓ PostgreSQL    Заявлено
  ✓ Docker        Заявлено
  ✓ FastAPI       Заявлено
  ✗ Kubernetes    нет

Подтверждено ФСП:
  Алгоритмы — КМС, 7 место из 412 на всероссийских (2025)
  Командная разработка — 3 результата в продуктовых соревнованиях
```

Score округляется до целого. Сортировка — по score, при равенстве — по `trust`.

### 8.5. Тесты

`tests/matching/` — 5–7 пар «вакансия + набор кандидатов → ожидаемый порядок в шортлисте». Проверяют, что веса дают осмысленный порядок, а не только что код не падает.

## 9. LLM

### 9.1. Где используется

| Задача | Вход | Выход |
|---|---|---|
| Разбор вакансии | текст вакансии | JSON по схеме 9.2 |
| Разбор резюме | текст резюме | JSON: навыки, роли, грейд, опыт |
| Перефразирование объяснения | шаблонное объяснение | 2–3 предложения человеческим языком |

### 9.2. Разбор вакансии

Порядок:

1. Словарный матчер по алиасам находит навыки в тексте.
2. LLM получает текст и **полный список id навыков из онтологии** и возвращает JSON строго по схеме:

```json
{
  "title": "string",
  "role": "backend | frontend | fullstack | ml | data | devops | qa | security | mobile | other",
  "grade": "junior | middle | senior | lead | null",
  "required": ["skill_id"],
  "optional": ["skill_id"],
  "unmapped": ["термин из текста, которого нет в онтологии"],
  "work_format": "office | hybrid | remote | null",
  "city": "string | null",
  "salary_from": "number | null",
  "salary_to": "number | null"
}
```

3. Ответ валидируется Pydantic. Неизвестные `skill_id` переносятся в `unmapped`. При невалидном JSON — один повтор, потом откат на результат словаря.
4. Результат показывается работодателю как редактируемая форма: он может поправить требования до запуска поиска. Это закрывает вопрос «а если LLM ошибся».

`unmapped` показывается в UI: «не распознали: X, Y». Это честнее, чем молча выкинуть.

### 9.3. Объяснение

Объяснение собирается кодом из компонентов скоринга (раздел 8.4). LLM получает этот текст и только переписывает связным языком, без права добавлять факты. Если LLM недоступен — показывается шаблонная версия. Генерация по запросу при открытии карточки, с кешем.

## 10. FSP Provider

```python
class FspProvider(Protocol):
    def get_participant(self, participant_id: str) -> FspParticipant | None: ...
    def get_achievements(self, participant_id: str) -> list[FspAchievement]: ...
    def get_ranks(self, participant_id: str) -> list[FspRank]: ...
    def list_competitions(self) -> list[FspCompetition]: ...
```

- `MockFspProvider` — читает данные, созданные генератором синтетики. Реализуется в день 1.
- `HttpFspProvider` — когда придёт спецификация или mock-сервис организаторов.
- Выбор провайдера — переменная окружения.

### Привязка профиля ФСП

Кандидат вводит ID участника ФСП и ставит отметку согласия на обработку данных. В демо подтверждение владения ID не делаем, но в документации и на защите описываем, как оно должно работать (OAuth ФСП или код на email из профиля ФСП) — это частый вопрос жюри.

## 13. Frontend: экраны

### Работодатель

1. **Каталог категорий** — главный экран. Карточки категорий: название, число кандидатов, медианный уровень, мини-распределение по грейдам.
2. **Список кандидатов категории** — фильтры: грейд, город, формат, ожидания по зарплате.
3. **Карточка кандидата** — навыки со статусами, блоки evidence ФСП, кнопка «Сделать предложение».
4. **Вакансия** — вставка текста → разобранные требования (редактируемые) → шортлист с разложением score.
5. **Форма оффера** — вакансия, вилка, сообщение.
6. **Отправленные офферы** — статусы.

### Кандидат

1. **Профиль** — данные, резюме (вставка текста), привязка ФСП.
2. **Мой verified-профиль** — компетенции и навыки со статусами и evidence; список категорий, в которые попал.
3. **Входящие предложения** — принять / отклонить.

Брендбук и макеты ФСП — источник стилей. Если макеты не покрывают экран, делаем по аналогии с ближайшим.

---

## 14. Демо-сценарий (e2e)

Этот сценарий проходит на проде каждый вечер и покрывается Playwright-тестом:

1. Работодатель входит → видит каталог категорий.
2. Открывает «Продуктовый backend — командный опыт» → список кандидатов.
3. Открывает «героя демо» → видит evidence ФСП.
4. Отправляет оффер с вилкой.
5. Кандидат входит → видит оффер → принимает.
6. Работодатель видит статус «принято».

Второй сценарий (вставка текста вакансии → шортлист) — тоже в e2e, но вторым приоритетом.

## 15. Деплой

- Docker Compose: `db`, `backend`, `frontend` (статические файлы через nginx), reverse proxy с TLS.
- GitHub Actions: тесты → сборка образов → деплой на VDS при пуше в `main`.
- `make reseed` / `POST /admin/reseed` — откат демо-данных к исходному состоянию перед каждым показом.
- `docs/deploy.md` — инструкция развёртывания с нуля одной командой (`docker compose up`), включая `.env.example`.

## 17. Разбивка на задачи для агентов

Уровни — по принятой шкале (1 — локальная реализация, 2 — много связанных файлов или нетривиальная логика, 3 — архитектура). Для каждой задачи при запуске пишется отдельное ТЗ.

| # | Задача | Зависит от | Уровень | Почему |
|---|---|---|---|---|
| T01 | Каркас репо, Docker Compose, CI/CD, `/health`, пустой фронт | — | 1 | известный пайплайн, переиспользование DealDojo |
| T02 | Схема БД, модели, миграции, Pydantic-схемы, OpenAPI-контракт | — | 3 | контракт, от которого зависят все остальные задачи; ошибка дорого стоит позже |
| T03 | YAML-справочники: онтология (~150), компетенции, маппинг дисциплин, категории | T02 | 1 | данные, не код; проверка человеком |
| T04 | Генератор синтетики + `MockFspProvider` | T02, T03 | 2 | нужно реалистичное распределение архетипов и связность данных |
| T05 | Модуль evidence + статусы + golden-тесты | T02, T03 | 2 | ядро доказательности, формулы и граничные случаи |
| T06 | Движок категорий + эндпоинты каталога | T05 | 2 | интерпретатор правил, связан с evidence |
| T07 | Matching + разложение score + golden-тесты | T05 | 2 | ядро ранжирования |
| T08 | LLM-клиент, разбор вакансии и резюме, словарный матчер, откат | T03 | 2 | внешний API, валидация, обработка сбоев |
| T09 | Объяснения: шаблон + LLM-перефразирование + кеш | T07, T08 | 1 | локальная задача с понятным входом и выходом |
| T10 | Офферы: API + статусы | T02 | 1 | простой CRUD |
| T11 | Фронт: каталог, список, карточка кандидата | T02 (контракт) | 1 | экраны по макетам против готового контракта |

Если задача уровня 1 не справилась с первой попытки по существу (не по мелочам) — поднимать на уровень 2, а не перезапускать ту же конфигурацию.

## 18. Что сознательно не делаем

- pgvector, embeddings, обучаемые модели.
- Чат, уведомления по email, ATS-воронка.
- Тестирование кандидатов, coding interview.
- Подтверждение владения ID ФСП (описываем, не реализуем).
- Роли сверх `candidate` / `employer`, команды работодателей, права доступа.
- Асинхронные очереди, микросервисы.
