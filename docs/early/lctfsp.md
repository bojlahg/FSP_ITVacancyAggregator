# 4. Формулировка задачи

## Название

**Цифровая платформа-агрегатор ИТ-вакансий с верифицированным профилем достижений участника Федерации спортивного программирования (ФСП)**

## Постановка

Необходимо разработать цифровую платформу / веб-сервис — отраслевой агрегатор вакансий для ИТ-специалистов с обратной механикой подбора:

- соискатели автоматически категоризируются по объективно подтверждаемому профилю;
- работодатель сам находит нужную категорию специалистов;
- работодатель выходит на конкретного кандидата с вакансией и уровнем заработной платы.

---

# 5. Мотивация задачи от организаторов

Организаторы считают, что существующие универсальные площадки поиска работы плохо подходят именно для ИТ:

- работодатели вручную фильтруют множество нерелевантных откликов;
- кандидаты массово откликаются «вслепую»;
- формальное резюме показывает стек и места работы, но не подтверждает реальную практическую компетентность;
- отбор часто сводится к совпадению ключевых слов;
- универсальные платформы плохо формализуют отраслевые параметры:
  - стек;
  - грейд;
  - роль в команде;
  - формат работы;
- из-за этого точность подбора низкая для обеих сторон.

Ключевое преимущество ФСП:

Федерация располагает данными о соревнованиях и результатах участников, которые можно использовать как **объективное подтверждение практических навыков**.

Профиль кандидата может автоматически обогащаться:
- дисциплинами;
- соревнованиями;
- результатами;
- ролями;
- спортивными разрядами;
- другими достижениями ФСП.

# 9. Наша текущая продуктовая идея

Не делать ещё один обычный job board с AI-поиском.

Главный продуктовый тезис:

> Не просто заявленные навыки кандидата, а навыки, подтверждённые объективными evidence из ФСП.

Центральная сущность — **Verified Professional Profile**.

Он объединяет:
- обычное резюме;
- заявленные навыки;
- опыт;
- предпочтения;
- достижения ФСП;
- соревнования;
- дисциплины;
- роли;
- результаты;
- спортивные разряды.

# 10. Основные пользовательские сценарии

## 10.1. Кандидат

1. Создаёт профиль.
2. Загружает / заполняет резюме.
3. Подключается профиль / данные ФСП.
4. Система автоматически импортирует подтверждённые достижения.
5. Навыки нормализуются и связываются с evidence.
6. Пользователь получает структурированный verified-профиль.

Пример:

```text
Python — 91 / Verified

Evidence:
- соревнование ФСП #1
- роль: Backend Developer
- 2 место
- участие в 4 соревнованиях
```

## 10.2. Работодатель

1. Вставляет обычный текст вакансии.
2. Система автоматически разбирает требования.
3. Требования превращаются в структурированный профиль.

Пример:

```json
{
  "role": "Backend Developer",
  "grade": "Middle",
  "skills": [
    "Python",
    "FastAPI",
    "PostgreSQL",
    "Docker"
  ],
  "optional": [
    "Kubernetes"
  ]
}
```

4. Matching Engine ищет наиболее подходящих кандидатов.
5. Работодатель получает shortlist.
6. Для каждого кандидата видит:
   - итоговый match score;
   - причины совпадения;
   - сильные стороны;
   - отсутствующие компетенции;
   - подтверждение навыков данными ФСП.
7. Работодатель отправляет кандидату прямое предложение с вакансией и зарплатой.

# 11. Обратная механика найма

Важная часть постановки:

не кандидат массово откликается на вакансии, а работодатель:

```text
категория специалистов
        ↓
подходящие кандидаты
        ↓
конкретный кандидат
        ↓
персональное предложение
        ↓
зарплатная вилка
```

То есть основной сценарий должен быть employer-driven.

# 13. LLM: предлагаемая роль

Не делать LLM главным decision-maker.

LLM использовать для:
- разбора свободного текста вакансии;
- разбора резюме;
- нормализации названий технологий;
- извлечения структуры;
- генерации понятного объяснения;
- возможно, классификации неструктурированных достижений.

Но финальный match score желательно вычислять детерминированным алгоритмом.

Причины:
- объяснимость;
- воспроизводимость;
- контроль;
- отсутствие случайного score;
- проще защитить архитектуру перед жюри.

---

# 14. Matching Engine

Базовый вариант:

```text
MatchScore =
    0.30 StackMatch
  + 0.20 ExperienceMatch
  + 0.20 VerifiedSkills
  + 0.10 CompetitionLevel
  + 0.10 RoleMatch
  + 0.10 PreferencesMatch
```

Коэффициенты пока условные.

Важно не столько конкретное значение весов, сколько возможность объяснить:

```text
Backend Python Developer
Match: 88%

✓ Python              95%
✓ Algorithms          91%
✓ Backend role        87%
✓ Docker              74%
✗ Kubernetes          12%
```

И отдельно показать evidence.

# 15. Возможная уникальная фича — Verified Skill Graph

Визуальная карта навыков:

```text
                    Backend
                  82 VERIFIED
                 /           \
              Python        Go
              91             63
             /                 \
      Algorithms             Docker
          88                   70
         /                      \
   ФСП contests            Hackathons
     4 results              2 results
```

Каждый навык можно раскрыть и увидеть, почему он считается подтверждённым.

Пример:

```text
Python — 91 / Verified

Evidence:
✓ соревнование ФСП
✓ Backend role
✓ призовое место
✓ несколько независимых результатов
```

Это может стать главным визуальным элементом демо.

Желательно ограничить проект четырьмя end-to-end сценариями.

## 1. Профиль кандидата
- резюме;

- achievements ФСП;
- verified skills.

## 2. Вакансия
- создание;

## 3. Поиск / matching

- score;
- explanation;

## 4. Прямое предложение
- вакансия;
- зарплатная вилка;
- отправка кандидату.

Полный идеальный сценарий:

```text
Кандидат
    ↓
импорт достижений ФСП
    ↓
Verified Profile

Работодатель
    ↓
вставляет вакансию
    ↓
LLM Parser
    ↓
Structured Requirements
    ↓
Matching Engine
    ↓
Shortlist
    ↓
открывает кандидата
    ↓
видит evidence
    ↓
отправляет предложение
```

# 17. Что НЕ хочется делать в недельном MVP

Не планируется, если этого не потребуют правила:
- полноценный ATS;
- чат;
- видеособеседования;
- собственный мессенджер;
- сложная социальная сеть;
- аналог LinkedIn;
- аналог HeadHunter целиком;
- большая тестовая платформа;
- сложное online coding interview;
- полноценная ML-рекомендательная система, требующая большого обучающего датасета;
- микросервисный зоопарк;
- сложная event-driven инфраструктура;
- десятки ролей и permission levels.

Цель — хороший end-to-end продуктовый сценарий, а не «SAP за семь дней».

# 20. Главные риски

## 20.1. ФСП API

Пока неизвестно:
- насколько API полный;
- насколько хорошие данные;
- есть ли реальные данные или только mock;
- есть ли стабильный ID участника;
- насколько достижения можно связать с конкретными skills;
- какие поля обязательны;
- какие ограничения API.

Это может сильно изменить архитектуру.

## 20.2. Слабая связь achievement → skill

Факт участия в соревновании ещё не всегда прямо доказывает конкретный технологический skill.

Нужно определить механизм:

```text
achievement
   ↓
discipline / role / competition
   ↓
competency evidence
   ↓
verified skill
```

Важно не сделать ложную «объективность».

## 20.3. Match score

Нужно, чтобы score:
- был понятен;
- не выглядел произвольным;
- не был псевдонаучным;
- объяснялся пользователю.

## 20.4. Отличие от HH / LinkedIn

Если продукт будет выглядеть просто как job board + ChatGPT, ценность ФСП потеряется.

Главное отличие должно быть заметно в первые 20–30 секунд демо.

## 20.5. Feature creep

Очень легко начать добавлять:
- тестирование;
- coding interview;
- чаты;
- AI recruiter;
- AI coach;
- roadmap skills;
- карьерные рекомендации;
- обучение;
- HR analytics.

Для семидневного хакатона это опасно.
