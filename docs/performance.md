# Нагрузочное тестирование

Требование ТЗ (п. 3.5): «стабильная работа при одновременном использовании десятками пользователей; основные операции — формирование подборки, открытие профиля, поиск — выполняются за приемлемое время». Нагрузочный тест в [`loadtest/`](../loadtest/run.py) проверяет это воспроизводимо: 10, 30 и 50 одновременных пользователей по 60 секунд на основных операциях обоих кабинетов.

## 1. Что измеряется

**Модель нагрузки — замкнутая.** N виртуальных пользователей работают параллельно, каждый в цикле делает запрос, ждёт ответа и «думает» 1–3 секунды (равномерно), затем выбирает следующую операцию. 70% пользователей — работодатели, 30% — кандидаты. Выбор операций детерминирован по `--seed`.

| Роль | Операция | Эндпоинт | Доля |
|---|---|---|---:|
| Работодатель | Подборка по потребности | `GET /needs/{id}/recommendations` | 30% |
|  | Поиск по базе (случайные специализация, грейд, сортировка) | `GET /talent/search` | 25% |
|  | Карточка кандидата с объяснением | `GET /talent/candidates/{id}?need_id=` | 25% |
|  | Покрытие вилки | `GET /needs/{id}/salary-coverage` | 10% |
|  | Список потребностей | `GET /needs` | 10% |
| Кандидат | Профиль (дашборд) | `GET /candidates/me` | 40% |
|  | Приглашения | `GET /candidates/me/invitations` | 30% |
|  | Вакансии с оценкой совпадения | `GET /vacancies?match=true` | 30% |

- **Только чтение.** Тест делает GET-запросы и демо-вход, данные не меняет — его можно направить на любой стенд с `DEMO_MODE=true`, в том числе на прод. Единственная запись на стороне сервера — ленивое истечение просроченных приглашений в `GET /candidates/me/invitations`, его так же делает открытие экрана в интерфейсе.
- **Вход.** `POST /auth/demo-login` ограничен 20 запросами в минуту на IP и путь, поэтому тест заранее получает пул токенов (по умолчанию 5 на роль, не больше 18 входов в минуту) и раздаёт их пользователям. Access-токен живёт 15 минут, пул перевыпускается через 12. Подготовка (список потребностей, кандидаты из подборок для карточек, справочник специализаций) в замер не входит.
- **Метрики.** На каждый эндпоинт и уровень: число запросов, RPS, задержка p50/p95/p99/max (метод ближайшего ранга), доля ошибок (HTTP ≥ 400 и сетевые ошибки). Задержка — от отправки запроса до получения всего тела ответа на стороне клиента.

## 2. Как запустить

```bash
make loadtest LOADTEST_URL=http://localhost:8000             # 10/30/50 пользователей по 60 с, ~3,5 мин
cd loadtest && uv run python run.py --base-url https://itscout.ru --out result.json
cd loadtest && uv run python run.py --users 50 --duration 30 --think-min 0 --think-max 0   # предельная пропускная способность
```

Ключи: `--users 10,30,50`, `--duration 60`, `--think-min 1 --think-max 3`, `--employer-share 0.7`, `--pool 5`, `--seed 42`, `--out` (JSON с полными результатами). В конце печатается markdown-таблица, код выхода 1 — если доля ошибок на каком-то уровне выше `--max-error-rate` (1%). Стенду нужны демо-данные (`make reseed`).

**Предел пропускной способности.** Без пауз (`--think-min 0 --think-max 0`, 50 пользователей, 30 с) backend обслуживает **26 запросов в секунду** без ошибок, загружая одно ядро на 90%; задержки тогда растут до p50 1,5 с, p95 4,6 с — это очередь, а не сбои.

**Где тратится время.** Один запрос подборки — 8 SQL-запросов и 60–80 мс CPU: score и объяснение считаются на Python для всех кандидатов категорий потребности и соседних (§8), ответ — около 100 КБ JSON. Поиск без фильтра по специализации читает весь индекс выдачи (около 80 мс CPU), с фильтром — около 15 мс. Карточка — 18 SQL-запросов, 22 мс CPU. N+1 с заметным влиянием нет: в `GET /vacancies?match=true` около 6 запросов на опубликованную вакансию (31 на 5 вакансий), в `GET /needs` — 3 на потребность. Узкое место — CPU одного процесса Python, а не PostgreSQL.

## 5. Оптимизация

По результатам раздела 4 сделано:

| Что | Как | Эффект |
|---|---|---|
| Несколько процессов backend | uvicorn с `WEB_CONCURRENCY` процессами (по умолчанию 3, ~190 МБ каждый); используются 3 ядра из 4 | пропускная способность растёт почти линейно |
| Общие лимиты для всех процессов | ограничитель частоты `/auth/*` — счётчик скользящего окна в Postgres (`rate_limit_hits`, одна атомарная операция `INSERT … ON CONFLICT`); суточный бюджет и часовой лимит LLM на пользователя — в файлах состояния под межпроцессной блокировкой (`flock`) | 20 попыток входа в минуту — ровно 20 на все процессы вместе (проверено) |
| Кэш подборки | оценки кандидатов по потребности хранятся в памяти процесса; ключ — версия потребности и «отпечаток» индекса выдачи (число строк и время последнего пересчёта), TTL `RECOMMENDATIONS_CACHE_SECONDS` (60 с); фильтры, шорт-лист и статусы приглашений накладываются поверх при каждом запросе | подборка — 12 мс CPU вместо 93 мс; любое изменение кандидата или потребности сбрасывает кэш сразу (тест `test_recommendations_cache_follows_index_and_need_changes`) |
| Поиск в SQL | фильтры, сортировка и страница — в Postgres, Python собирает только карточки страницы | время не растёт с размером базы; совпадение с прежней логикой проверено тестом на 81 наборе фильтров |
| Вакансии кандидата | данные кандидата и цепочки версий читаются один раз на список, профиль компании — один раз на работодателя | вместо ~6 запросов на вакансию — постоянное число |

**Тот же тест после оптимизации** (та же машина и данные, что в разделе 4, 3 процесса):

| Операция | p95 до, мс (10 / 30 / 50) | p95 после, мс (10 / 30 / 50) |
|---|---|---|
| Подборка | 303 / 572 / 1 218 | 36 / 72 / 48 |
| Поиск по базе | 268 / 390 / 831 | 33 / 35 / 34 |
| Карточка кандидата | 124 / 357 / 839 | 257 / 45 / 48 |
| Вакансии с оценкой совпадения | 314 / 629 / 1 263 | 40 / 46 / 45 |
| **Всего** | 229 / 455 / 936 | **44 / 41 / 42** |

Ошибок нет ни на одном уровне; при 50 пользователях — 24,4 запроса в секунду при p50 24 мс (до — 20,9 при p50 289 мс): сервер больше не является узким местом, темп задают паузы пользователей.

**Прод до и после** — тот же тест против `https://itscout.ru` из облачной песочницы через её HTTPS-прокси; к каждому запросу добавляется около 0,2 с сети, поэтому медиана не опускается ниже ~0,2 с:

| Нагрузка | p50 до → после, мс | p95 до → после, мс |
|---|---|---|
| 10 пользователей | 219 → 206 | 558 → 589 |
| 30 пользователей | 292 → 214 | 941 → 588 |
| 50 пользователей | 448 → 209 | 1 358 → 569 |
| Подборка, 50 пользователей | 661 → 217 | 1 493 → 547 |
| Вакансии с оценкой совпадения, 50 пользователей | 796 → 223 | 1 925 → 509 |

До оптимизации задержка росла с нагрузкой (сервер копил очередь), после — не зависит от числа пользователей: остаётся только сеть. Одиночные ошибки (0,1–0,8%) — обрывы соединения примерно через 11 с (тайм-аут клиента — 30 с) в обоих прогонах и на любом уровне, в том числе при 10 пользователях; на локальном стенде их нет ни разу, поэтому это обрывы соединения на стороне прокси песочницы, а не отказы backend.

## 6. Вывод

- **Десятки пользователей — с запасом.** После оптимизации общий p95 на стенде — около 40 мс при 10, 30 и 50 одновременных пользователях, без ошибок; подборка, поиск и карточка кандидата укладываются в 0,1 с. На проде задержка больше не растёт с нагрузкой: p95 при 50 пользователях — 0,57 с вместо 1,36 с, и почти всё это — сеть до клиента.
- **Масштабирование дальше** — без изменений кода: больше процессов (`WEB_CONCURRENCY`) или второй сервер за балансировщиком, потому что всё общее состояние уже в Postgres и файлах под блокировкой; кэш подборки локален для процесса и потому безопасен.
