## 1. Продукт в одном абзаце

Кандидат регистрируется, проходит опрос по специализации и отрасли, выбирает грейд и сдаёт адаптивный тест. Система присваивает ему **категорию «специализация × грейд»** (например, «Backend · Middle»), видимую работодателю. Работодатель описывает потребность и получает подборку: рекомендованные категории и ранжированных кандидатов с объяснением. Внутри категории выше стоят кандидаты с более сильным подтверждённым профилем: результат теста, достижения ФСП, свежие решённые задания. Работодатель отправляет конкретному кандидату приглашение с обязательной вилкой зарплаты. Контакты кандидата раскрываются только после того, как он принял приглашение.

---

## 2. Принципы

1. **Категорию определяет тест, а не резюме.** Резюме и опрос нужны для заполнения профиля и сборки теста, но категорию не задают.
2. **Детерминированное ядро.** Грейд, категория, score и объяснение считаются кодом с конфигами. LLM только извлекает структуру из текста, оценивает открытые ответы по чек-листу и офлайн помогает писать черновики шаблонов.
3. **Сопоставимость через общую шкалу.** Кандидаты получают разные задания, но все задания одной специализации лежат на одной IRT-шкале. Поэтому результаты сопоставимы. Это ответ на требование ТЗ о «сопоставимой сложности и объективности».
4. **ФСП — бонус, а не штраф.** Профиль без истории ФСП работает полностью. ФСП поднимает кандидата в ранжировании и даёт подтверждённые компетенции.
5. **Честная доказательность.** У каждого навыка есть источник и статус: «Проверено тестом», «Подтверждено ФСП», «Заявлено». Число без объяснения не показывается.
6. **Каждый вечер демо-сценарий проходит на проде.**

```text
                    ┌────────────────────── Caddy (TLS, itscout.ru) ──────────────────────┐
                    │   /            → frontend (статика SPA)                             │
                    │   /api/*       → backend                                            │
                    │   /api/docs    → Swagger UI                                         │
                    │   /fsp-id/*    → keycloak (P1, демо ФСП ID)                         │
                    └─────────────────────────────────────────────────────────────────────┘
                                 │
        ┌────────────────────────┴───────────────────────────┐
        │ backend (FastAPI, модульный монолит)               │
        │  auth · candidates · resume · catalog · survey     │        ┌──────────────────┐
        │  testing · categories · employers · needs          │──HTTP─▶│ fsp-mock         │
        │  matching · invitations · applications · tasks     │        │ (реестр ФСП:     │
        │  fsp · notifications · admin                       │        │  участники,      │
        └───────┬───────────────────────┬────────────────────┘        │  результаты,     │
                │                       │                             │  разряды)        │
          PostgreSQL 16          Yandex AI Studio (LLM)               └──────────────────┘
                                 Unisender Go (HTTPS)                  keycloak realm "fsp" (P1)
```

- **Модульный монолит.** Каждый модуль — папка с `router.py`, `service.py`, `models.py`, `schemas.py`. Модули вызывают чужие `service`, но не трогают чужие модели напрямую.
- **fsp-mock — отдельный сервис.** Так видна граница внешней системы: в проде его заменяет реальный реестр ФСП без правок backend. Доступ по API-ключу (service-to-service).
- **Keycloak** (P1, профиль compose `fsp`) показывает привязку ФСП ID через OIDC, как она будет работать в проде.

## 6. Путь кандидата и правила грейда

### 6.1. Регистрация (P0)

1. Email и пароль, две отметки:
   - согласие на обработку ПДн (обязательно);
   - согласие на публикацию профиля работодателям (обязательно, чтобы попасть в поиск; можно отозвать в настройках).
2. Письмо со ссылкой подтверждения: токен одноразовый, живёт 24 часа. Пока домен в Unisender не подтверждён, `EMAIL_VERIFICATION_REQUIRED=false`: сессия выдаётся сразу, в кабинете — баннер «Подтвердите почту». С флагом `true` без подтверждения доступен только экран «Подтвердите почту».
   Сессия: access JWT 15 минут в ответе; refresh — httpOnly cookie на `/api/v1/auth`, ротация при каждом обновлении, повторное использование отозванного токена отзывает все сессии пользователя.
3. Демо-аккаунты из seed подтверждены заранее.

### 6.2. Онбординг (P0)

1. **Опрос по отрасли и специализации** (12 вопросов, `content/survey.yaml`). Шаги онбординга в API: `survey → specialization → grade → test → done`:
   - чем занимаетесь каждый день — несколько вариантов, к каждому привязаны веса специализаций;
   - основной язык и фреймворки (из онтологии);
   - стаж в ИТ;
   - роли в команде;
   - отрасли, в которых был опыт, и интересные отрасли;
   - формат работы, город, релокация;
   - ожидания по зарплате, от–до.

   По ответам система **рассчитывает специализацию** (суммирует веса и берёт максимум, показывает топ-2), кандидат подтверждает выбор. Стек определяет стек-модули теста.
2. **Необязательно — загрузка PDF-резюме** для предзаполнения профиля (раздел 7).
3. **Выбор грейда.** Подсказка по стажу: меньше года — Junior, 1–3 года — Middle, больше 3 лет — Senior. Выбирает сам кандидат.
4. **Тест на выбранный грейд** (раздел 10). Около 25 минут, по одному вопросу на экран, таймер, вернуться назад нельзя.
5. **Результат:**
   - экран с категорией, перцентилем в категории и разбором по темам;
   - если тест не пройден — предложение сдать тест на грейд ниже;
   - если пройден уверенно — предложение сдать тест на грейд выше.

### 6.3. Правила смены грейда (P0)

| Ситуация | Правило |
|---|---|
| **Калибровка** (категории ещё нет) | Цепочка тестов вниз или один раз вверх без ожидания. На каждый грейд — не больше одной попытки |
| Не прошёл тест на грейд G | Повтор на G — не раньше чем через 30 дней (защита от заучивания) |
| Категория уже есть, попытка повысить грейд | Не чаще раза в `GRADE_CHANGE_COOLDOWN_DAYS = 90` дней. Неудача **не понижает** текущий грейд |
| Добровольное понижение | Тест на грейд ниже, тот же интервал 90 дней |
| Срок действия результата | 12 месяцев. Затем категория помечается «требует подтверждения», в ранжировании у неё снижена свежесть |
| `DEMO_MODE=true` | В кабинете есть кнопка «Сбросить ограничения» — для показа жюри |

Вся история хранится: опрос, попытки, ответы, выданные категории. Кандидат видит её на экране «Категория и грейд».

### 6.4. Кабинет кандидата (P0, кроме отмеченного)

- **Профиль и резюме:** форма, загрузка PDF (P1), скачивание стандартного PDF-профиля (P1).
- **Категория и грейд:** текущий статус, история, кнопки «Повысить» и «Понизить» с таймером до следующей возможности.
- **Приглашения:** входящие с вилкой, компанией, описанием и объяснением «почему вам». Можно принять или отклонить, при отказе выбирается причина.
- **Вакансии и отклики** (P1): список, отклик, статусы.
- **Регулярные задания** (P2).
- **Настройки:**
  - приватность;
  - согласия с датами;
  - привязка ФСП ID;
  - статус поиска: «активно ищу», «открыт к предложениям», «не ищу» (в последнем случае профиль скрыт из поиска);
  - удаление аккаунта.

**Приватность** — галочки, по умолчанию разумные:
- показывать фамилию до контакта (по умолчанию нет — только имя и первая буква фамилии);
- показывать достижения ФСП (да);
- показывать зарплатные ожидания (да);
- скрыть профиль от выбранных компаний, например от текущего работодателя.

## 7. Резюме и PDF-профиль (P1)

**Импорт:**
1. Загрузка PDF до 5 МБ. Текст извлекается через pdfplumber. Сканы без текстового слоя — сообщение «заполните вручную», OCR после MVP.
2. Разбор текста. Сначала регулярки и словарь: email, телефон, Telegram, навыки по алиасам. Затем LLM по JSON-схеме: ФИО, контакты, стек (строго `skill_id` из онтологии; неизвестное — в `unmapped`), роли, стаж, опыт по местам работы, софт-скиллы, грейд. Ответ валидируется Pydantic. При ошибке — один повтор, потом откат на результат словаря.
3. Результат открывается как **предзаполненная форма**: кандидат подтверждает или правит. В БД — только подтверждённые данные.

**Экспорт.** Стандартный PDF-профиль (WeasyPrint, HTML-шаблон в стиле брендбука): категория, результат теста по темам, проверенный стек, достижения ФСП, опыт, QR-ссылка на профиль. Две версии:
- обезличенная — для работодателя до контакта;
- полная — после раскрытия контактов и для самого кандидата.

## 8. Механика подбора (35%)

### 8.1. Сценарий работодателя (P0)

1. **Профиль компании:** название, ИНН (необязательно, задел для верификации), отрасль, описание, сайт, контакты рекрутера.
2. **Потребность** — приватный запрос на подбор, не публичная вакансия. Задаётся текстом или формой. Текст разбирается (словарь, затем LLM) в редактируемую форму:
   - специализация и грейд;
   - обязательный и желательный стек;
   - отрасль, чем занимается команда;
   - формат, город;
   - **вилка от–до в рублях, обязательно**.

   Нераспознанные термины показываются: «не распознали: X, Y».
3. **Подборка** (экран из двух уровней):
   - **Рекомендованные категории** с объяснением: «Backend · Middle — точное совпадение, 37 кандидатов, 12 с ФСП, ваша вилка покрывает ожидания 64%». Плюс смежные: «Backend · Senior — 9 кандидатов, ожидания выше вилки у 70%», «Fullstack · Middle — смежная специализация».
   - **Кандидаты**, по умолчанию сгруппированы по категориям; переключатель «общий топ». Строка кандидата: score, категория, 2–3 причины, бейджи (ФСП, «проверено тестом», свежесть).
4. **Уточнение без потери подборки.** Фильтры поверх результата, их состояние хранится в URL. Кнопка «В шорт-лист» закрепляет кандидата за потребностью: он остаётся в шорт-листе при любой правке. Правка потребности создаёт новую версию, предыдущая доступна в истории.
5. **Карточка кандидата (обезличенная):**
   - имя и первая буква фамилии, категория, перцентиль в категории;
   - результаты теста по темам, проверенный и заявленный стек;
   - достижения ФСП, отрасли, формат, город, зарплатные ожидания;
   - свежесть: последний тест или задание;
   - полное объяснение совпадения с потребностью.

   Контактов нет.
6. **Приглашение:** заголовок, описание предложения, **вилка (обязательно)**, способ связи с работодателем (рекрутер, Telegram, email, телефон), необязательная привязка к потребности или вакансии, срок ответа (по умолчанию 14 дней). К приглашению автоматически прикладывается снимок объяснения совпадения — кандидат видит, почему выбрали именно его.
7. **Статусы приглашения:** `sent → viewed → accepted | declined | expired | withdrawn`. Обе стороны видят актуальный статус. После `accepted` работодателю открываются контакты кандидата (запись в `contact_unlocks` и в аудит).
8. **Поиск по всей базе** (P0) — отдельный экран без потребности. Фильтры: специализация, грейд, категория, стек (с флагом «только проверенный»), наличие ФСП, дисциплина и разряд ФСП, зарплата, формат, город, свежесть.

### 8.2. Кто виден в поиске

Кандидат попадает в выдачу, если одновременно:
- у него есть согласие на публикацию;
- статус поиска не «не ищу»;
- есть действующая категория;
- компания не в его списке скрытых.

### 8.3. Ранжирование

**Жёсткие фильтры** (переключаемые). Кандидаты, не прошедшие фильтр, не исчезают, а уходят в свёрнутый блок «Вне фильтров» с причиной:
- несовместимый формат работы: только офис или только удалёнка;
- другой город без готовности к релокации, если вакансия не удалённая;
- минимальные ожидания выше верхней границы вилки больше чем на 30%.

**Score:**

```text
match = 100 × ( 0.30·skills + 0.30·strength + 0.15·category + 0.10·fsp + 0.05·fresh + 0.10·conditions )
```

| Компонент | Расчёт |
|---|---|
| `category` | 1.0 — та же специализация и грейд; 0.6 — смежная специализация или грейд ±1; 0.3 — и то и другое; иначе кандидат не попадает в выдачу |
| `skills` | Взвешенное покрытие стека потребности: Σ(w·v) / Σw, где w = 1.0 для обязательных навыков и 0.3 для желательных. v: 1.0 — проверено тестом (≥2 задания по навыку, ≥70% верно); 0.9 — подтверждено ФСП или регулярным заданием; 0.5 — заявлено; 0.3 — есть только родительский навык; 0 — навыка нет |
| `strength` | 0.7·Φ((θ̂ − cut_целевой_грейд) / 0.6) + 0.3·topic_fit. θ̂ — оценка способности на шкале специализации, поэтому кандидаты разных грейдов сравнимы. `topic_fit` — средний балл кандидата по темам теста, взвешенным по стеку потребности (нужен PostgreSQL → тема «Базы данных») |
| `fsp` | max(competency_score × relevance(специализация, компетенция)) по компетенциям ФСП (раздел 9); 0, если ФСП нет |
| `fresh` | 0.5^(дней с последнего проверенного действия / 90) |
| `conditions` | 0.6·salary_fit + 0.4·format_fit. salary_fit = 1, если минимальные ожидания ≤ верхней границы вилки; линейно падает до 0 при превышении на 30% |

**Внутри категории без потребности** (каталог, поиск) — сила подтверждённого профиля:

```text
VPS = 0.60·θ̂_перцентиль_в_категории + 0.15·fsp + 0.15·fresh + 0.10·approach
```

`approach` — оценка открытых ответов о подходе к решению (раздел 10.5).

При равенстве score сортировка: ФСП, затем свежесть, затем дата теста.

### 8.4. Объяснимость (P0)

Объяснение собирается **кодом из тех же компонентов, что и score**, поэтому всегда с ним совпадает:

```text
Анна К. · Backend · Middle · 84
✓ Категория совпадает: Middle Backend, подтверждено тестом (78-й перцентиль)
✓ PostgreSQL — проверено тестом: «Базы данных» 85%
✓ Python — проверено тестом, FastAPI — заявлено
✓ ФСП: 2 место, всероссийский хакатон по продуктовому программированию (роль backend), 2025
⚠ Kafka — нет данных
⚠ Ожидания от 280 000 ₽ — выше вилки (до 250 000 ₽)
```

LLM в объяснении не используется: шаблон надёжнее и воспроизводим.

### 8.5. Сценарий кандидата

Кандидат видит приглашения с вилкой **до начала общения**. Принял — работодателю открываются контакты, кандидату — контакт рекрутера. Отклонил — выбирает причину: зарплата, стек, формат, компания, не ищу.

### 8.6. Чем выделяемся (P1, всё детерминированно и дёшево)

1. **Покрытие вилки.** При вводе вилки работодатель сразу видит распределение ожиданий в категории: «покрывает 64% кандидатов Backend · Middle». В списке кандидатов — пометка «ожидания выше вилки».
2. **Обратная связь по отказам.** Работодатель видит агрегат причин отказов по своим приглашениям: «3 из 5 отказов — зарплата». На существующих площадках этого нет.
3. **Лимит активных приглашений**: `MAX_ACTIVE_INVITES_PER_NEED = 15`. Заставляет приглашать адресно, а не рассылать спам. Ответ кандидата или истечение срока освобождает слот.
4. **Репутация работодателя для кандидата:** доля приглашений с реальной вилкой, средний срок ответа на отклики, доля отозванных приглашений. Это задел для защиты от недобросовестных работодателей.
5. **«Почему вам»** — кандидат видит объяснение совпадения так же, как работодатель. Прозрачность в обе стороны.
6. **Слепой первый просмотр:** без фото, возраста и пола, фамилия скрыта. Снижает предвзятость.

### 8.7. Вакансии и отклики (P1)

Вакансия — это потребность с флагом `published=true`. Отдельной сущности не нужно.
- Кандидат видит список вакансий. Сначала подходящие его категории, с тем же объяснением совпадения.
- Отклик с сопроводительным текстом сразу раскрывает контакты работодателю, как требует ТЗ.
- Статусы отклика: `sent → viewed → accepted | rejected`.
- Работодатель видит отклики по вакансии, отсортированные по тому же `match`.

## 9. ФСП

### 9.1. Модель данных реестра (наше предложение, в fsp-mock)

```text
Participant(fsp_id, full_name, birth_year, region)
Competition(id, name, discipline, level, format: individual|team, date, participants_count, organizer)
Result(id, fsp_id, competition_id, team_name, team_role, place, score, prize: winner|prize|participant)
Rank(fsp_id, discipline, rank: III|II|I|КМС|МС, awarded_at)
Activity(fsp_id, kind: judge|organizer|mentor, competition_id)
```

Дисциплины (сверить с экспертами ФСП): `algorithmic`, `product`, `infosec`, `drones`, `robotics`.

### 9.2. Сила результата и компетенции (переносим из ранних документов)

```text
percentile = 1 − (place − 1) / max(participants − 1, 1)
strength   = percentile × level_weight × 0.5^(возраст_в_годах / 3)
competency = 1 − Π(1 − strength_i)          # noisy-OR; для связи по роли strength × 0.7
competency = max(competency, rank_floor)     # МС 0.95 … III 0.40
```

**Уровни соревнований** (`level_weight`): международное — 1.0, всероссийское — 0.9, межрегиональное — 0.75, региональное — 0.6, муниципальное — 0.4.

**Компетенции и связь со специализациями** (`competency_relevance.yaml`):
- `algorithms` — 0.8 для всех разработческих специализаций, 0.6 для data;
- `product_team_dev` и компетенции по роли — 1.0 для специализации роли;
- `infosec_ctf` — 1.0 для devops, 0.6 для backend;
- `drones` и `robotics` — 0.3 как общий инженерный сигнал.

**Ограничение:** технологический навык (Python, Docker) из данных ФСП получает не больше статуса «подтверждено ФСП» и только через роль в продуктовой дисциплине. Проверенным навык делает только тест. Это осознанное решение и аргумент на защите.

### 9.3. Привязка ФСП ID

| Способ | Приоритет | Как работает |
|---|---|---|
| Ручной | P0 | Кандидат вводит ФСП ID и даёт согласие на импорт. Backend забирает данные из fsp-mock. Помечается как «не подтверждено владение» |
| OIDC через Keycloak | P1 | Кнопка «Войти через ФСП ID»: authorization code + PKCE к realm `fsp` в Keycloak; из токена берётся claim `fsp_id`. Так подтверждается владение и исключаются чужие достижения. В проде issuer заменяется реальным ФСП ID без изменения кода |

Импорт выполняется при привязке и затем раз в сутки (APScheduler). Отзыв согласия удаляет импортированные данные.

### 9.4. Показ работодателю

- В списке — бейдж «ФСП» и разряд.
- В карточке — блок «Подтверждено ФСП»: разряд, 3 сильнейших результата (место, участники, уровень, год, роль), компетенции со статусом, лента результатов.
- Фильтры: «есть ФСП», дисциплина, минимальный разряд.

**Без истории ФСП:** нейтральная плашка «Данных ФСП нет», никакого штрафа в категории. Кандидату показываем призыв «Привяжите ФСП ID или участвуйте в соревнованиях ФСП». Это ещё и воронка в соревнования — хороший тезис для питча.

## 10. Механика тестирования (25%)

### 10.1. Идея

Единый набор заданий утекает. Уникальные задания от нейросети несопоставимы по сложности. Наш подход — третий путь:

> **Калиброванный банк параметризованных шаблонов + адаптивная сборка теста по blueprint + оценка на общей IRT-шкале.**

- **Шаблон** — семейство изоморфных заданий: одна проверяемая идея и одна сложность, но параметры (числа, имена, код, данные, порядок, дистракторы) генерируются на каждую попытку из seed.
- Сложность и дискриминация задаются **на уровне шаблона** (IRT 2PL, для вопросов с выбором — 3PL с c = 1/k) и калибруются по ответам.
- Тест каждого кандидата собирается из банка по **blueprint** «специализация × грейд». Задания разные, но шкала одна, поэтому θ̂ сопоставимы.
- **LLM расширяет банк, а не выдаёт задания напрямую.** Черновые шаблоны от LLM проходят ревью человеком, затем стадию `pilot`: встраиваются в тесты как неоцениваемые, пока не наберут ответов для калибровки. Только после этого становятся `active`.

### 10.2. Формат шаблона

YAML; для вычисляемых заданий — Python-генератор.

```yaml
id: be.db.composite_index_order
specializations: [backend, data]
topic: databases
skills: [sql, postgresql]
kind: single_choice           # single_choice | multi_choice | numeric | ordering | code_output | sql_result | open_approach
irt: { b: 0.35, a: 1.3 }      # стартовая экспертная оценка; c = 1/k для выбора
status: active                 # pilot | active | retired
params:
  table: { choice: [orders, payments, events, shipments] }
  col_a: { choice: [customer_id, account_id, user_id] }
  col_b: { choice: [created_at, updated_at, paid_at] }
stem_variants:
  - "Запрос: SELECT * FROM {table} WHERE {col_a} = $1 ORDER BY {col_b} DESC LIMIT 20. Какой индекс лучше?"
  - "Нужно быстро получать последние 20 записей {table} конкретного {col_a}. Какой индекс создать?"
generator: generators.db.composite_index_order   # строит верный ответ и дистракторы
time_limit_sec: 90
```

```python
# generators/py/code_output.py — пример code_output: значения, имена и порядок операций
# генерируются из seed; верный ответ вычисляется детерминированно в Python (без exec),
# дистракторы строятся из типичных ошибок (off-by-one, мутабельный дефолт, порядок вычисления).
def list_default_arg(rng) -> Instance: ...
```

**Виды заданий:**
- выбор одного или нескольких вариантов с пулами дистракторов;
- числовой ответ (расчёт RPS, пула соединений, сложности);
- упорядочивание (шаги деплоя, этапы запроса);
- «что выведет код» на сгенерированном сниппете;
- «результат SQL-запроса» на сгенерированных данных;
- открытый вопрос о подходе (10.5).

Живой coding с песочницей — после MVP: возможна интеграция с тестирующей системой ФСП.

### 10.3. Blueprint и сборка теста

```yaml
# content/blueprints/backend.yaml
backend:
  topics: { http_api: 3, databases: 3, concurrency: 2, architecture: 2, stack: 4, algorithms: 2, testing: 1, security: 1 }
  open_approach: { from_grade: middle, count: 1 }
  pilot_slots: 2
  max_items: 22
```

**Двухэтапный адаптивный тест (MST).** Он проще и устойчивее полного CAT, а точнее всего работает как раз около порога грейда.
1. **Этап 1:** 9 заданий с b около `cut_G`, пропорционально темам blueprint.
2. **Этап 2:** 9 заданий. Если по этапу 1 θ̂ высокий — блок около `cut_{G+1}`, чтобы распознать уверенный проход. Если низкий — блок около `cut_{G−1}…cut_G`.
3. **Правило остановки:** если после 18 заданий |θ̂ − cut_G| < SE, добавляются до 4 заданий у порога.
4. Плюс 2 пилотных неоцениваемых слота (кандидат их не отличает) и открытый вопрос для Middle и выше.

**Отбор шаблонов:** случайный внутри темы и окна сложности с **контролем экспозиции** — вес шаблона ~ 1/(1 + доля показов); шаблоны с долей показов выше 25% временно исключаются. Внутри попытки темы не повторяются подряд. Варианты ответов перемешиваются.

### 10.4. Оценка и грейд

- θ̂ — **EAP** с априорным N(0, 1), квадратура на 61 точке (numpy). SE — апостериорное стандартное отклонение.
- **Пороги** на шкале специализации (стартовые, `content/blueprints.yaml`): `cut_intern = −1.8`, `cut_junior = −0.8`, `cut_middle = 0.2`, `cut_senior = 1.2`. Ниже порога стажёра категория не присваивается. Окончательные пороги — экспертная процедура *modified Angoff*: эксперт оценивает, с какой вероятностью «минимально компетентный Middle» решит каждый шаблон, и порог выводится из этих оценок. Описывается в документации.
- **Решение** по тесту на грейд G:
  - не пройден — θ̂ < cut_G;
  - пройден — θ̂ ≥ cut_G;
  - **пройден уверенно** — θ̂ − SE ≥ cut_G и θ̂ ≥ cut_{G+1} − SE. В этом случае предлагается тест на G+1.
- **Подсчёты по темам** — доля верных по теме (описательно, для объяснений). **Навык проверен**, если по нему ≥2 оценённых задания и ≥70% верно.
- **Перцентиль в категории** пересчитывается при появлении новых результатов.

### 10.5. Открытый вопрос о подходе (P1)

Для Middle и выше: «Как бы вы спроектировали X / нашли причину Y?», ответ до 1500 символов.
- LLM оценивает по **чек-листу из 4–6 бинарных критериев** из шаблона, температура 0, ответ в JSON со ссылками на фрагменты ответа.
- Итог хранится отдельно как `approach` (0..1) и **не входит в θ̂**, чтобы не смешивать шумную оценку с калиброванной шкалой.
- Работодатель видит сам ответ и отметки по критериям.

### 10.6. Защита от распространения заданий

| Угроза | Защита |
|---|---|
| Утечка конкретных вопросов и ответов | Параметризация: у каждой попытки свои числа, код и данные, поэтому ключ ответов из чужой попытки не подходит. Выучить шаблон — значит выучить концепцию |
| Слив пула вопросов | Большой банк (цель ≥ 3× задач на blueprint), случайная выборка, контроль экспозиции. В валидации считаем средний процент общих шаблонов между двумя попытками |
| Устаревание и компрометация шаблона | Мониторинг дрейфа: шаблон вдруг стал легче (растёт доля верных при том же θ) → флаг и вывод из ротации (`retired`) |
| Подсказчик или поиск в интернете | Лимит времени на задание, задания по одному, нельзя вернуться назад; копирование в вопросах отключено; уход со вкладки логируется (показывается флагом, не валит тест) |
| Аномальные паттерны | Статистика согласованности ответов (person-fit, lz): слишком много верных ответов на сложные задания при ошибках на простых → флаг. Ещё флаг — подозрительно быстрые верные ответы на сложные задания |
| Перебор попыток | Интервалы из 6.3, новый seed на каждую попытку |
| Пополнение банка | LLM-черновики → ревью → `pilot` → калибровка → `active` |

### 10.7. Тесты из описаний вакансий (P0 для демо)

ТЗ просит на нескольких описаниях вакансий показать, как формируются задания. Экран работодателя «Проверка под вакансию»:
1. Текст вакансии → разобранные требования.
2. **Blueprint под вакансию:** веса тем смещаются по требованиям. Например, вакансия требует Kafka и PostgreSQL → растут веса `messaging` и `databases`, добавляется стек-модуль `java`.
3. **Предпросмотр:** 3 примера сгенерированных заданий из банка с указанием шаблона, темы и сложности. Повторная генерация даёт другие экземпляры той же сложности — это наглядно показывает параметризацию.
4. **Черновики LLM** для навыков вакансии, которых нет в банке, со статусом `pilot` и пометкой «не влияют на оценку до калибровки».
5. Этот же blueprint используется в регулярных заданиях от работодателя (11).

**Демо-набор:** 4 вакансии (Backend Middle на Python, Frontend Junior на React, QA Middle, DevOps Senior) лежат в `content/demo_vacancies/`.

## 11. Регулярные задания (P2)

- Работодатель создаёт короткое задание: выбирает шаблон из банка (автопроверка) или пишет текст «предложите подход» (оценка по чек-листу LLM и, по желанию, оценка работодателя 1–5). Задание привязывается к специализации и грейду или к потребности.

## 12. Процедура валидации (P0, оценивается отдельно)

Папка `validation/`, запуск `make validate`. Результат детерминирован по seed. На выходе `validation/report.md` и PNG-графики, которые идут в документацию и в презентацию.

### 12.1. Симулированная популяция

- 2 000 синтетических кандидатов. У каждого: истинная специализация, истинная способность θ_true на шкале специализации (смесь распределений по грейдам), истинный стек, профили по темам (коррелированные отклонения от θ), заявленный грейд с шумом (20% завышают на 1, 10% занижают), история ФСП, коррелирующая с θ (у 35% она есть).
- Модель ответа: 3PL с параметрами шаблона **плюс случайное отклонение сложности экземпляра** (σ_b = 0.15). Это проверяет, что параметризация не ломает сопоставимость.
- Тест проходит через **тот же движок**, что и в продукте: импорт `backend/app/modules/testing/engine`.

### 12.2. Метрики

| Свойство (из критериев ТЗ) | Метрика |
|---|---|
| Согласованность (повторное прохождение) | Каждый кандидат проходит 2 независимые попытки → совпадение грейда в %, взвешенная κ Коэна, корреляция θ̂₁ и θ̂₂ |
| Соответствие эталону | Точность грейда относительно истинного, матрица ошибок, доля ошибок больше чем на один грейд |
| Дискриминативность | Точечно-бисериальная корреляция по шаблонам, информационная функция теста у порогов; распределения θ̂ сильных и слабых кандидатов |
| Устойчивость к утечке | (а) средняя доля общих шаблонов и общих экземпляров у двух попыток; (б) сценарий «слили 30% ключей»: на сколько завышается грейд у фиксированного теста (базовая линия) и у нашего |
| Сопоставимость форм | Для одинакового θ_true разные формы дают одинаковое среднее θ̂ (смещение по формам); устойчивость решения о грейде при σ_b |
| Калибровка | Восстановление b и a шаблонов из симулированных ответов (`girth`), RMSE относительно истинных значений |
| Категоризация | Точность определения специализации по опросу и резюме относительно истины; поля резюме — precision и recall на 30 синтетических и 5–10 реальных резюме |
| Подбор | 15 потребностей; истинная релевантность 0–3 из истинных специализации, грейда и стека → **precision@5/10 и nDCG@10**. Сравнение трёх способов ранжирования: наш `match`, ключевые слова по резюме, заявленный грейд |
| Экспертная оценка | Участник команды и 2–3 приглашённых ИТ-специалиста размечают 100 пар «потребность — карточка кандидата» по шкале 0–3 → корреляция Спирмена с нашим ранжированием, P@5 |

### 12.3. Честные ограничения (пишем в отчёте)

Симуляция проверяет механику при заданной модели ответов. Реальную калибровку параметров дают только пилотные данные. Мы описываем, как она устроена: пилотные слоты и периодическая перекалибровка.

## 13. Безопасность и 152-ФЗ (P0)

- **Пароли и сессия.** Пароли хранятся как argon2id. Access JWT живёт 15 минут. Refresh-токен лежит в httpOnly Secure cookie и меняется при каждом обновлении; в БД — только хэши.
- **Защита от подбора.** Ограничение частоты запросов на `/auth/*`.
- **Разграничение доступа.** Роли проверяются dependency-функциями FastAPI. Проверки на уровне объектов вынесены в сервисы и покрыты тестами:
  - кандидат видит только свои приглашения и отклики;
  - работодатель видит контакты, только если есть запись в `contact_unlocks`;
  - работодатель видит только свои потребности и приглашения.
- **Ответы на тест.** Ключи ответов не уходят на фронт; ответ принимается только для текущего задания и в пределах времени (время считается на сервере).
- **Согласия.** Хранятся с версией текста политики и датой; отзыв согласия работает.
- **Удаление аккаунта.** Мягкое удаление с обезличиванием ПДн.
- **Аудит.** Журнал раскрытия контактов и изменения согласий.
- **Персональные данные.** Резюме обрабатываются через Yandex AI Studio, данные не уходят за рубеж. В БД хранятся только подтверждённые пользователем данные.
- **Секреты.** В `.env` на сервере, в репозитории только `.env.example`. CORS — только свой домен.

## 17. Синтетика и демо-данные (`backend/seed/`)

## 18. Демо-сценарий (e2e и видео)

1. Новый кандидат регистрируется и подтверждает почту (на проде — реальное письмо).
2. Проходит опрос: система предлагает специализацию Backend, выбран грейд Middle.
3. Сдаёт тест (в демо-режиме — сокращённый, 8 заданий), получает категорию «Backend · Middle» и разбор по темам.
4. Работодатель «Демо Банк» создаёт потребность текстом и видит разбор и покрытие вилки.
5. Открывает подборку: рекомендованные категории и топ кандидатов с объяснениями. Фильтрует «есть ФСП», закрепляет двоих в шорт-листе, меняет фильтр — шорт-лист на месте.
6. Открывает карточку героя: тест по темам, блок ФСП, контактов нет.
7. Отправляет приглашение с вилкой 220–260 тыс. ₽.
8. Кандидат видит приглашение, вилку и «почему вам» → принимает.
9. Работодатель видит статус «принято» и контакты кандидата.
10. Классический путь: кандидат откликается на вакансию, работодатель сразу видит контакты.
11. «Проверка под вакансию»: blueprint и 3 примера заданий, повторная генерация даёт другие экземпляры той же сложности.

Шаги 1–9 покрыты Playwright-тестом и прогоняются после каждого деплоя.

## 20. Деплой и CI/CD

- **compose:** `infra/docker-compose.yml` — сервисы `caddy`, `frontend` (сборка Vite, статика в volume для Caddy), `backend`, `db`, `fsp-mock`; профиль `fsp` добавляет `keycloak`. `docker-compose.dev.yml` добавляет `mailpit` и hot reload.
- **CI** (`.github/workflows/ci.yml`, на каждый push): ruff, миграции с нуля + `alembic check`, pytest, актуальность `openapi.json` и сгенерированного клиента, lint/typecheck/build фронта.
- **Deploy** (push в `master`, после зелёного CI): rsync репозитория в `/opt/itscout/app` → `docker compose up -d --build` (backend сам применяет миграции при старте) → smoke-тест `/api/v1/health` (позже — Playwright). Единственный секрет GitHub — `DEPLOY_SSH_KEY` (отдельный ключ деплоя). Остальные секреты — в `/opt/itscout/app/.env` на сервере (права 600).
- **HTTPS:** после появления A-записи `itscout.ru` в `Caddyfile` включается блок домена.
- **Почта:** контейнер `mail` (Postfix, только отправка) подписывает письма DKIM (селектор `mail`, ключ в volume `dkim`). В DNS: SPF `v=spf1 ip4:94.103.87.151 -all`, DKIM `mail._domainkey`, DMARC; PTR IP → `itscout.ru` в панели VDSina.
- **Запуск с нуля:** `docs/deploy.md` — `cp .env.example .env && docker compose up -d` поднимает всё, включая seed.

**Что идёт в доработку 19–21.10 при нехватке времени:** регулярные задания, Keycloak, мобильная вёрстка, расширение банка, экспертная разметка 100 пар.

## 24. Концепции вне MVP (только в документации)

**Защита от фиктивных вакансий и недобросовестных работодателей:**
- верификация компании: корпоративный домен email, проверка ИНН через открытые данные ФНС;
- проверка вилки на адекватность рынку категории;
- рейтинг по откликам и отказам, жалобы кандидатов;
- очередь модерации для помеченных;
- бейдж «Проверенный работодатель»;
- лимиты приглашений для новых компаний.

**Интеграция с ATS:**
- API-ключи работодателя;
- исходящие webhook'и (`invitation.accepted`, `application.created`);
- экспорт кандидата в JSON Resume;
- коннекторы к российским ATS (Huntflow, Talantix, Potok) через их API.

**Реальная интеграция с ФСП:**
- OIDC через ФСП ID (Keycloak);
- REST-API реестра с client credentials;
- webhook о новых результатах;
- scope согласия `fsp:achievements:read`.
