## 1. Продукт в одном абзаце

Кандидат регистрируется, проходит опрос по специализации и отрасли, выбирает грейд и сдаёт адаптивный тест. Система присваивает ему **категорию «специализация × грейд»** (например, «Backend · Middle»), видимую работодателю. Работодатель описывает потребность и получает подборку: рекомендованные категории и ранжированных кандидатов с объяснением. Внутри категории выше стоят кандидаты с более сильным подтверждённым профилем: результат теста, достижения ФСП, свежие решённые задания. Работодатель отправляет конкретному кандидату приглашение с обязательной вилкой зарплаты. Контакты кандидата раскрываются только после того, как он принял приглашение.

---

## 2. Принципы

1. **Категорию определяет тест, а не резюме.** Резюме и опрос нужны для заполнения профиля и сборки теста, но категорию не задают.
2. **Детерминированное ядро.** Грейд, категория, score и объяснение считаются кодом с конфигами. LLM только извлекает структуру из текста, оценивает открытые ответы по чек-листу и офлайн помогает писать черновики шаблонов.
3. **Сопоставимость через общую шкалу.** Кандидаты получают разные задания, но все задания одной специализации лежат на одной IRT-шкале. Поэтому результаты сопоставимы. Это ответ на требование ТЗ о «сопоставимой сложности и объективности».
4. **ФСП — бонус, а не штраф.** Профиль без истории ФСП работает полностью. ФСП поднимает кандидата в ранжировании и даёт подтверждённые компетенции.
5. **Честная доказательность.** У каждого навыка есть источник и статус: «Проверено тестом», «Подтверждено ФСП», «Заявлено». Число без объяснения не показывается.
6. **Каждый вечер демо-сценарий проходит на проде.**

        │  testing · categories · employers · needs          │──HTTP─▶│ fsp-mock         │
        │  matching · invitations · applications · tasks     │        │ (реестр ФСП:     │
        │  fsp · notifications · admin                       │        │  участники,      │
        └───────┬───────────────────────┬────────────────────┘        │  результаты,     │

          PostgreSQL 16          Yandex AI Studio (LLM)               └──────────────────┘

- **Модульный монолит.** Каждый модуль — папка с `router.py`, `service.py`, `models.py`, `schemas.py`. Модули вызывают чужие `service`, но не трогают чужие модели напрямую.
- **fsp-mock — отдельный сервис.** Так видна граница внешней системы: в проде его заменяет реальный реестр ФСП без правок backend. Доступ по API-ключу (service-to-service).
- **Keycloak** (P1, профиль compose `fsp`) показывает привязку ФСП ID через OIDC, как она будет работать в проде.

## 6. Путь кандидата и правила грейда

### 6.1. Регистрация (P0)

1. Email и пароль, две отметки:
   - согласие на обработку ПДн (обязательно);
   - согласие на публикацию профиля работодателям (обязательно, чтобы попасть в поиск; можно отозвать в настройках).

   Каждая отметка ссылается на свой документ (§13.1): `/legal/consent-pd` и `/legal/consent-publication`, ниже формы — ссылка на правила рекомендательных технологий.
2. Письмо со ссылкой подтверждения: токен одноразовый, живёт 24 часа. Пока доставляемость писем с собственного Postfix не проверена, `EMAIL_VERIFICATION_REQUIRED=false`: сессия выдаётся сразу, в кабинете — баннер «Подтвердите почту». С флагом `true` без подтверждения доступен только экран «Подтвердите почту».
   Сессия: access JWT 15 минут в ответе; refresh — httpOnly cookie на `/api/v1/auth`, ротация при каждом обновлении, повторное использование отозванного токена отзывает все сессии пользователя.
3. Демо-аккаунты из seed подтверждены заранее.

### 6.2. Онбординг (P0)

1. **Опрос по отрасли и специализации** (12 вопросов, `content/survey.yaml`). Шаги онбординга в API: `survey → specialization → grade → test → done`:
   - чем занимаетесь каждый день — несколько вариантов, к каждому привязаны веса специализаций;
   - основной язык и фреймворки (из онтологии);
   - стаж в ИТ;
   - роли в команде;
   - отрасли, в которых был опыт, и интересные отрасли;
   - формат работы, город, релокация;
   - ожидания по зарплате, от–до.

   По ответам система **рассчитывает специализацию** (суммирует веса и берёт максимум, показывает топ-2), кандидат подтверждает выбор. Стек определяет стек-модули теста.
2. **Необязательно — загрузка PDF-резюме** для предзаполнения профиля (раздел 7).
3. **Выбор грейда.** Подсказка по стажу: меньше года — Junior, 1–3 года — Middle, больше 3 лет — Senior. Выбирает сам кандидат.
4. **Тест на выбранный грейд** (раздел 10). Около 25 минут, по одному вопросу на экран, таймер, вернуться назад нельзя.
5. **Результат:**
   - экран с категорией, перцентилем в категории и разбором по темам;
   - если тест не пройден — предложение сдать тест на грейд ниже;
   - если пройден уверенно — предложение сдать тест на грейд выше.

### 6.3. Правила смены грейда (P0)

| Ситуация | Правило |
|---|---|
| **Калибровка** (категории ещё нет) | Цепочка тестов вниз или один раз вверх без ожидания. На каждый грейд — не больше одной попытки |
| Не прошёл тест на грейд G | Повтор на G — не раньше чем через 30 дней (защита от заучивания) |
| Категория уже есть, попытка повысить грейд | Не чаще раза в `GRADE_CHANGE_COOLDOWN_DAYS = 90` дней. Неудача **не понижает** текущий грейд |
| Добровольное понижение | Тест на грейд ниже, тот же интервал 90 дней |
| Срок действия результата | 12 месяцев. Затем категория помечается «требует подтверждения», в ранжировании у неё снижена свежесть; тест на тот же грейд снова доступен (кнопка «Подтвердить», действие `reconfirm`), пройденный — продлевает категорию, неудача её не понижает, повтор — через 30 дней |
| Перепроверка своего грейда (настройка `GRADE_RETEST_CAN_DOWNGRADE`, по умолчанию выключена) | Тест на свой действующий грейд — не чаще раза в `GRADE_CHANGE_COOLDOWN_DAYS` (кнопка «Перепроверить»). Пройден — категория продлевается; провал — категория понижается до старшего грейда, чей порог не выше θ̂ этой попытки, а ниже порога стажёра снимается. Так работает пример постановщиков «ниже порога — грейд ниже»; по умолчанию провал не понижает никогда |
| `DEMO_MODE=true` | В кабинете есть кнопка «Сбросить ограничения» — для показа жюри |

Правила считаются внутри специализации: провал Backend · Middle не блокирует Frontend · Middle. Незавершённый тест блокирует любой новый, а специализацию нельзя сменить, пока тест идёт (409 `attempt_in_progress`) или есть действующая категория (409 `specialization_locked`). Сроки в текстах ошибок берутся из настроек (`FAILED_GRADE_RETRY_DAYS`, `GRADE_CHANGE_COOLDOWN_DAYS`).

Вся история хранится: опрос, попытки, ответы, выданные категории. Кандидат видит её на экране «Категория и грейд».

### 6.4. Кабинет кандидата (P0, кроме отмеченного)

- **Профиль и резюме:** форма, загрузка PDF (P1), скачивание стандартного PDF-профиля (P1).
- **Категория и грейд:** текущий статус, история, кнопки «Повысить» и «Понизить» с таймером до следующей возможности; блок «Как определён грейд» с кнопкой «Оспорить» (§13.1).
- **Приглашения:** входящие с вилкой, компанией, описанием и объяснением «почему вам». Можно принять или отклонить, при отказе выбирается причина.
- **Вакансии и отклики** (P1): список, отклик, статусы.
- **Регулярные задания** (P2).
- **Настройки:**
  - приватность;
  - согласия с датами;
  - привязка ФСП ID;
  - статус поиска: «активно ищу», «открыт к предложениям», «не ищу» (в последнем случае профиль скрыт из поиска);
  - уведомления на почту (§8.9);
  - удаление аккаунта.

**Приватность** — галочки, по умолчанию разумные:
- показывать фамилию до контакта (по умолчанию нет — только имя и первая буква фамилии);
- показывать достижения ФСП (да);
- показывать зарплатные ожидания (да);
- скрыть профиль от выбранных компаний, например от текущего работодателя.

Скрытые зарплата и ФСП не попадают в индекс выдачи: для подбора, объяснения и фильтров поиска скрытая зарплата неизвестна, а ФСП отсутствует. Иначе точную сумму можно найти бинарным поиском по `salary_max`, а скрытый ФСП — фильтром `has_fsp`.

## 7. Резюме и PDF-профиль (P1)

**Импорт:**
1. Загрузка PDF до 5 МБ. Текст извлекается через pdfplumber. Сканы без текстового слоя — сообщение «заполните вручную», OCR после MVP.
2. Разбор текста. Сначала регулярки и словарь: email, телефон, Telegram, навыки по алиасам. Затем LLM по JSON-схеме: ФИО, контакты, стек (строго `skill_id` из онтологии; неизвестное — в `unmapped`), роли, стаж, опыт по местам работы, софт-скиллы, грейд. Ответ валидируется Pydantic. При ошибке — один повтор, потом откат на результат словаря.
3. Результат открывается как **предзаполненная форма**: кандидат подтверждает или правит. В БД — только подтверждённые данные.

**Экспорт.** Стандартный PDF-профиль (WeasyPrint, HTML-шаблон в стиле брендбука): категория, результат теста по темам, проверенный стек, достижения ФСП, опыт, QR-ссылка на профиль. Две версии:
- обезличенная — для работодателя до контакта;
- полная — после раскрытия контактов и для самого кандидата.

**Как реализовано (T15).**
- `POST /candidates/me/resume` (`backend/app/modules/resume/`): файл кладётся в `UPLOAD_DIR/resumes/<candidate_id>/`, в `resumes` — полный путь (по нему файл удаляется вместе с аккаунтом), текст и черновик разбора. Лимиты — в настройках: `RESUME_MAX_BYTES` (5 МБ), `RESUME_MAX_PAGES` (10), `RESUME_MIN_TEXT_CHARS` (меньше — считаем сканом и просим заполнить вручную). Неподходящий файл → 422 с кодом `file_too_large`, `not_pdf` или `invalid_pdf`.
- Словарный разбор переиспользует матчер навыков и детекторы города, формата, вилки и отраслей из разбора потребностей (`needs/parser.py`). Дополнительно: ФИО из шапки, email, телефон, Telegram, релокация, стаж, места работы (оба частых порядка: «период → компания → должность» и «должность, компания → период»), роли и софт-скиллы по ключевым словам. Неизвестные термины берутся только из раздела «Навыки».
- LLM только дополняет пустые поля значениями из справочников; ответ проверяется Pydantic, при ошибке — один повтор с пометкой, затем словарный результат. **Грейд у LLM не запрашивается**: резюме не выставляет ни грейд, ни категорию; `suggested_grade` — подсказка по стажу из `survey.yaml`, как в онбординге.
- Ответ — `prefill`: текущий профиль, дополненный резюме (заполненное кандидатом не перетирается, навыки и опыт объединяются) и список полей `from_resume`. Профиль меняется только после подтверждения через `PUT /candidates/me`; навыки из резюме сохраняются со статусом «заявлено».
- `GET /candidates/me/profile.pdf?variant=full|public` и `GET /talent/candidates/{id}/profile.pdf`. PDF работодателя строится из карточки кандидата с теми же проверками доступа: полная версия — только при записи в `contact_unlocks`, иначе обезличенная (имя и первая буква фамилии, без контактов и названий компаний, с учётом настроек приватности). В обезличенной версии контакты дополнительно вычищаются из свободного текста («О себе», описания опыта).
- Шрифты PDF (JetBrains Mono, Inter latin+cyrillic, WOFF2) лежат в `resume/assets/fonts`, системные библиотеки WeasyPrint (pango, harfbuzz-subset) ставятся в `backend/Dockerfile` и в CI.

## 8. Механика подбора (35%)

### 8.1. Сценарий работодателя (P0)

1. **Профиль компании:** название, ИНН (необязательно, задел для верификации), отрасль, описание, сайт, контакты рекрутера.
2. **Потребность** — приватный запрос на подбор, не публичная вакансия. Задаётся текстом или формой. Текст разбирается (словарь, затем LLM) в редактируемую форму:
   - специализация и грейд;
   - обязательный и желательный стек;
   - отрасль, чем занимается команда;
   - формат, город;
   - **вилка от–до в рублях, обязательно**. Все суммы на платформе — **на руки** (после НДФЛ): вилки, ожидания кандидата и фильтры подписаны «₽ на руки» в интерфейсе, письмах и описании API. На встрече с постановщиками сказали, что гросс или нетто — непринципиально, главное подписать (`docs/qa-summary-fsp-2026.md`).

   Нераспознанные термины показываются: «не распознали: X, Y».

   **Проверка на запрещённые требования** (ТК РФ ст. 3, 64; 565-ФЗ ст. 53): название, исходный текст и описание команды проверяются правилами из `content/need_text_rules.yaml` — возраст, пол, национальность, место жительства и регистрация, семейное положение, религия (severity `block`), внешность и гражданство (`warn`, гражданство законно только по прямому требованию закона). Регулярные выражения без LLM; у правил возраста есть исключение по контексту («опыт от 10 лет» не срабатывает). Найденные фрагменты с пояснением показываются при разборе текста и на странице потребности (`text_issues` в `NeedParseResult` и `NeedOut`). Режим `NEED_TEXT_CHECK`: `block` (по умолчанию) — публикация как вакансии и правка опубликованной отвечают 409 `need_text_discriminatory` со списком фрагментов, приватную потребность сохранить можно; `warn` — только подсказки; `off` — проверки нет.
3. **Подборка** (экран из двух уровней):
   - **Рекомендованные категории** с объяснением: «Backend · Middle — точное совпадение, 37 кандидатов, 12 с ФСП, ваша вилка покрывает ожидания 64%». Плюс смежные: «Backend · Senior — 9 кандидатов, ожидания выше вилки у 70%», «Fullstack · Middle — смежная специализация».
   - **Кандидаты**, по умолчанию сгруппированы по категориям; переключатель «общий топ». Строка кандидата: score, категория, 2–3 причины, бейджи (ФСП, «проверено тестом», свежесть).
4. **Уточнение без потери подборки.** Фильтры поверх результата, их состояние хранится в URL. Кнопка «В шорт-лист» закрепляет кандидата за потребностью: он остаётся в шорт-листе при любой правке. Если после правки категория кандидата вне окрестности потребности, score для него не определён: он показывается в шорт-листе отдельной карточкой «не подходит под новые требования» (`shortlist_outside`, те же проверки видимости), его можно открыть или убрать. Правка потребности создаёт новую версию, предыдущая доступна в истории.
5. **Карточка кандидата (обезличенная):**
   - имя и первая буква фамилии, категория, перцентиль в категории;
   - результаты теста по темам, проверенный и заявленный стек;
   - достижения ФСП, отрасли, формат, город, зарплатные ожидания;
   - свежесть: последний тест или задание;
   - полное объяснение совпадения с потребностью.

   Контактов нет.
6. **Приглашение:** заголовок, описание предложения, **вилка (обязательно)**, способ связи с работодателем (рекрутер, Telegram, email, телефон), необязательная привязка к потребности или вакансии, срок ответа (по умолчанию 14 дней). К приглашению автоматически прикладывается снимок объяснения совпадения — кандидат видит, почему выбрали именно его.
7. **Статусы приглашения:** `sent → viewed → accepted | declined | expired | withdrawn`. Обе стороны видят актуальный статус. После `accepted` работодателю открываются контакты кандидата (запись в `contact_unlocks` и в аудит).
8. **Поиск по всей базе** (P0) — отдельный экран без потребности. Фильтры: специализация, грейд, категория, стек (с флагом «только проверенный»), наличие ФСП, дисциплина и разряд ФСП, зарплата, формат, город, свежесть.

### 8.2. Кто виден в поиске

Кандидат попадает в выдачу, если одновременно:
- у него есть согласие на публикацию;
- статус поиска не «не ищу»;
- есть действующая категория;
- компания не в его списке скрытых.

### 8.3. Ранжирование

**Жёсткие фильтры** (переключаемые). Кандидаты, не прошедшие фильтр, не исчезают, а уходят в свёрнутый блок «Вне фильтров» с причиной:
- несовместимый формат работы: только офис или только удалёнка;
- другой город без готовности к релокации, если вакансия не удалённая;
- минимальные ожидания выше верхней границы вилки больше чем на 30%.

**Score:**

```text
match = 100 × ( 0.45·skills + 0.22·strength + 0.16·category + 0.01·fsp + 0.05·fresh + 0.11·conditions )
```

| Компонент | Расчёт |
|---|---|
| `category` | 1.0 — та же специализация и грейд; 0.6 — смежная специализация; 0.3 — грейд ±1; 0.15 — и то и другое (`category_fit` в `content/matching.yaml`; соседний грейд штрафуется сильнее по итогам валидации, §12); иначе кандидат не попадает в выдачу |
| `skills` | Взвешенное покрытие стека потребности: Σ(w·v) / Σw, где w = 1.0 для обязательных навыков и 0.3 для желательных. v: 1.0 — проверено тестом (≥2 задания по навыку, ≥70% верно); 0.9 — подтверждено ФСП или регулярным заданием; 0.5 — заявлено; 0.3 — есть только родительский навык; 0 — навыка нет. **Близкий навык:** требуемого нет, но есть близкий из замороженной таблицы `content/skill_similarity.yaml` (PostgreSQL ↔ MySQL 0.7, Kafka ↔ RabbitMQ 0.5, React ↔ Vue 0.5 …) — v = близость × ценность статуса близкого навыка, не больше 0.3 — как у родительского навыка и ниже «заявлено» (на синтетике потолок 0.6 снижал P@5 на 0.05, потолок 0.3 — на 0.01, в пределах шума; §12, отчёт валидации, раздел 10.2); засчитывается, только если близкий даёт больше родительского. Параметры и выключатель — `skill_similarity` в `content/matching.yaml` (по умолчанию включено). Фильтры по навыкам («только проверенный стек», навыки в поиске по базе) и «Рынок категории» для кандидата близкие навыки не засчитывают |
| `strength` | 0.7·ability + 0.3·topic_fit; ability = Φ((θ̂ − cut_G) / 0.6) − 1.5·max(0, 2·Φ((θ̂ − cut_{G+1}) / 0.6) − 1). θ̂ — оценка способности на шкале специализации, поэтому кандидаты разных грейдов сравнимы. До порога следующего грейда более сильный выше (требование ТЗ к порядку внутри категории); за порогом — штраф «перерос грейд» и предупреждение в объяснении («по тесту уже ближе к уровню Senior»). `topic_fit` — средний балл кандидата по темам теста, взвешенным по стеку потребности (нужен PostgreSQL → тема «Базы данных») |
| `fsp` | max(competency_score × relevance(специализация, компетенция)) по компетенциям ФСП (раздел 9); 0, если ФСП нет |
| `fresh` | 0.5^(дней с последнего проверенного действия / 90); полураспад — `freshness.half_life_days` в `content/matching.yaml` |
| `conditions` | 0.6·salary_fit + 0.4·format_fit. salary_fit = 1, если минимальные ожидания ≤ верхней границы вилки; линейно падает до 0 при превышении на 30% |

**Внутри категории без потребности** (каталог, поиск) — сила подтверждённого профиля:

```text
VPS = 0.60·θ̂_перцентиль_в_категории + 0.15·fsp + 0.15·fresh + 0.10·approach
```

`approach` — оценка открытых ответов о подходе к решению (раздел 10.5). Если её нет (LLM выключен или открытых ответов не было), это «нет данных», а не ноль: остальные три слагаемых делятся на 0,90. Свежесть в сортировке поиска считается на момент запроса (SQL-выражение с той же формулой), а не берётся из индекса, где она застыла на момент пересчёта. Веса VPS — `vps_weights` в `content/matching.yaml`.

При равенстве score сортировка: ФСП, затем свежесть, затем дата теста.

Вес `fsp` снижен с 0.10 до 0.01 (до +1 балла) по аудиту справедливости (§12.2): при 0.10 бонус решал топ-10 — кандидаты без ФСП при равной способности попадали туда в 0,40 раза реже (правило 4/5 нарушено), при 0.03 — 0,66, при 0.01 — 0,78–0,80 на двух выборках (у самой границы 4/5, чуть ниже), при 0 — 0,87 (остаток — ФСП в силе профиля и тай-брейк); освободившиеся 0.09 распределены между остальными компонентами, больше всего — `skills`. ФСП остаётся небольшим преимуществом и первым тай-брейком при равном score. Веса `skills` / `strength` (тогда 0.40 / 0.20) и штраф «перерос грейд» (λ = 1.5) выбраны по валидации (§12, бенчмарк из 60 потребностей): при прежних 0.30 / 0.30 без штрафа сильный кандидат категории, по тесту уже уровня следующего грейда, вытеснял из топа точное совпадение (P@5 0.65, в «общем топе» 0.60); сейчас P@5 0.69 (95% ДИ 0.63–0.75; в «общем топе» 0.69), nDCG@10 0.81, доля переросших в топ-10 — 2%.

#### 8.3.1. Вероятность, что кандидат примет приглашение

Двусторонний подбор (LinkedIn Recruiter, reciprocal recommenders): работодателю полезно видеть не только «подходит ли кандидат», но и «примет ли он приглашение». Данных о принятиях для обучения пока нет, поэтому оценка — прозрачная логистическая модель с коэффициентами в `acceptance` (`content/matching.yaml`), без ML и без LLM (`scoring.acceptance`):

```text
p = σ(intercept + Σ вкладов факторов)
```

| Фактор | Вклад в логит |
|---|---|
| Вилка против ожиданий | 4·clip((верх вилки − salary_min) / salary_min, ±0.5); +0.4, если и нижняя граница не ниже ожиданий |
| Формат | +0.3 — формат потребности среди форматов кандидата; −1.5 — нет |
| Город (работа не удалённая) | −0.6 — другой город, готов к переезду; −2.0 — переезд не рассматривает |
| Статус поиска | +0.5 — «активно ищу»; «открыт к предложениям» — 0 |
| Активные приглашения других компаний | −0.15 за каждое, не больше 5 |
| Причины прошлых отказов (от 2 отказов) | доля отказов «зарплата» усиливает фактор вилки, «формат» — факторы формата и города: × (1 + доля); доля «не ищу» × (−1.0) |

Уровни: высокая — p ≥ 0.6, средняя — p ≥ 0.35, иначе низкая. Текст собирается из тех же вкладов, что и p: для высокой — два самых сильных плюса, для низкой — два самых сильных минуса, для средней — два самых сильных по модулю: «Вероятность, что кандидат примет приглашение: низкая — вилка ниже ожиданий (прошлые отказы — чаще из-за зарплаты), у кандидата уже есть активные приглашения (3)».

- **Кто видит.** Только работодатель: поле `acceptance` в `CandidateMatch` — в подборке и в карточке кандидата с потребностью (`?need_id=`), фронт показывает его строкой под объяснением. В снимок «почему вы» для кандидата (приглашение, отклик) оно не входит. Своё активное приглашение компании «занятостью» кандидата не считается.
- **Влияние на порядок — за флагом.** `acceptance.rank_weight` = 0 (по умолчанию): score и порядок не меняются, вероятность только показывается. При w > 0 `scoring.evaluate` умножает match на (1 − w) + w·p — в той же функции, поэтому число в ответе и score не расходятся (`affects_score` в ответе). По умолчанию выключено. На синтетике (§12.2, отчёт валидации, раздел 10.1) показ без множителя даёт accept@5 47% при P@5 0.66; w = 0.3 — 59% при 0.65, w = 0.6 — 66% при 0.62; оценка согласуется с синтетической «истиной» (Спирмен 0.91). Но «истина» построена из тех же по природе факторов, коэффициенты не откалиброваны на реальных ответах, а вилка и формат уже входят в score (`conditions`) — множитель включается после проверки на живых данных (доля принятых приглашений по уровням вероятности). `acceptance.enabled: false` убирает оценку совсем.
- **Источник данных** — индекс выдачи и таблица `invitations`: `search_status` кандидата, число активных (`sent`/`viewed`, срок не истёк) приглашений по компаниям и счётчики причин отказа; новых таблиц нет.

### 8.4. Объяснимость (P0)

Объяснение собирается **кодом из тех же компонентов, что и score**, поэтому всегда с ним совпадает:

```text
Анна К. · Backend · Middle · 84
✓ Категория совпадает: Middle Backend, подтверждено тестом (78-й перцентиль)
✓ PostgreSQL — проверено тестом: «Базы данных» 85%
✓ Python — проверено тестом, FastAPI — заявлено
✓ ФСП: 2 место, всероссийский хакатон по продуктовому программированию (роль backend), 2025
⚠ Kafka — нет данных
⚠ Ожидания от 280 000 ₽ — выше вилки (до 250 000 ₽)
```

Зачёт за близкий навык — отдельной строкой: «PostgreSQL — нет, есть близкий MySQL (зачтено 30%)». Вероятность принятия приглашения (§8.3.1) показывается работодателю отдельной строкой под объяснением.

LLM в объяснении не используется: шаблон надёжнее и воспроизводим.

### 8.5. Сценарий кандидата

Кандидат видит приглашения с вилкой **до начала общения**. Принял — работодателю открываются контакты, кандидату — контакт рекрутера (до принятия API его не отдаёт: раскрытие симметричное). Отклонил — выбирает причину: зарплата, стек, формат, компания, не ищу.

Правила приглашений в коде (`invitations/service.py`):
- пригласить можно только кандидата, который виден компании в поиске (или уже открыл ей контакты); скрывший профиль или скрывший эту компанию — 404;
- у одной компании не больше одного активного (`sent`/`viewed`) приглашения одному кандидату — иначе 409 `already_invited`; после отказа, отзыва или истечения можно пригласить снова. Гонки закрыты: отправки одной компании сериализуются блокировкой строки работодателя (и частичный уникальный индекс `uq_invitations_active`), принятие и отзыв блокируют строку приглашения, повторное раскрытие контактов пропускается (`ON CONFLICT DO NOTHING`), двойной отклик ждёт первый и получает 409;
- срок истекает лениво: при каждом обращении активные приглашения с прошедшим `expires_at` становятся `expired`;
- снимок «почему вы» считается тем же `scoring.evaluate`: по потребности, а без неё — по категории кандидата;
- в подборке и карточке кандидата работодатель видит `invitation_status` — статус последнего приглашения от своей компании.

**Защита кандидата от мошеннических приглашений.** Заголовок и текст приглашения проверяются правилами `content/invitation_scam_rules.yaml` (без LLM): оплата обучения или оформления, криптовалюта и «пассивный доход», уход в мессенджер до принятия, просьбы о паспорте, данных карты, кодах из СМС. Найденное показывается кандидату предупреждением в карточке приглашения (`warnings` в `InvitationForCandidate`); приглашение не блокируется — формулировки бывают и у честных компаний. Выключатель — `INVITATION_SCAM_CHECK`. Кнопка «Пожаловаться» (`POST /invitations/{id}/report`: причина — мошенничество, дискриминация, компания не та, спам, другое — и комментарий) создаёт одну жалобу на приглашение (повтор — 409 `report_exists`), пишет запись в аудит и не меняет статус приглашения. Жалобы разбирает администратор в кабинете `/admin` (`GET /admin/invitation-reports`, `POST /admin/invitation-reports/{id}/resolve` с описанием принятых мер); работодатель не узнаёт, кто пожаловался.

**«Рынок вашей категории»** (`GET /candidates/me/market`, карточка в кабинете кандидата; `matching/market.py`, без LLM). Считается по действующим последним версиям потребностей всех работодателей:
- счётчики потребностей и опубликованных вакансий в своей категории, на соседнем грейде и в смежных специализациях (`scoring.category_fit`);
- медианная вилка (медианы `salary_from` и `salary_to`) против `salary_min` кандидата: ниже / внутри / выше и доля потребностей, чья верхняя граница покрывает ожидания;
- топ навыков категории: доля потребностей, где навык обязательный и желательный, и статус у кандидата (`scoring.skill_status` — тот же, что в skills-компоненте score);
- «что поможет»: для отсутствующих или только заявленных навыков из топа — контрфактический пересчёт тем же `scoring.skills_component`: на сколько больше потребностей своей и соседних категорий наберёт skills-компонент ≥ `skills_match` (0,75), если навык будет проверен тестом или заданием (навык есть в банке шаблонов специализации) или хотя бы указан в профиле. Показываются до 3 действий с ненулевым эффектом.

Приватность: наружу уходят только агрегаты — ни названий компаний, ни заголовков потребностей. Вилки, навыки и подсказки считаются по своей категории, если в ней не меньше `min_needs` (3) потребностей от не меньше `min_employers` (2) компаний, иначе — вместе с соседними категориями, а если и там меньше — скрываются (`suppressed=true`); счётчики видны всегда. Пороги — `insights` в `content/matching.yaml`.

### 8.6. Чем выделяемся (P1, всё детерминированно и дёшево)

1. **Покрытие вилки.** При вводе вилки работодатель сразу видит распределение ожиданий в категории: «покрывает 64% кандидатов Backend · Middle». В списке кандидатов — пометка «ожидания выше вилки».
2. **Обратная связь по отказам.** Работодатель видит агрегат причин отказов по своим приглашениям: «3 из 5 отказов — зарплата». На существующих площадках этого нет.
3. **Лимит активных приглашений**: `MAX_ACTIVE_INVITES_PER_NEED = 15`, считается по всей цепочке версий потребности (уточнение не обнуляет счётчик). Заставляет приглашать адресно, а не рассылать спам. Ответ кандидата, отзыв или истечение срока освобождает слот; превышение — 409 `invitation_limit`.
4. **Репутация работодателя для кандидата:** доля приглашений с реальной вилкой, средний срок ответа на отклики, доля отозванных приглашений. Это задел для защиты от недобросовестных работодателей.
5. **«Почему вам»** — кандидат видит объяснение совпадения так же, как работодатель. Прозрачность в обе стороны.
6. **Слепой первый просмотр:** без фото, возраста и пола, фамилия скрыта. Снижает предвзятость.
7. **Проверка вилки на адекватность рынку** (§24, реализовано): вилка сравнивается с ожиданиями кандидатов категории в индексе выдачи (`scoring.salary_market`, пороги — `market` в `content/matching.yaml`). Верхняя граница покрывает ожидания меньше 20% кандидатов — «ниже рынка»; нижняя граница вдвое выше медианы ожиданий — «подозрительно высокая» (типичная приманка фиктивной вакансии); меньше 5 ожиданий — вердикт не выносится. Работодатель видит вердикт в блоке «Покрытие вилки» (`GET /needs/{id}/salary-coverage` → `market`), кандидат — пометку «ниже рынка» / «выше рынка — уточните» в приглашении (`salary_market`) относительно своей категории.

### 8.7. Вакансии и отклики (P1)

Вакансия — это потребность с флагом `published=true`. Отдельной сущности не нужно.
- Кандидат видит список вакансий. Сначала подходящие его категории, с тем же объяснением совпадения.
- Отклик с сопроводительным текстом сразу раскрывает контакты работодателю, как требует ТЗ.
- Откликаться можно с действующей категорией (иначе 409 `category_required`): работодатель сравнивает отклики по тому же `match`. Повторный отклик на любую версию той же вакансии — 409 `already_applied`.
- Правка опубликованной потребности создаёт новую версию-вакансию; отклики старых версий видны в новой.
- Статусы отклика: `sent → viewed → accepted | rejected`.
- Работодатель видит отклики по вакансии, отсортированные по тому же `match`. Если категория кандидата вне окрестности категорий вакансии, score не считается (`match_score: null`, строка «вне категорий вакансии»), и отклик идёт в конце списка: score «по своей категории» поставил бы чужую категорию выше подходящих кандидатов. Отклик на вакансию общего демо-работодателя доступен только аккаунтам seed (403 `demo_account`).

### 8.8. Интеграция с ATS: API-ключи и webhook'и

- **API-ключ** выпускает работодатель в профиле компании; ключ `itsk_<prefix>_<secret>` показывается один раз, в БД — только SHA-256. С заголовком `X-API-Key` доступны все методы работодателя, что и из кабинета (потребности, подборка, поиск, приглашения, отклики), с теми же правилами видимости. Управлять ключами и webhook по ключу нельзя — только из кабинета. Не больше `API_KEYS_PER_EMPLOYER` активных ключей (5).
- **Webhook**: один адрес на компанию, только публичный HTTPS (адреса из частных сетей, loopback и редиректы отклоняются — защита от SSRF). События: `invitation.accepted`, `invitation.declined`, `application.created`, тестовое `ping`. Тело — `{id, event, created_at, data}`, где `data` — тот же объект, что работодатель получает в API: контакты кандидата — только после записи в `contact_unlocks`.
- **Подпись**: `X-ITScout-Signature: t=<unix>,v1=<hex>`, где `v1 = HMAC-SHA256(secret, "<t>.<тело>")` — защищает от подмены и повтора; также `X-ITScout-Event`, `X-ITScout-Delivery`.
- **Доставка (outbox)**: событие пишется в `webhook_deliveries` в одной транзакции с действием, отправляется сразу после ответа и повторяется фоновым циклом с задержками `WEBHOOK_RETRY_DELAYS_SECONDS` (30 с, 5 мин, 30 мин); после последней неудачи — `failed`, повтор вручную из журнала. `SELECT … FOR UPDATE SKIP LOCKED` не даёт отправить событие дважды.
- **Надёжность доставки:** пачка арендуется короткой транзакцией (`WEBHOOK_LEASE_SECONDS`), отправка — вне транзакции с общим тайм-аутом `WEBHOOK_TIMEOUT_SECONDS`; ручные проверка и повтор — до `WEBHOOK_MANUAL_PER_HOUR` в час (429); журнал хранится `WEBHOOK_RETENTION_DAYS` дней; при удалении аккаунта кандидата события с его данными удаляются. В общем демо-аккаунте работодателя интеграция недоступна (403 `demo_account`).
- **Экспорт кандидата** — `GET /talent/candidates/{id}/resume.json`: стандартная схема JSON Resume (basics, work, skills, awards — результаты ФСП) и расширение `x-itscout` (категория, перцентиль, темы, разряды ФСП, совпадение с потребностью). Правила видимости — как у карточки: до раскрытия контактов имя сокращено, контактов и названий компаний нет.

### 8.9. Уведомления на почту

| Событие | Кому | Ссылка в письме |
|---|---|---|
| Новое приглашение: компания, должность, вилка | кандидату | `/candidate/invitations` |
| Приглашение отозвано | кандидату | `/candidate/invitations` |
| Приглашение принято: имя как в выдаче | работодателю | карточка `/employer/candidates/{id}` |
| Приглашение отклонено: причина из списка | работодателю | `/employer/invitations` |
| Новый отклик на вакансию | работодателю | карточка `/employer/candidates/{id}?need={id}` |

- **Адрес** — почта аккаунта (`users.email`) и для кандидата, и для работодателя. `employers.contact_email` — публичный контакт рекрутера для кандидатов, он не подтверждён и не связан с настройкой отписки, поэтому для уведомлений не используется.
- **Без контактов кандидата.** В письмах только имя в том виде, в каком его показывает выдача (`display_name`, учитывает настройку фамилии), и ссылка в кабинет. Комментарий кандидата к отказу в письмо не попадает: в нём могут быть контакты. Так инвариант `contact_unlocks` не зависит от писем.
- **Отправка** не влияет на запрос: сервис после коммита складывает письма в список, роутер отдаёт их в `BackgroundTasks` (`send_all` → `send_safely`), и они уходят после ответа. Ошибка почты пишется в лог `itscout.mail`, запрос не падает. При `APP_ENV=test` SMTP не используется никогда.
- **Выключатели:** общий `NOTIFICATIONS_ENABLED` (по умолчанию `true`) и личный `users.email_notifications` — галочка «Уведомления на почту» в настройках кандидата и в профиле компании (`PUT /me/notifications`). В каждом письме есть строка «Отключить уведомления можно в настройках» со ссылкой.
- **Служебные адреса не получают писем:** домены из `NOTIFICATIONS_SKIP_DOMAINS` (зарезервированные `example`, `test`, `invalid`, `localhost`, `example.com/.net/.org` и домен сида `demo.itscout.ru`, включая поддомены), адреса из `NOTIFICATIONS_SKIP_EMAILS` (служебный кандидат e2e) и демо-аккаунты `DEMO_CANDIDATE_EMAIL`, `DEMO_EMPLOYER_EMAIL`, `DEMO_ADMIN_EMAIL`. Поэтому `make reseed`, e2e и показ жюри на демо-аккаунтах почту не рассылают. Письмо подтверждения почты этими правилами не ограничено.
- **Шаблоны** — `backend/app/core/mail_templates.py`: текст и простой HTML из одного описания, ссылки от `PUBLIC_BASE_URL`. Там же письмо подтверждения почты.

## 9. ФСП

### 9.1. Модель данных реестра (наше предложение, в fsp-mock)

```text
Participant(fsp_id, full_name, birth_year, region)
Competition(id, name, discipline, level, format: individual|team, date, participants_count, organizer)
Result(id, fsp_id, competition_id, team_name, team_role, place, score, prize: winner|prize|participant)
Rank(fsp_id, discipline, rank: III|II|I|КМС|МС, awarded_at)
Activity(fsp_id, kind: judge|organizer|mentor, competition_id)
```

Дисциплины (сверить с экспертами ФСП): `algorithmic`, `product`, `infosec`, `drones`, `robotics`.

### 9.2. Сила результата и компетенции (переносим из ранних документов)

```text
percentile = 1 − (place − 1) / max(participants − 1, 1)
strength   = percentile × level_weight × 0.5^(возраст_в_годах / 3)
competency = 1 − Π(1 − strength_i)          # noisy-OR; для связи по роли strength × 0.7
competency = max(competency, rank_floor)     # МС 0.95 … III 0.40
```

**Уровни соревнований** (`level_weight` в `content/rules.yaml`): все 1.0. На встрече с постановщиками (06.10, `docs/qa-summary-fsp-2026.md`) советовали не ранжировать соревнования между собой, а учитывать результативность — она и так входит через перцентиль места. Веса настраиваются: при желании платформа снова различит уровни (раньше было 1.0 / 0.9 / 0.75 / 0.6 / 0.4 от международного до муниципального).

**Компетенции и связь со специализациями** (`competency_relevance.yaml`):
- `algorithms` — 0.8 для всех разработческих специализаций, 0.6 для data;
- `product_team_dev` и компетенции по роли — 1.0 для специализации роли;
- `infosec_ctf` — 1.0 для devops, 0.6 для backend;
- `drones` и `robotics` — 0.3 как общий инженерный сигнал.

**Ограничение:** технологический навык (Python, Docker) из данных ФСП получает не больше статуса «подтверждено ФСП» и только через роль в продуктовой дисциплине. Проверенным навык делает только тест. Это осознанное решение и аргумент на защите.

### 9.3. Привязка ФСП ID

| Способ | Приоритет | Как работает |
|---|---|---|
| Ручной | P0 | Кандидат вводит ФСП ID и даёт согласие на импорт. Backend забирает данные из fsp-mock. Помечается как «не подтверждено владение» |
| OIDC через Keycloak | P1 | Кнопка «Войти через ФСП ID»: authorization code + PKCE к realm `fsp` в Keycloak; из токена берётся claim `fsp_id`. Так подтверждается владение и исключаются чужие достижения. В проде issuer заменяется реальным ФСП ID без изменения кода |

Импорт выполняется при привязке (в MVP; ежедневный повторный импорт или webhook реестра — после MVP). Отзыв согласия удаляет импортированные данные.

**OIDC-флоу (реализован, T17):**
1. Кандидат отмечает согласие на импорт и жмёт «Войти через ФСП ID» (Настройки). `GET /fsp/oidc/start?consent=true` (нужен access JWT кандидата) генерирует `state`, `code_verifier` (PKCE S256) и `nonce`, кладёт их вместе с id кандидата в подписанную (`JWT_SECRET`) httpOnly cookie `itscout_fsp_oidc` на 10 минут (path `/api/v1/fsp/oidc`, SameSite=Lax) и возвращает `authorization_url`. Verifier в URL не попадает, callback привязан к браузеру и кандидату.
2. IdP возвращает браузер на `GET /fsp/oidc/callback?code&state`. Backend сверяет `state` с cookie, обменивает код на токены по внутреннему адресу IdP, проверяет `id_token`: подпись по JWKS (только асимметричные алгоритмы), `iss`, `aud = client_id`, `exp`, `nonce`. Из claim `fsp_id` берётся номер участника.
3. Дальше — общий путь с ручной привязкой: ФСП ID, привязанный к другому кандидату, → `fsp_id_taken`; импорт из реестра (`fetch_from_registry` + `store_evidence`), запись согласия `fsp_import`, аудит, пересчёт индекса выдачи; `fsp_link_method = oidc`, `ownership_verified = true`. Ручная привязка того же ФСП ID повышается до подтверждённой. **Ручная привязка в подбор не идёт:** достижения видны с пометкой «владение не подтверждено, в score не учтено», а `fsp_score` в индексе — 0 и навыки не получают статус «подтверждено ФСП» (`fsp_service.counts_in_score`; `FSP_MANUAL_LINK_COUNTS=true` — учитывать как подтверждённую). Правило одно для индекса, профиля, карточки работодателя, JSON Resume и PDF (`candidates_service.fsp_skills_count`); если кандидат скрыл ФСП, работодатель не видит и статусов «подтверждено ФСП». В демо-данных большинство привязок — через ФСП ID, каждая седьмая и у демо-кандидата Анны — ручная.
4. Callback всегда редиректит в `/candidate/settings?fsp_oidc=linked` или `?fsp_oidc=error&reason=<код>`, cookie флоу удаляется (повтор callback не проходит).

Эндпоинты IdP берутся из discovery (`FSP_OIDC_DISCOVERY_URL`, по умолчанию `http://keycloak:8080/fsp-id/realms/fsp/.well-known/openid-configuration`): у Keycloak с `KC_HOSTNAME` issuer и адрес входа публичные (`https://itscout.ru/fsp-id/realms/fsp`), token и JWKS — внутренние. Для настоящего ФСП ID меняются только настройки `FSP_OIDC_*` (секрет конфиденциального клиента — `FSP_OIDC_CLIENT_SECRET`, только в `.env`).

**Мок IdP:** Keycloak 26 (`infra/keycloak/`: Dockerfile с `kc.sh build` и `fsp-realm.json`), встроенная H2 без volume — realm импортируется заново при каждом пересоздании контейнера. Публикация через Caddy на `https://itscout.ru/fsp-id/`; наружу открыты только `/fsp-id/realms/fsp/*` и `/fsp-id/resources/*`, админка и realm `master` закрыты (404). Пароль админа — `KEYCLOAK_ADMIN_PASSWORD` в `.env`. Клиент `itscout` публичный, authorization code + PKCE S256, без password grant; mapper кладёт атрибут пользователя `fsp_id` в одноимённый claim; изменить `fsp_id` может только админ.

**Демо-участники мок-IdP** (логины и общий тестовый пароль лежат в `infra/keycloak/fsp-realm.json`; это демо-учётки мока, не реальные данные, поэтому они в публичном репозитории):

| Логин | ФСП ID | Кто в сиде |
|---|---|---|
| `fsp-2026-7781` | FSP-2026-7781 | участник реестра без профиля на платформе (`FREE_FSP_ID`) — для живой привязки новым кандидатом |
| `anna.kovaleva` | FSP-2026-1001 | герой Анна (демо-кандидат): ручная привязка повышается до подтверждённой |
| `maria.orlova` | FSP-2026-1002 | героиня Мария: попытка привязать её ФСП ID к другому кандидату → `fsp_id_taken` |

ФСП ID героев детерминированы сидом (`FSP-{год}-{1000+n}`, герои создаются первыми); при смене года в сиде realm нужно обновить.

## 10. Механика тестирования (25%)

### 10.1. Идея

Единый набор заданий утекает. Уникальные задания от нейросети несопоставимы по сложности. Наш подход — третий путь:

> **Калиброванный банк параметризованных шаблонов + адаптивная сборка теста по blueprint + оценка на общей IRT-шкале.**

- **Шаблон** — семейство изоморфных заданий: одна проверяемая идея и одна сложность, но параметры (числа, имена, код, данные, порядок, дистракторы) генерируются на каждую попытку из seed.
- Сложность и дискриминация задаются **на уровне шаблона** (IRT 2PL, для вопросов с выбором — 3PL с c = 1/k) и калибруются по ответам.
- Тест каждого кандидата собирается из банка по **blueprint** «специализация × грейд». Задания разные, но шкала одна, поэтому θ̂ сопоставимы.
- **LLM расширяет банк, а не выдаёт задания напрямую.** Черновые шаблоны от LLM проходят ревью человеком, затем стадию `pilot`: встраиваются в тесты как неоцениваемые, пока не наберут ответов для калибровки. Только после этого становятся `active`.

### 10.2. Формат шаблона

YAML; для вычисляемых заданий — Python-генератор.

```yaml
id: be.db.composite_index_order
specializations: [backend, data]
topic: databases
skills: [sql, postgresql]
kind: single_choice           # single_choice | multi_choice | numeric | ordering | code_output | sql_result | open_approach
irt: { b: 0.35, a: 1.3 }      # стартовая экспертная оценка; c = 1/k для выбора
status: active                 # pilot | active | retired
params:
  table: { choice: [orders, payments, events, shipments] }
  col_a: { choice: [customer_id, account_id, user_id] }
  col_b: { choice: [created_at, updated_at, paid_at] }
stem_variants:
  - "Запрос: SELECT * FROM {table} WHERE {col_a} = $1 ORDER BY {col_b} DESC LIMIT 20. Какой индекс лучше?"
  - "Нужно быстро получать последние 20 записей {table} конкретного {col_a}. Какой индекс создать?"
generator: generators.db.composite_index_order   # строит верный ответ и дистракторы
time_limit_sec: 90
```

```python
# generators/py/code_output.py — пример code_output: значения, имена и порядок операций
# генерируются из seed; верный ответ вычисляется детерминированно в Python (без exec),
# дистракторы строятся из типичных ошибок (off-by-one, мутабельный дефолт, порядок вычисления).
def list_default_arg(rng) -> Instance: ...
```

**Виды заданий:**
- выбор одного или нескольких вариантов с пулами дистракторов;
- числовой ответ (расчёт RPS, пула соединений, сложности);
- упорядочивание (шаги деплоя, этапы запроса);
- «что выведет код» на сгенерированном сниппете;
- «результат SQL-запроса» на сгенерированных данных;
- открытый вопрос о подходе (10.5).

Живой coding с песочницей — после MVP: возможна интеграция с тестирующей системой ФСП.

### 10.3. Blueprint и сборка теста

```yaml
# content/blueprints/backend.yaml
backend:
  topics: { http_api: 3, databases: 3, concurrency: 2, architecture: 2, stack: 4, algorithms: 2, testing: 1, security: 1 }
  open_approach: { from_grade: middle, count: 1 }
  pilot_slots: 2
  max_items: 22
```

**Двухэтапный адаптивный тест (MST).** Он проще и устойчивее полного CAT, а точнее всего работает как раз около порога грейда.
1. **Этап 1:** 9 заданий с b около `cut_G`, пропорционально темам blueprint.
2. **Этап 2:** 9 заданий. Если по этапу 1 θ̂ высокий — блок около `cut_{G+1}`, чтобы распознать уверенный проход. Если низкий — блок около `cut_{G−1}…cut_G`.
3. **Правило остановки:** если после 18 заданий |θ̂ − cut_G| < SE, добавляются до 4 заданий у порога. Кандидат видит диапазон «Вопрос 7 из 20–24» (`total_estimate` — без уточняющих, `total_max` — с ними), прогресс считается от верхней границы, а на уточняющих заданиях объясняется, почему тест продолжается.
4. Плюс 2 пилотных неоцениваемых слота (кандидат их не отличает) и открытый вопрос для Middle и выше.

**Последовательность выдачи.** Запросы текущего задания и ответа на одну попытку выполняются по очереди (блокировка строки попытки `SELECT … FOR UPDATE`), старт попытки — под блокировкой кандидата; в БД — уникальность `(attempt_id, position)`. Две вкладки или двойной клик не дают двух «текущих» заданий.

**Отбор шаблонов:** случайный внутри темы и окна сложности с **контролем экспозиции** — вес шаблона exp(−((b − цель)/окно)²) / (1 + 10 · доля показов): ближе к цели и реже показанные вероятнее; шаблоны с долей показов выше 25% временно исключаются. Коэффициенты — `selection` в `content/blueprints.yaml`. Внутри попытки темы не повторяются подряд. Варианты ответов перемешиваются.

### 10.3.1. Экспресс-тест

Постановщики просили, чтобы жюри могло само пройти тест, и назвали допустимым экспресс-тест на 3–5 минут (`docs/qa-summary-fsp-2026.md`). Кнопка «Пройти экспресс-тест» на экране «Категория и грейд» (`purpose: "express"` в `POST /tests/attempts`):
- режим `express` в `content/blueprints.yaml`: 4 + 4 задания, без уточняющих, пилотных и открытого вопроса; тот же движок — MST, свои экземпляры, контроль экспозиции, время считает сервер;
- **категорию не присваивает**: навыки, индекс выдачи и перцентили не меняются, в правилах грейда (§6.3) попытка не считается — кроме незавершённой, которая, как любая, блокирует новый тест; θ̂ экспресс-попыток не идёт в данные Angoff;
- результат — «порог пройден / ниже порога» выбранного грейда с той же уверенностью (§10.4.1) и кнопкой «Полный тест»;
- выключатель `EXPRESS_TEST_ENABLED` (по умолчанию включён) и лимит `EXPRESS_TESTS_PER_DAY` (5) на кандидата в сутки: каждая попытка показывает шаблоны банка, поэтому без лимита экспресс-тест стал бы способом его выгрузить.

### 10.4. Оценка и грейд

- θ̂ — **EAP** с априорным N(0, 1), квадратура на 81 точке от −4 до 4 (numpy, `engine/irt.py`). SE — апостериорное стандартное отклонение.
- **Пороги** на шкале специализации (стартовые, `content/blueprints.yaml`): `cut_intern = −1.8`, `cut_junior = −0.8`, `cut_middle = 0.2`, `cut_senior = 1.2`. Ниже порога стажёра категория не присваивается. Окончательные пороги — экспертная процедура *modified Angoff* (реализована, §12.4): эксперт оценивает p_i — вероятность, что «минимально компетентный» кандидат грейда решит шаблон i, и порог эксперта — θ, при котором тестовая характеристическая кривая Σ P_i(θ) (та же 3PL, что в EAP) равна Σ p_i (`engine/angoff.py`, бисекция на [−4, 4]; Σ p_i вне TCC на этом отрезке — порог у края шкалы). Два раунда: после первого эксперт видит данные о последствиях и пороги группы и может пересмотреть оценки; рекомендуемый порог — среднее по экспертам последнего раунда ± SE, рядом — проверка Hofstee. В `blueprints.yaml` его переносит команда вручную.
- **Решение** по тесту на грейд G:
  - не пройден — θ̂ < cut_G;
  - пройден — θ̂ ≥ cut_G;
  - **пройден уверенно** — θ̂ − SE ≥ cut_G и θ̂ ≥ cut_{G+1} − SE. В этом случае предлагается тест на G+1.
- **Подсчёты по темам** — доля верных по теме (описательно, для объяснений). **Навык проверен**, если по нему ≥2 оценённых задания и ≥70% верно.
- **Перцентиль в категории** пересчитывается при появлении новых результатов.

### 10.4.1. Уверенность в грейде и блок «Почему этому грейду можно верить»

- **Только объяснение.** Грейд выставляет правило §10.4; уверенность считается после него теми же порогами (`blueprints.yaml`) и ничего не меняет — ни результат попытки, ни категорию, ни score подбора.
- **Формула (Rudner 2001, 2005).** По θ̂ и SE попытки считаем, что θ ~ N(θ̂, SE²). Вероятность полосы грейда k: P_k = Φ((cut_{k+1} − θ̂)/SE) − Φ((cut_k − θ̂)/SE); у полосы «ниже стажёра» нижней границы нет, у Senior нет верхней. Главная цифра — P(θ ≥ cut_G) для присвоенного (в результате попытки — проверяемого) грейда G: «88% — вероятность, что уровень не ниже Middle». Код — `engine/confidence.py` (чистые функции, golden-кейсы в `tests/test_confidence.py`).
- **Слова и границы — в `content/confidence.yaml`:** уровни «высокая» (P ≥ 0,90), «средняя» (≥ 0,70), «низкая»; процент в тексте ограничен 1–99%; тексты для кандидата и работодателя; ссылки на `/how-it-works` и на отчёт валидации.
- **Где видно.** Кандидату — в результате попытки (`AttemptResultOut.confidence`) и на экране «Категория и грейд» (`GradeStatus.current.evidence`, короткая версия без сигналов честности). Работодателю — в карточке кандидата (`CandidateCard.grade_evidence`): блок «Почему этому грейду можно верить» с датой теста и сроком результата, адаптивностью и числом оценённых заданий, θ̂ ± SE, уверенностью и полосой вероятностей грейдов, сводкой сигналов честности §10.9 (если `INTEGRITY_SIGNALS_ENABLED`) и ссылками на «Как работает тест» и отчёт валидации. В обезличенной карточке эксперта (§12.4) блока нет.
- **Валидация.** Средние по популяции P полосы θ̂ и Σ P_k² — индексы точности и согласованности классификации по Руднеру (Lee 2010). Отчёт валидации (§12.2, раздел 3.1) ставит их рядом с фактическими значениями симуляции (против θ_true и повторной попытки): так видно, насколько «уверенности» можно верить на реальных данных, где θ_true нет.

### 10.5. Открытый вопрос о подходе (P1)

Для Middle и выше: «Как бы вы спроектировали X / нашли причину Y?», ответ до 1500 символов.
- LLM оценивает по **чек-листу из 4–6 бинарных критериев** из шаблона, температура 0, ответ в JSON со ссылками на фрагменты ответа.
- Итог хранится отдельно как `approach` (0..1) и **не входит в θ̂**, чтобы не смешивать шумную оценку с калиброванной шкалой.
- Работодатель видит сам ответ и отметки по критериям.

**Как реализовано:** при ответе на открытый вопрос (`testing/service.py`, `_grade_open_answer`) `llm.rubric_hits` — тот же вызов, что в регулярных заданиях (§11), — отмечает критерии из `answer_key.rubric`; `approach_score` = доля отмеченных, его считает код (оценку модели, если она её вернёт, игнорируем). Без LLM или при ошибке ответ сохраняется без оценки. Карточка кандидата (`approach_answers`) отдаёт вопрос, ответ, критерии с отметками и долю по попытке текущей категории; до раскрытия контактов из ответа, «О себе» и описаний опыта вычищаются email, телефоны, Telegram и ссылки.

4. **Черновики LLM** для навыков вакансии, которых нет в банке, со статусом `pilot` и пометкой «не влияют на оценку до калибровки».

**Как реализовано** (`testing/engine/vacancy.py`, `testing/preview_service.py`, `POST /vacancy-tests/preview`):
- источник — текст (словарный разбор §8.1, LLM только дополняет) или своя потребность `need_id` (чужая → 404); без специализации или без теста по ней → 422;
- навык вакансии привязывается к теме, где банк проверяет его чаще всего; обязательный навык добавляет `vacancy.boost_required`, желательный — `boost_optional` к весу темы (`content/blueprints.yaml`), затем веса снова делятся на прежнее число заданий методом наибольшего остатка. Стек-модули — по навыкам вакансии через `content/survey.yaml`; тема без шаблонов под стек вакансии уходит, её квота — другим темам (как в MST);

### 10.9. Сигналы честности попытки

Статистическая пометка нетипичного рисунка ответов для работодателя: «нетипичный рисунок ответов — стоит перепроверить на собеседовании; на грейд не влияет». Обзор методов — `docs/research/psychometrics.md` §3 и `docs/research/integrity.md` §2.1.

**Инвариант.** Сигналы **не входят** в θ̂, решение по тесту, категорию, перцентиль, score подбора и объяснение выдачи и не меняют порядок выдачи. Кандидату они не показываются: в его результате нет ни сигналов, ни намёков на них. Это следует из инварианта «грейд определяет только тест» и из ст. 16 152-ФЗ (решения с юридическими последствиями не принимаются только на основе автоматизированной обработки): решение о том, что делать с пометкой, принимает человек на собеседовании.

**Выключатель** — `INTEGRITY_SIGNALS_ENABLED` (`core/config.py`, по умолчанию `true`). При `false` сигналы не считаются и не сохраняются при завершении попытки, а API отдаёт `integrity: null` даже для попыток, где они были сохранены раньше.

**Что считается** (чистые функции `testing/engine/integrity.py`, пороги и тексты — `content/integrity.yaml`). Берутся только оценённые ответы (без пилотных слотов и открытого вопроса) и итоговая θ̂ попытки.
- **Person-fit lz\*** (Snijders, 2001) для 3PL: W = Σ(uᵢ − Pᵢ)·wᵢ, wᵢ = ln(Pᵢ/Qᵢ); поправка на оценённую θ̂: c_n = ΣPᵢ′wᵢ / ΣPᵢ′rᵢ, rᵢ = Pᵢ′/(PᵢQᵢ), r₀(θ̂) = −θ̂ (априорное N(0, 1) EAP-оценки, приближение байесовской модой); lz\* = (W + c_n·r₀) / √Σ(wᵢ − c_n·rᵢ)²PᵢQᵢ. При честных ответах ≈ N(0, 1); сигнал — lz\* < −1,645.
- **Быстрое угадывание** (Wise & DeMars, 2006): ответ быстрее порога NT10 = min(10% лимита задания, 10 с). Норм времени пока нет, поэтому порог считается от `time_limit_sec` шаблона. Сигнал — доля таких ответов больше 10% (RTE < 0,9).
- **«Быстро и верно на трудном»** (упрощённая идея Sinharay, 2020): верный ответ быстрее min(20% лимита, 30 с) на задании с b − θ̂ ≥ 1. Сигнал — 2 и больше таких ответов.
- Меньше 12 оценённых заданий — «недостаточно данных», сигналы не считаются.

**Хранение и показ.** При завершении попытки (`testing/service.py`, `_finalize`) результат пишется в `test_attempts.flags.integrity`: `{items, enough_data, lz_star, rapid_share, fast_correct_hard, flagged, reasons}`; новых таблиц и миграций нет. Карточка кандидата у работодателя (`GET /talent/candidates/{id}`) отдаёт `integrity` по попытке текущей категории: `flagged`, причины по-русски и пояснение; в обезличенной карточке эксперта (§12.2) поля нет. Фронт показывает нейтральную карточку только при `flagged`.

**Проверка на симуляции:** `make integrity-check` → `docs/validation/integrity.md` — ложные срабатывания на честных кандидатах и доля помеченных среди кандидатов с предзнанием утёкших шаблонов и с быстрым угадыванием. Модель времени в симуляции условная, пороги нужно пересчитать по реальным временам ответов.

## 11. Регулярные задания (P2)

- Работодатель создаёт короткое задание: выбирает тему и уровень из банка (автопроверка; конкретный шаблон выбирается при выдаче кандидату — тексты, id и сложность шаблонов работодателю не показываются, иначе любой зарегистрированный работодатель выгрузит банк) или пишет текст «предложите подход» (оценка по чек-листу LLM и, по желанию, оценка работодателя 1–5). Задание привязывается к специализации и грейду или к потребности.
- Раз в неделю (лениво при открытии раздела, см. ниже) кандидату категории предлагается одно задание; не больше одного активного одновременно.
- Результат обновляет `fresh` и `approach`, а также статус навыка «подтверждено заданием».
- Работодатель видит обезличенные ответы на свои задания: email, телефоны, Telegram и ссылки в тексте решения скрыты, пока нет записи в `contact_unlocks` (как в карточке кандидата). Из ответа можно сразу отправить приглашение — естественный повод для первого контакта.

**Как реализовано** (`tasks/service.py`, числа — `content/tasks.yaml`):
- «Раз в неделю» сделано лениво, без планировщика: при открытии `GET /candidates/me/tasks` просроченные задания становятся `expired`, и если активного нет и с прошлого предложения прошло `offer_interval_days`, кандидату предлагается самое новое ещё не выданное задание его специализации и грейда (или без грейда); работодатели из `hidden_employer_ids` пропускаются. Кандидат может пропустить задание (`POST /tasks/assignments/{id}/skip`).
- `auto`: задание хранит группу `template_pool` = «тема:стек:уровень» (уровень — самый высокий грейд, порог которого не выше b шаблона). При предложении из активных шаблонов группы случайно выбирается один, он записывается в `task_assignments.template_id`, экземпляр рендерится с новым seed, ключ остаётся в БД; старые задания с `template_id` работают как раньше. Группы для формы — `GET /employer-tasks/templates` (только название, уровень и навыки); проверка — тем же `scoring.score`, что и в тесте. Score ≥ `confirm_min_score` добавляет навыкам шаблона источник `task` → статус `task_confirmed` в профиле и индексе. Группы для формы — `GET /employer-tasks/templates?need_id=`: сначала с навыками потребности, стек — по ней же (тот же подход, что в §10.7).
- `approach`: при включённом LLM он только отмечает критерии чек-листа (`rubric_hits`), score = доля отмеченных, считает код; без LLM решение ждёт оценки работодателя 1–5, score = (оценка − 1) / 4. Оценка работодателя не перетирает автопроверку и чек-лист.
- Индекс выдачи: проверенное решение (есть score) обновляет `last_activity_at` → `fresh`; `approach` — среднее из оценки открытого вопроса теста и оценок заданий на подход. Грейд и категорию задания не меняют.
- Чужое задание или решение → 404 (и для кандидата, и для работодателя).

### 11.1. Челленджи компании (P2)

Работодатель сам пишет вопросы для кандидатов нужной категории, кандидат проходит челлендж по желанию, работодатель видит решивших по результату и приглашает первым. Отличие от регулярных заданий (§11): вопросы свои, а не из банка (банк работодателю не показывается, §10.6), и кандидат выбирает челлендж сам.

- **Конструктор** (`challenges/service.py`, лимиты — `content/challenges.yaml`): 3–20 вопросов — `single_choice`, `multi_choice`, `numeric` (ответ и допуск), `open_approach` (необязательный чек-лист); специализация, грейд или «любой», навыки из справочника, время на вопрос 20–600 с, «показывать N вопросов из написанных». Черновик можно править; опубликованный — нет (иначе решившие сравнивались бы по разным вопросам), его закрывают и создают новый.
- **Публикация** проверяет все тексты теми же правилами, что и потребность (`content/need_text_rules.yaml`, §8.1): запрещённые требования → 409 `challenge_text_discriminatory` с найденными фрагментами.
- **Кому видно:** опубликованные челленджи специализации и грейда (если задан) текущей категории кандидата. Без категории челленджей нет: такого кандидата нет в выдаче, и компания не увидела бы его результат. Компании из `hidden_employer_ids` не показываются, а кандидат, скрывший компанию, пропадает из её списка решивших (и из решений регулярных заданий). Начатые и пройденные остаются в списке.
- **Прохождение:** одна попытка на кандидата (уникальность `(challenge_id, candidate_id)` и блокировка строки кандидата при старте; повторный старт возвращает её же). У каждой попытки свой набор и порядок вопросов и свои метки вариантов «1, 2, 3…» вместо исходных — подсказка «правильный ответ b» из чата не подходит. Вопросы по одному, время считает сервер (`shown_at` + лимит + `ANSWER_GRACE_SECONDS`), опоздание засчитывается как неверный ответ, а текст опоздавшего открытого ответа не сохраняется; вопрос, время которого вышло без ответа, закрывают и `/current`, и запрос результата попытки; запросы по одной попытке сериализованы блокировкой строки, как в тесте. Экран вопроса — тот же, что в тесте (`CurrentItem`). Ключи ответов наружу не уходят.
- **Результат:** доля верных автопроверяемых ответов; открытые ответы не оцениваются баллом, их читает работодатель. **На грейд, категорию, score подбора и статусы навыков челлендж не влияет** — вопросы не откалиброваны и их может написать кто угодно; иначе навыки можно было бы «подтвердить» лёгкими вопросами.
- **Решившие** (`GET /employer-challenges/{id}/solvers`): по убыванию результата, обезличенные карточки, текст открытых ответов без контактов до записи в `contact_unlocks`; из списка — приглашение с вилкой (§8.5).
- **Удаление аккаунта** кандидата стирает текст его открытых ответов, баллы остаются (§13).
- **Демо:** у «Демо Банка» опубликован челлендж по Backend с тремя решившими; демо-кандидат проходит его на показе.

## 12. Процедура валидации (P0, оценивается отдельно)

Папка `validation/`, запуск `make validate` (без make: `cd backend && uv run python ../validation/run.py`, параметры `--size`, `--seed`, `--out`). Результат детерминирован по seed; все параметры симуляции — в `validation/config.yaml`. На выходе `docs/validation/report.md` (текст и числа генерирует код, руками не правится), `docs/validation/metrics.json` и PNG-графики для документации и презентации. Прогон на 2 000 кандидатов — 7–8 минут. Smoke-тест на маленькой популяции (`backend/tests/test_validation.py`) проверяет в CI, что метрики считаются и детерминированы. Сигналы честности (§10.9) проверяются отдельным прогоном `make integrity-check` (`validation/integrity_check.py`, ~30 с) → `docs/validation/integrity.md`: ложные срабатывания на честных кандидатах и доля помеченных при предзнании утёкших шаблонов и быстром угадывании. Аудит предвзятости входит в отчёт разделом «Справедливость» и запускается отдельно `make fairness-check` (`validation/fairness.py`, ~1 мин) → `docs/validation/fairness.md`.

Используется только чистый код продукта, без БД и HTTP: движок `backend/app/modules/testing/engine` (банк, blueprint'ы, `Planner`, рендер, EAP, решение о грейде), `matching/scoring.py` (score подбора), `survey.service.score_specializations` (специализация по опросу). Прохождение теста повторяет подход `seed/generate.py`.

### 12.1. Симулированная популяция

- 2 000 синтетических кандидатов. У каждого: истинная специализация, истинная способность θ_true на шкале специализации (смесь распределений по грейдам), истинный грейд — старший грейд, чей порог не выше θ_true, истинный стек и резюме с шумом (лишние и пропущенные навыки), профили по темам (отклонения от θ, σ = 0,3), заявленный грейд с шумом (20% завышают на 1, 10% занижают), история ФСП, коррелирующая с θ (у 35% она есть), ожидания, формат, город.
- Модель ответа: 3PL с параметрами шаблона от способности по теме задания **плюс отклонение сложности экземпляра** (σ_b = 0.15; отклонение — свойство содержимого экземпляра). Это проверяет, что параметризация не ломает сопоставимость.
- Тест проходит через **тот же движок**, что и в продукте. Путь кандидата — калибровка по §6.3: тест на заявленный грейд, вниз при провале, один раз вверх при «пройден уверенно»; итоговая категория сравнивается с истинным грейдом. Для согласованности путь проходится дважды с разными seed.

### 12.2. Метрики

| Свойство (из критериев ТЗ) | Метрика |
|---|---|
| Согласованность (повторное прохождение) | Каждый кандидат дважды проходит калибровку на независимых вариантах → совпадение категории в %, взвешенная κ Коэна, корреляция θ̂₁ и θ̂₂; повтор решения «пройден / не пройден» и трёхуровневого решения — в целом, вдали от порога и у порога; ожидаемые точность и согласованность классификации по Руднеру (из θ̂ и SE, §10.4.1) рядом с фактическими — для решения «пройден / не пройден» и для полосы грейда по всем порогам |
| Соответствие эталону | Точность категории относительно истинного грейда, матрица ошибок, доля ошибок больше чем на один грейд; точность решения по одному тесту (ложный проход и ложный провал) |
| Точность оценки и длина теста | RMSE, смещение и средняя SE θ̂ по уровням θ_true; число оценённых заданий, доля попыток с доп. заданиями, тестов на кандидата |
| Дискриминативность | Точечно-бисериальная корреляция по шаблонам, информационная функция теста у порогов; распределения θ̂ сильных и слабых кандидатов; покрытие шкалы банком |
| Устойчивость к утечке | (а) средняя доля общих шаблонов и общих экземпляров у двух попыток; (б) сценарий «слили 30% ключей»: доля прошедших среди кандидатов ниже грейда у фиксированного теста (базовая линия), у адаптивного теста без параметризации и у нашего; (в) разнообразие экземпляров каждого шаблона; (г) экспозиция шаблонов против порога 25% |
| Сопоставимость форм | Для одинакового θ_true формы на разных стек-модулях дают одинаковое среднее θ̂ (критерий χ²); устойчивость решения о грейде при σ_b от 0 до 0,5 и при ошибке экспертных b |
| Калибровка | Восстановление b и a шаблонов из симулированных ответов — fixed-parameter MML, как калибруются пилотные слоты (numpy/scipy вместо `girth`); RMSE относительно истинных значений по числу ответов |
| Категоризация | Точность определения специализации по опросу (синтетические ответы) относительно истины. Поля резюме — precision и recall на 30 синтетических и 5–10 реальных резюме — после готовности разбора резюме (T15), в автоматический прогон пока не входят |
| Подбор | 60 потребностей; истинная релевантность 0–3 из истинных специализации, грейда и стека → **precision@5/10 (релевантны точные совпадения) и nDCG@10**. Сравнение: выдача ITScout по категориям (режим по умолчанию), «общий топ» по `match`, категория по тесту + ключевые слова, заявленный грейд + ключевые слова, ключевые слова по резюме. 95% bootstrap-интервалы по потребностям и парное сравнение с базовыми линиями (парный bootstrap, знаковый тест, число потребностей для мощности 0,8); **accept@5** — ожидаемая доля принявших приглашение в топ-5 на синтетической модели ответа кандидата (§8.3.1) для показа и множителей разной силы; P@5 и nDCG@10 с зачётом близких навыков и без него; ожидаемые интервалы и κ на цели экспертной разметки (20 потребностей, шумные эксперты) |
| Справедливость | Аудит предвзятости по прокси-признакам, которые есть в данных: город (Москва и Санкт-Петербург против регионов), история ФСП, формат работы; пол, возраст и национальность не собираются и не выдумываются. **Отбор** — тест на заявленный грейд пройден и попадание в топ-k (`fairness.top_k`) выдачи по умолчанию по 60 синтетическим потребностям (город потребности — из распределения городов). **Impact ratio** — доля отбора группы к доле самой успешной, флаг ниже 0,8 (правило 4/5, EEOC 29 CFR 1607.4(D), NYC LL 144); 95% ДИ — Каца для теста, bootstrap по потребностям для выдачи. **При равной способности** — отношение Мантеля–Хензеля (дисперсия Greenland–Robins) в слоях «грейд теста или потребности × бин θ_true − порог»: отделяет различия, объяснимые способностью. Флаги: `below` — ниже 4/5 только в целом, `below_conditional` — и при равной способности, `conditional_only` — только при равной. Отдельно **инвариант «ФСП не штрафует»**: для каждой пары «потребность — кандидат» score сравнивается с нейтральной базой (тот же кандидат с обнулённым ФСП) — без ФСП разница ровно 0, с ФСП — от 0 до 100·`weights.fsp`; сила профиля (VPS) — то же; плюс доля мест в топ-k, которые кандидаты без ФСП теряют из-за бонуса. Код — `validation/fairness.py`, golden-кейсы — `tests/test_fairness.py`, параметры — `validation/config.yaml`, раздел `fairness` |
| «Что если» | Альтернативные правила «пройден уверенно» и длина теста (без изменения движка): точность и повтор категории, занижение, тестов на кандидата |
| Экспертная оценка | Участник команды и 2–3 приглашённых ИТ-специалиста размечают пары «потребность — карточка кандидата» по шкале 0–3 на экране `/expert` → P@5 и nDCG@5 выдачи ITScout и базовой линии по ключевым словам с 95% bootstrap-интервалами, парное сравнение (парный bootstrap, знаковый тест), корреляция Спирмена score со средней оценкой, согласие экспертов (точное совпадение, квадратично взвешенная κ с интервалом и уровнем по Landis & Koch, α Криппендорфа), прогресс к цели «20 потребностей / 200 меток». Требует людей, в автоматический прогон не входит; порядок — §12.4 |

### 12.3. Честные ограничения (пишем в отчёте)

Симуляция проверяет механику при заданной модели ответов. Реальную калибровку параметров дают только пилотные данные. Мы описываем, как она устроена: пилотные слоты и периодическая перекалибровка. Отчёт также перечисляет, что не измерено (разбор резюме, экспертная разметка, открытые вопросы) и какие изменения рекомендуются по результатам — сами пороги и движок по итогам валидации автоматически не меняются.

### 12.4. Экспертная разметка

- **Доступ.** Роль `expert`; регистрация на `/expert/join` по коду-приглашению `EXPERT_INVITE_CODE` (пусто — регистрация закрыта, 404). Код раздаёт команда.
- **Набор пар** собирается при первом обращении эксперта: до `expert.needs` (20) активных потребностей поровну по специализациям; по каждой — объединение топ-`expert.top_k` выдачи ITScout и топ-`expert.top_k` поиска по ключевым словам (обязательные навыки — 1, желательные — 0,3). Обе выдачи и score сохраняются в паре, карточка потребности и кандидата — снимком, поэтому `make reseed` набор не ломает (`expert_pairs` и `expert_labels` при пересидировании не очищаются). Собранные пары не меняются; если в наборе меньше `expert.needs` потребностей (цель подняли после начала разметки), он дополняется новыми потребностями по тем же правилам. Числа — `content/matching.yaml`, раздел `expert`.
- **Вслепую.** Эксперт видит потребность и обезличенную карточку без score, объяснения, места в выдаче и контактов. Пары одной потребности идут подряд, внутри — в своём псевдослучайном порядке для каждого эксперта. Шкала: 0 — не подходит, 1 — слабо, 2 — с оговорками, 3 — подходит. Повторная оценка заменяет прежнюю.
- **Метрики** (`GET /expert/summary`, вкладка «Итоги»): пара релевантна, если средняя оценка ≥ `expert.relevant_from`; P@5 и nDCG@5 (выигрыш 2^оценка − 1, идеал — лучшие размеченные пары потребности) для каждой выдачи считаются по потребностям, где размечены все пять первых; 95% интервал — перцентильный bootstrap по потребностям (`expert.bootstrap_resamples`, seed `expert.bootstrap_seed`); сравнение ITScout с ключевыми словами — парное, на потребностях, где размечены обе пятёрки: разница с интервалом и p парного bootstrap, знаковый тест (точный биномиальный). Спирмен — между score ITScout и средней оценкой; согласие — по парам с двумя и более оценками: точное совпадение, квадратично взвешенная κ с bootstrap-интервалом и уровнем по Landis & Koch, α Криппендорфа (интервальная, любое число экспертов на пару), доля двойной разметки (ориентир — не меньше 20%). Цель — `expert.target_needs` потребностей с полностью размеченными пятёрками и `expert.target_labels` оценок (20 и 200): при σ разницы nDCG ≈ 0,15 парный тест заметит разницу 0,1 с мощностью 0,8 (Sakai, topic set size design); прогресс — на вкладке «Итоги». Функции — `backend/app/modules/expert/stats.py`, их же вызывает отчёт валидации.
- Результаты разметки идут в отчёт валидации (`docs/validation.md`, раздел 8) и до них веса подбора дальше не меняются.
- **Пороги грейдов (modified Angoff, §10.4)** — вкладка «Пороги (Angoff)». Эксперт выбирает специализацию и границу грейда и оценивает каждое задание набора по шкале 0–100% с шагом 5 («с какой вероятностью его решит минимально компетентный Middle?»); оценка сохраняется сразу, повторная заменяет прежнюю. Набор на пару «специализация × грейд» детерминирован: `items` активных автопроверяемых шаблонов с |b − cut_G| ≤ `window` (окно расширяется на `window_step`), равномерно по сложности, в порядке, не связанном с b (`content/angoff.yaml`). Эксперт видит пример экземпляра (seed `instance_seed`) без ключа ответа и без параметров IRT. Оценки — в `angoff_ratings` по email эксперта, при reseed не очищаются. Сводка (`GET /expert/angoff/summary`) по каждому грейду, где хотя бы один эксперт оценил весь набор: по каждому раунду — порог каждого эксперта, среднее, медиана, SD, SE = SD/√k; рекомендуемый порог — среднее последнего раунда, который прошёл хотя бы один эксперт; действующий порог и разница; предупреждение, если экспертов меньше `recommended_raters`. Пороги автоматически не меняются.
  - **Два раунда** (Cizek & Bunch, 2007). Оценки раундов хранятся раздельно (`angoff_ratings.round`). Когда эксперт оценил весь набор в раунде 1, ему открываются **данные о последствиях** (`GET /expert/angoff/impact`): его порог, медиана, минимум, максимум и SD порогов группы в раунде 1 (если раунд прошли не меньше `feedback_min_raters` экспертов), доля кандидатов ниже действующего, его и предложенного порога (медиана группы, иначе его порог) и распределение по полосам грейдов при действующих порогах против действующих с заменой этого порога. Кандидаты — θ̂ последней завершённой попытки каждого кандидата специализации (`testing.service.latest_thetas`); если их меньше `impact.min_candidates`, — синтетическая популяция из `content/angoff.yaml` (та же смесь по грейдам, что в `validation/config.yaml`), источник подписан. До полного раунда 1 эти данные не отдаются (409 `round1_incomplete`), чтобы не влиять на первичную оценку. Раунд 2 начинается копией оценок раунда 1 (`POST /expert/angoff/round2`); на карточке задания — своя оценка раунда 1 и медиана, минимум и максимум оценок группы.
  - **Проверка Hofstee** (Hofstee, 1983). Каждый эксперт задаёт окно: минимальный и максимальный приемлемый порог — долю верных по набору у минимально компетентного кандидата — и минимальную и максимальную долю кандидатов специализации, не дотягивающих до грейда (`PUT /expert/angoff/hofstee`, значения по умолчанию — `hofstee_defaults`). В сводке окно — средние границы экспертов; кривая F(k) — доля кандидатов с θ̂ ниже θ_k, где θ_k — решение TCC(θ)/n = k на наборе Angoff; порог Hofstee — пересечение F с диагональю окна из (min_cut, max_fail) в (max_cut, min_fail), бисекцией (`engine/angoff.py`, `hofstee`; без пересечения — ближний край окна и пометка). Рекомендуемый порог Angoff переводится в долю верных TCC(θ)/n и долю не дотягивающих; `in_box` — обе величины внутри окна. Golden-кейсы — `tests/test_angoff.py`.

## 13. Безопасность и 152-ФЗ (P0)

- **Пароли и сессия.** Пароли хранятся как argon2id. Access JWT живёт 15 минут. Refresh-токен лежит в httpOnly Secure cookie и меняется при каждом обновлении; в БД — только хэши.
- **Защита от подбора.** Ограничение частоты запросов на `/auth/*` по IP и пути (`AUTH_RATE_LIMIT` в окне `AUTH_RATE_WINDOW_SECONDS`), вход дополнительно ограничен на один email со всех адресов (`LOGIN_EMAIL_RATE_LIMIT`). У демо-входа свой, больший лимит (`DEMO_LOGIN_RATE_LIMIT`): пароля нет, а жюри в одном зале выходит в сеть с одного IP.
- **Разграничение доступа.** Роли проверяются dependency-функциями FastAPI. Проверки на уровне объектов вынесены в сервисы и покрыты тестами:
  - кандидат видит только свои приглашения и отклики;
  - работодатель видит контакты, только если есть запись в `contact_unlocks`;
  - работодатель видит только свои потребности и приглашения.
- **Ответы на тест.** Ключи ответов не уходят на фронт; ответ принимается только для текущего задания и в пределах времени (время считается на сервере).
- **Согласия.** Хранятся с версией текста политики и датой; отзыв согласия работает: отзыв публикации убирает профиль из выдачи, отзыв импорта ФСП удаляет импортированные данные; согласие на обработку ПДн отзывается только удалением аккаунта (409 `consent_required`).
- **Удаление аккаунта.** Выданный ранее access JWT удалённого пользователя отклоняется общей зависимостью авторизации (401) ещё до бизнес-логики. Мягкое удаление с обезличиванием ПДн: ФИО и контакты стираются, опыт работы, резюме и данные ФСП удаляются, свободный текст кандидата (ответы на задания, открытые ответы теста, сопроводительные письма, комментарии к отказам и жалобам) стирается — оценки и θ̂ остаются для статистики, профиль убирается из выдачи, активные приглашения истекают, сессии и согласия отзываются, email заменяется на `deleted-<id>@deleted.invalid`.
- **Аудит.** Журнал раскрытия контактов и изменения согласий.
- **Персональные данные.** Резюме обрабатываются через Yandex AI Studio, данные не уходят за рубеж. В БД хранятся только подтверждённые пользователем данные.
- **Секреты.** В `.env` на сервере, в репозитории только `.env.example`. CORS — только свой домен.

### 13.1. Правовые документы и возражение против грейда

Обзор требований — `docs/research/legal.md` (блок A в `docs/research/README.md`).

- **Документы** (`backend/content/legal/*.yaml`, отдаёт `GET /legal/documents/{slug}`, страница `/legal/:slug` без входа):
  - `recommendations` — правила применения рекомендательных технологий (149-ФЗ ст. 10.2-2): где применяются, какие данные используются и какие нет, компоненты и веса score, порядок без потребности, пороги грейдов, роль LLM, как отказаться, контакт;
  - `privacy` — политика обработки ПДн (152-ФЗ ст. 18.1): оператор, цели, состав данных, основания, обработчик Yandex Cloud (AI Studio), реестр ФСП как источник, хранение в РФ без трансграничной передачи, сроки, права субъекта, меры защиты;
  - `consent-pd` — согласие на обработку ПДн отдельным документом (ст. 9, с 01.09.2025): цели, перечень данных, действия, автоматизированное тестирование и ранжирование, обработчик LLM, источник ФСП, срок и отзыв;
  - `consent-publication` — согласие на распространение (ст. 10.1): кому и что видно, запреты (контакты до раскрытия не распространяются, скрытие от компаний), отзыв.
- **Числа не дублируются:** в YAML стоят плейсхолдеры (`{w_skills}`, `{cut_middle}` …), backend подставляет их из `content/matching.yaml` и `content/blueprints.yaml` (`legal/service.py`). Тест `test_legal.py` проверяет, что веса в правилах совпадают с весами подбора и описан каждый компонент score.
- **Версия текстов** — `POLICY_VERSION`; та же строка пишется в `consents.policy_version` при регистрации и в настройках, на странице документа — «Редакция от …». Оператор и контакт — `LEGAL_OPERATOR`, `LEGAL_CONTACT_EMAIL` (до запуска — заглушка «оператор будет указан при запуске»).
- **Ссылки:** футер публичных страниц и кабинетов (правила рекомендаций и политика), галочки регистрации (кандидат, работодатель, эксперт), «текст» у согласий в настройках кандидата.
- **LLM:** в запросы к Yandex AI Studio добавлен заголовок `x-data-logging-enabled: false` — запросы не сохраняются на стороне Yandex.
- **«Как определён грейд»** (152-ФЗ ст. 16): `GET /candidates/me/grade-explanation` — категория, θ̂, SE, порог грейда и следующего грейда, итог попытки, дата теста, срок действия. В кабинете — шкала с θ̂ ± SE и порогами.
- **Возражение:** кнопка «Оспорить» → комментарий 10–2000 символов → `grade_appeals` (status `open|resolved`). Одно открытое обращение на категорию (409 `appeal_already_open`, частичный уникальный индекс); без категории — 409 `no_category`. Админ видит список в кабинете (`/admin/appeals`) и отвечает (`POST /admin/appeals/{id}/resolve`), кандидат видит ответ в разделе «Категория и грейд». **Обращение и ответ грейд не меняют**: изменить категорию может только тест. Создание и ответ пишутся в `audit_log`; при удалении аккаунта обращения удаляются. Тесты доступа — `test_appeals.py` (кандидат видит только свои, не-админ → 403).

## 17. Синтетика и демо-данные (`backend/seed/`)

- **Кандидаты:** 600 по 5 специализациям. Сначала генерируется θ_true, затем **ответы на тест через настоящий движок**, поэтому категории получаются по реальной механике, а не прописываются вручную. Архетипы: сильный олимпиадник-алгоритмист, продуктовый backend с хакатонами, CTF-специалист в devops, кандидат без ФСП, junior с одним региональным результатом, завысивший грейд, «серый» профиль без активности.
- **ФСП:** 40 соревнований с реалистичными названиями, уровнями, датами и числом участников; данные кладутся в fsp-mock.
- **Работодатели и активность:** 12 работодателей, 20 потребностей (6 опубликованы как вакансии), история приглашений и откликов со всеми статусами.
- **Регулярные задания:** у «Демо Банка» два задания по первой потребности (автопроверка и подход) с решениями обычных кандидатов; героям задания не выдаются заранее — им предложат при первом открытии раздела.
- **Герои демо** с известными сильными профилями:
  - кандидаты Анна (Backend Middle, есть ФСП), Илья (Frontend Junior, без ФСП), Мария (DevOps Senior, CTF);
  - работодатели «Демо Банк» и «Демо Ритейл».
- **Служебный кандидат e2e** `e2e-candidate@itscout.ru` («Тест Автотестов», Backend · Middle, без ФСП, пароль — как у демо-аккаунтов): не герой показа, принимает приглашения e2e-работодателей (§18). Создаётся последним кандидатом из своей ветки RNG (`random.Random(f"{SEED}:e2e")`) и исключён из синтетических приглашений и откликов, поэтому данные остальных кандидатов, приглашения и шорт-листы не сдвигаются; θ — среднее для Middle (тест «пройден», без уверенного прохождения), в подборках он ниже середины и не попадает в топ показа. Единственное влияние на остальных — он входит в знаменатель перцентилей Backend · Middle.
- **Аккаунты команды и пароли.** `TEAM_ACCOUNTS` (JSON) — генератор создаёт каждому участнику админа, кандидата Backend · Middle с пройденным тестом и компанию; пароли сид-аккаунтов — `DEMO_SEED_PASSWORD` (пусто — случайный), кандидата e2e — `E2E_CANDIDATE_PASSWORD`. Паролей в коде нет (`docs/deploy.md` §5.5).
- **Отладочный раздел** (`DEBUG_TOOLS=true`): пункт «Отладка» в кабинетах (у админа — `/admin/debug`) — сброс ограничений на пересдачу и своих результатов теста, тестовое письмо, reseed. Без флага `/debug/*` отвечают 404, пункта нет.
- `POST /admin/reseed` (роль admin) и `make reseed` возвращают демо-данные в исходное состояние перед показом. Пересидирование очищает все таблицы, кроме экспертной разметки (`expert_pairs`, `expert_labels`, `angoff_ratings`, `angoff_hofstee` — `PRESERVED_TABLES` в `seed/generate.py`): **API-ключи, webhook'и и журнал доставок работодателей тоже удаляются** вместе с компаниями — после reseed ATS нужно подключить заново. Демо-админ `DEMO_ADMIN_EMAIL` создаётся генератором, только если в `.env` задан `DEMO_ADMIN_PASSWORD`; генератор запускается отдельным процессом, чтобы не блокировать API.

## 18. Демо-сценарий (e2e и видео)

1. Новый кандидат регистрируется и подтверждает почту (на проде — реальное письмо).
2. Проходит опрос: система предлагает специализацию Backend, выбран грейд Middle.
3. Сдаёт тест (в демо-режиме — сокращённый, 8 заданий), получает категорию «Backend · Middle» и разбор по темам.
4. Работодатель «Демо Банк» создаёт потребность текстом и видит разбор и покрытие вилки.
5. Открывает подборку: рекомендованные категории и топ кандидатов с объяснениями. Фильтрует «есть ФСП», закрепляет двоих в шорт-листе, меняет фильтр — шорт-лист на месте.
6. Открывает карточку героя: тест по темам, блок ФСП, контактов нет.
7. Отправляет приглашение с вилкой 220–260 тыс. ₽.
8. Кандидат видит приглашение, вилку и «почему вам» → принимает.
9. Работодатель видит статус «принято» и контакты кандидата.
10. Классический путь: кандидат откликается на вакансию, работодатель сразу видит контакты.
11. «Проверка под вакансию»: blueprint и 3 примера заданий, повторная генерация даёт другие экземпляры той же сложности.

Шаги 1–9 покрыты Playwright-тестом (`e2e/`, Chromium) и прогоняются после каждого деплоя вместе с проверкой мобильной вёрстки (`tests/mobile-layout.spec.ts`: экраны обоих кабинетов на 390px без горизонтальной прокрутки) — job `e2e` в CI против `https://itscout.ru`; локально — `make e2e` (адрес стенда — `E2E_BASE_URL`). Прогон не меняет демо-данные для показа:
- `tests/candidate-onboarding.spec.ts` (шаги 1–3): одноразовый кандидат `e2e-candidate-<id>@example.com` (домен не принимает почту; подтверждение на проде не обязательно) проходит опрос, подтверждает Backend, выбирает Middle и проходит полный тест, отвечая «как получится». Проверяется только механика: результат показан (категория или «грейд не подтверждён» — оба исхода валидны), разбор по темам есть, в ответах `GET /tests/attempts/*/current` нет полей с ключами ответов. В конце аккаунт удаляется через «Настройки».
- `tests/employer-invitation.spec.ts` (шаги 4–9): новый работодатель `e2e-employer-<id>@example.com` с компанией «E2E Компания <id>» создаёт потребность текстом (разбор словарём, вилка 220–260 тыс. ₽, покрытие вилки), собирает шорт-лист из двух кандидатов с фильтром «есть ФСП» и проверяет, что он переживает смену фильтров. Приглашение уходит не герою, а служебному кандидату сида `e2e-candidate@itscout.ru` (§17), найденному через поиск по базе: карточка без контактов → приглашение → вход кандидатом в отдельном контексте браузера, «почему вам», «Принять» → у работодателя «Принято» и контакты. Работодатель каждый раз новый, поэтому повторное активное приглашение невозможно; принятые приглашения у служебного кандидата копятся до `make reseed`.

## 20. Деплой и CI/CD

- **compose:** `infra/docker-compose.yml` — сервисы `caddy`, `frontend` (сборка Vite, статика в volume для Caddy), `backend`, `db`, `fsp-mock`, `keycloak` (мок IdP «ФСП ID», `-Xmx512m`, `mem_limit: 1g`, около 500 МБ RAM, §9.3). `docker-compose.dev.yml` добавляет `mailpit` и hot reload.
- **CI** (`.github/workflows/ci.yml`, на каждый push): ruff, миграции с нуля + `alembic check`, pytest, актуальность `openapi.json` и сгенерированного клиента, lint/typecheck/build фронта.
- **Deploy** (push в `master`, после зелёного CI): rsync репозитория в `/opt/itscout/app` → `docker compose up -d --build` (backend сам применяет миграции при старте) → smoke-тест `/api/v1/health` → job `e2e`: Playwright с Chromium гоняет демо-сценарий §18 против `https://itscout.ru`; при падении в артефакт `e2e-screenshots` уходят только скриншоты (трейсы и видео с паролями и cookie не пишутся). Изменение сида попадает на прод только после `make reseed`. Секреты GitHub — `DEPLOY_SSH_KEY` (отдельный ключ деплоя) и `E2E_CANDIDATE_PASSWORD` (пароль служебного кандидата e2e). Остальные секреты — в `/opt/itscout/app/.env` на сервере (права 600).
- **HTTPS:** после появления A-записи `itscout.ru` в `Caddyfile` включается блок домена.
- **Почта:** контейнер `mail` (Postfix, только отправка) подписывает письма DKIM (селектор `mail`, ключ в volume `dkim`). В DNS: SPF `v=spf1 ip4:94.103.87.151 -all`, DKIM `mail._domainkey`, DMARC; PTR IP → `itscout.ru` в панели VDSina.
- **Запуск с нуля:** `docs/deploy.md` — `cp .env.example .env && docker compose up -d` поднимает всё, включая seed.

## 24. Концепции вне MVP (только в документации)

**Защита от фиктивных вакансий и недобросовестных работодателей:**
- верификация компании: корпоративный домен email, проверка ИНН через открытые данные ФНС;
- проверка вилки на адекватность рынку категории — **реализована** (§8.6 п. 7);
- рейтинг по откликам и отказам, жалобы кандидатов;
- очередь модерации для помеченных;
- бейдж «Проверенный работодатель»;
- лимиты приглашений для новых компаний.

**Интеграция с ATS:**
- API-ключи работодателя — **реализованы** (§8.8);
- исходящие webhook'и (`invitation.accepted`, `invitation.declined`, `application.created`) — **реализованы** (§8.8);
- экспорт кандидата в JSON Resume — **реализован** (§8.8);
- коннекторы к российским ATS (Huntflow, Talantix, Potok) через их API.

**Реальная интеграция с ФСП:**
- OIDC через ФСП ID (Keycloak);
- REST-API реестра с client credentials;
- webhook о новых результатах;
- scope согласия `fsp:achievements:read`.
