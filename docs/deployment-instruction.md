# Инструкция по развёртыванию программного продукта «ITScout»

> Пароли, ключи и токены в документ не включены — указано только место их хранения. Подробности сборки и локального запуска — [deploy.md](deploy.md), схема CI/CD — [architecture.md §4](architecture.md).

## 1. Общие сведения

**Цель работ:** первичная установка ITScout на чистый сервер и обновление уже работающей установки. Основной путь обновления — автоматический: push в ветку `master` запускает CI/CD (`.github/workflows/ci.yml`), который проверяет код, выкладывает его на сервер, пересобирает контейнеры, применяет миграции БД и прогоняет e2e-сценарий против прода. Ручная установка через `docker compose` используется для первичного развёртывания сервера и для проверочного стенда экспертов и жюри. Ожидаемый результат — сайт `https://itscout.ru` отвечает, `GET /api/v1/health` возвращает `{"status":"ok","db":true,...}`, демо-вход и демо-сценарий работают.

| Параметр | Значение |
| --- | --- |
| Продукт и компонент | ITScout — весь стенд из `infra/docker-compose.yml` (проект compose `itscout`): `web` (Caddy + собранный фронтенд React), `backend` (FastAPI, миграции Alembic при старте), `db` (PostgreSQL 16), `fsp-mock` (мок реестра ФСП), `keycloak` (мок «ФСП ID»), `mail` (Postfix, только отправка), `backup` (ежедневные бэкапы) |
| Контур | Промышленный: `https://itscout.ru` (VDS, каталог приложения `/opt/itscout/app`). Проверочный: локальный стенд эксперта `http://localhost` (раздел 3.2) |
| Текущая → целевая версия | Версия приложения в `GET /api/v1/health` — поле `version` (на 09.10.2026: `0.1.0`, задаётся в `backend/pyproject.toml` и не меняется от коммита к коммиту). Фактическая версия кода — коммит `master`: «текущий коммит `master` на сервере → следующий коммит `master`». Какой коммит выложен, видно в последнем успешном прогоне «CI / Deploy» (`gh run list --workflow ci.yml --branch master`); на сервере каталога `.git` нет — rsync его исключает |
| Дата и окно работ | Обновление — при каждом push в `master`, в любое время; весь прогон CI занимает около 6 минут (проверки ~3 мин, deploy ~1 мин, e2e ~2 мин). Время — МСК (UTC+3). Сдача решения — 11.10.2026; во время показа жюри изменения в `master` не вливаются |
| Допустимый простой | Без формального SLA. Образы собираются до пересоздания контейнеров, поэтому недоступность ограничена перезапуском изменившихся сервисов: по прогону от 08.10.2026 шаг «Build and restart» занял ~35 с, health снова отвечал через ~17 с после него. Ориентир — до 1 минуты; страница входа «ФСП ID» (Keycloak) после пересоздания поднимается дольше, до 1–2 минут |
| Исполнитель и согласующие | Команда ITScout. Восстановление БД из бэкапа и удаление томов — только с подтверждения команды |
| Версия инструкции | 1.0, 09.10.2026 |

## 2. Предварительные условия

| Что требуется | Значение / расположение | Как проверить готовность |
| --- | --- | --- |
| Серверы и ресурсы | Прод: один VDS, Ubuntu 26.04 LTS, 4 vCPU, 7,25 ГБ RAM + своп 2 ГБ, диск 99 ГБ. Минимум для установки — 2 vCPU и 3 ГБ RAM; стенд занимает около 1,5 ГБ RAM, Keycloak — до 1 ГБ (`mem_limit`). Своп создаёт `infra/scripts/setup-swap.sh` (идемпотентно) | По SSH: `lsb_release -ds; nproc; free -m; df -h /`. Без SSH: `gh workflow run server-ops.yml -f action=status` (uptime, память, диск, `docker stats`, `docker compose ps`, health) |
| Зависимости | Docker Engine 24+ и Compose v2 (на проде — Docker 29.1.3, Compose 2.40.3). Все остальные зависимости (PostgreSQL 16, Python 3.12, Node.js 22, Caddy 2) приходят в образах. Docker Hub с сервера — только через зеркало `mirror.gcr.io` в `/etc/docker/daemon.json`. Сеть: входящие 80/tcp, 443/tcp и 443/udp (Caddy, сертификат Let's Encrypt выпускается автоматически); DNS — A-записи `itscout.ru` и `www.itscout.ru` на IP сервера. Для писем — исходящий порт 25, SPF, DKIM (`mail._domainkey`), DMARC, PTR | `docker version --format '{{.Server.Version}}'`, `docker compose version --short`, `cat /etc/docker/daemon.json` (ожидается `{"registry-mirrors": ["https://mirror.gcr.io"]}`), `dig +short itscout.ru` (IP сервера), `curl -sS http://itscout.ru/health` (`ok`, после первого запуска) |
| Учётные записи и права | Пользователь `root` на сервере по SSH-ключу (у команды — SSH-алиас `itscout`). CI и workflow «Server ops» ходят на сервер отдельным ключом деплоя из секрета GitHub `DEPLOY_SSH_KEY`. Для e2e — секрет `E2E_CANDIDATE_PASSWORD`. Запуск workflow — права на запись в репозиторий GitHub | `ssh itscout true` (код возврата 0). `gh secret list` — в списке есть `DEPLOY_SSH_KEY` и `E2E_CANDIDATE_PASSWORD` (значения не выводятся). `gh auth status` |
| Дистрибутив | Исходный код из репозитория `https://github.com/bojlahg/FSP_ITVacancyAggregator`, ветка `master`. Образы собираются на сервере из `backend/Dockerfile`, `fsp-mock/`, `frontend/Dockerfile` (контекст — корень репозитория), `infra/keycloak/`; готовых артефактов и контрольных сумм нет — версия определяется SHA коммита. Git LFS для сборки не нужен | `git rev-parse HEAD` в рабочей копии совпадает с `headSha` последнего успешного прогона: `gh run list --workflow ci.yml --branch master --limit 1 --json headSha,conclusion` |
| Конфигурация и секреты | Прод: `/opt/itscout/app/.env`, права `600`, в git нет и rsync его не перезаписывает. Шаблон — `.env.example`, описание — `backend/app/core/config.py` и [deploy.md §5.1, §5.5, §7](deploy.md). Обязательные для прода переменные (только имена): `APP_ENV=prod`, `DEMO_MODE`, `PUBLIC_BASE_URL`, `CORS_ORIGINS`, `COOKIE_SECURE=true`, `JWT_SECRET` (от 32 символов, иначе backend не стартует), `POSTGRES_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD` (без этих двух compose не запустится), `FSP_API_KEY`, `DEMO_ADMIN_PASSWORD`, `EMAIL_BACKEND`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `EMAIL_VERIFICATION_REQUIRED`, `LLM_PROVIDER` (при `yandex` — ещё `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`), `TEAM_ACCOUNTS`, `DEMO_SEED_PASSWORD`, `E2E_CANDIDATE_PASSWORD`, `DEBUG_TOOLS`, `BACKUP_KEEP_DAYS`, `BACKUP_INTERVAL_HOURS` | `stat -c '%a' /opt/itscout/app/.env` → `600`. Наличие переменной без вывода значения: `grep -c '^JWT_SECRET=' /opt/itscout/app/.env` → `1`. Синтаксис и подстановки compose: `cd /opt/itscout/app && docker compose --env-file .env -f infra/docker-compose.yml config --quiet` (без ошибок) |
| Резервная копия | Сервис `backup` (`infra/scripts/backup.sh`): раз в 24 ч `pg_dump` в формате custom (`db-<время>.dump`) и архив загруженных файлов (`uploads-<время>.tar.gz`) в отдельный том `itscout_backups`, хранение 7 дней. Каждый дамп проверяется `pg_restore -l`, архив — `tar -t`. Деплой и reseed том не трогают. Копия лежит на том же сервере и от потери сервера не защищает | Список: `gh workflow run server-ops.yml -f action=backups` или по SSH `docker compose --env-file .env -f infra/docker-compose.yml exec -T backup sh /usr/local/bin/backup.sh list` — есть свежий `db-*.dump`. В логе сервиса (`action=logs -f service=backup`) — `backup ok`, нет `backup failed`. Восстановление проверено на копии ([deploy.md §5.4](deploy.md)) |

**Условия начала работ:** для обновления через CI — изменения влиты в `master`, задачи проверены локально (тесты и линт по AGENTS.md); дальше CI сам не пустит деплой, если не прошли jobs `backend`, `fsp-mock` и `frontend`. Для ручной установки на сервер — все строки таблицы выше проверены, `.env` заполнен. Если обновление содержит миграцию БД, удаляющую или меняющую данные, — перед push снят внеочередной бэкап (шаг 2 раздела 3.1). Запуск разрешает команда ITScout; во время показа жюри обновления не выполняются.

## 3. Порядок развёртывания

Выполняйте шаги по порядку. Команды с `$DC` выполняются в каталоге приложения после `DC="docker compose --env-file .env -f infra/docker-compose.yml"`.

### 3.1. Вариант А — обновление прода через CI/CD (основной)

| № | Где выполнять | Действие / команда | Ожидаемый результат |
| ---: | --- | --- | --- |
| 1 | Рабочая машина разработчика | Зафиксировать текущее состояние: `curl -sS https://itscout.ru/api/v1/health` и `gh run list --workflow ci.yml --branch master --limit 1 --json headSha,conclusion` | Health отвечает `{"status":"ok","db":true,"version":"0.1.0"}`; записан SHA последнего успешного деплоя — это точка отката |
| 2 | GitHub Actions (или сервер по SSH) | Если обновление содержит миграцию БД или иное рискованное изменение — внеочередной бэкап: `gh workflow run server-ops.yml -f action=backup`, затем `gh run watch <id>`. По SSH: `cd /opt/itscout/app && $DC exec -T backup sh /usr/local/bin/backup.sh once` | В логе `backup ok: /backups/db-<время>.dump (<размер>)`; файл виден в `action=backups` |
| 3 | Рабочая машина разработчика | Влить изменения: `git pull --rebase --autostash`, `git push` в `master` | Запущен workflow «CI / Deploy» (`gh run list --workflow ci.yml --limit 1`) |
| 4 | GitHub Actions, jobs `backend`, `fsp-mock`, `frontend` | Выполняются автоматически: ruff; миграции с нуля + `alembic check` на PostgreSQL 16; `pytest`; актуальность `openapi.json`; eslint, `tsc`, актуальность клиента API, `vite build` | Все три job зелёные. При падении деплой не начинается, прод остаётся на прежней версии |
| 5 | GitHub Actions → сервер, job `deploy`, шаг «Upload sources» | `rsync -az --delete` рабочей копии в `/opt/itscout/app` (исключены `.git/`, `.env`, `node_modules/`, `.venv/`, `frontend/dist/`, `__pycache__/`) | На сервере код целевого коммита; `.env` и тома Docker (данные БД, загрузки, бэкапы) не затронуты |
| 6 | Сервер, job `deploy`, шаг «Build and restart» | `docker compose --env-file .env -f infra/docker-compose.yml up -d --build --remove-orphans`, затем `docker image prune -f`. Контейнер `backend` при старте выполняет `alembic upgrade head` и только потом запускает uvicorn (`backend/Dockerfile`) | Образы пересобраны, изменившиеся контейнеры пересозданы; миграции применены до `head`. Проверка схемы по SSH: `$DC exec -T backend alembic current` — ревизия с пометкой `(head)` |
| 7 | GitHub Actions, шаг «Smoke test» | До 30 попыток с интервалом 5 с: `curl -fsS http://<сервер>/api/v1/health`, ищется `"db":true` | В логе `healthy`. Иначе job падает с `health check failed` — переходите к разделу «Если шаг завершился ошибкой» |
| 8 | GitHub Actions, job `e2e` | Playwright (Chromium) проходит демо-сценарий §18 против `https://itscout.ru` | Job зелёный. При падении — артефакт `e2e-screenshots` (только скриншоты) |

### 3.2. Вариант Б — ручная установка на чистый сервер или стенд эксперта

| № | Где выполнять | Действие / команда | Ожидаемый результат |
| ---: | --- | --- | --- |
| 1 | Сервер (Ubuntu) или машина эксперта | Установить Docker Engine и Compose plugin. Если Docker Hub отвечает `429` или недоступен — в `/etc/docker/daemon.json` записать `{"registry-mirrors": ["https://mirror.gcr.io"]}` и перезапустить Docker | `docker compose version` выводит v2 |
| 2 | Сервер | DNS: A-записи `itscout.ru` и `www.itscout.ru` → IP сервера; открыть входящие 80, 443/tcp и 443/udp. Для стенда эксперта шаг пропускается | `dig +short itscout.ru` возвращает IP сервера |
| 3 | Сервер или машина эксперта | Получить код: на сервере `git clone https://github.com/bojlahg/FSP_ITVacancyAggregator.git /opt/itscout/app && cd /opt/itscout/app`; у эксперта `git clone https://github.com/bojlahg/FSP_ITVacancyAggregator.git itscout && cd itscout` | Рабочая копия ветки `master`; `git log -1 --format=%h` — SHA устанавливаемой версии |
| 4 | Сервер | Своп 2 ГБ на случай нехватки памяти: `sh infra/scripts/setup-swap.sh` (или `gh workflow run server-ops.yml -f action=swap`) | `swapon --show` показывает `/swapfile` |
| 5 | Сервер или машина эксперта | Конфигурация: `cp .env.example .env`. На сервере — `chmod 600 .env` и значения прода по [deploy.md §5.1 и §5.5](deploy.md) (секреты генерируются `openssl rand -hex 32` / `-hex 24` и хранятся только в этом файле). У эксперта достаточно поменять `PUBLIC_BASE_URL=http://localhost`, `CORS_ORIGINS=["http://localhost"]` и задать любые `POSTGRES_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD` | `docker compose --env-file .env -f infra/docker-compose.yml config --quiet` завершается без ошибок |
| 6 | Сервер или машина эксперта | Собрать и запустить: `docker compose --env-file .env -f infra/docker-compose.yml up -d --build` (на сервере то же делает `make prod-up`). Первая сборка — 5–10 минут | Образы собраны, контейнеры запущены |
| 7 | Там же | Миграции БД отдельной командой не запускаются: их применяет `backend` при старте (`alembic upgrade head`). Проверка: `docker compose --env-file .env -f infra/docker-compose.yml exec -T backend alembic current` | Ревизия с пометкой `(head)`; в `logs backend` нет ошибок Alembic |
| 8 | Там же | Состояние сервисов: `docker compose --env-file .env -f infra/docker-compose.yml ps` | Все сервисы `Up`, `db` и `keycloak` — `healthy` |
| 9 | Там же | Демо-данные (около минуты): `docker compose --env-file .env -f infra/docker-compose.yml exec backend python -m seed.generate`. На уже работающем проде — только через `make reseed` или `gh workflow run server-ops.yml -f action=reseed`: они сначала снимают бэкап, а сброс удаляет всех пользователей и компании | 600 кандидатов, 12 работодателей, 40 соревнований ФСП в моке реестра, приглашения и отклики во всех статусах |

**Если шаг завершился ошибкой:** остановите работы и не повторяйте вслепую. Если упали проверки CI (шаг 4 варианта А) — прод не менялся: исправьте код и сделайте новый push. Если упали `deploy` или `e2e` — сразу снимите состояние (`gh workflow run server-ops.yml -f action=status`, `-f action=logs -f service=backend`), сообщите команде ITScout и в течение 15 минут примите решение: исправление вперёд новым коммитом или откат (раздел 5). Если backend не стартует из-за миграции — не удаляйте тома и не пересоздавайте БД, переходите к шагу 3 раздела 5.

## 4. Проверка после развёртывания

| Проверка | Команда / адрес / действие | Ожидаемый результат |
| --- | --- | --- |
| Версия и состояние сервиса | `curl -sS https://itscout.ru/api/v1/health`; выложенный коммит — `gh run list --workflow ci.yml --branch master --limit 1 --json headSha,conclusion`; контейнеры — `gh workflow run server-ops.yml -f action=status` или по SSH `$DC ps` | `{"status":"ok","db":true,"version":"0.1.0"}` (`"degraded"` и `"db":false` — БД недоступна); `headSha` равен целевому коммиту, `conclusion` — `success`; все сервисы `Up`, `db` и `keycloak` — `healthy` |
| Доступность API или интерфейса | `curl -sS -o /dev/null -w '%{http_code}' https://itscout.ru/`; Swagger — `https://itscout.ru/api/docs`; по HTTP по IP отвечает только `curl -sS http://<IP>/health` | `200`; Swagger UI открывается; `/health` по HTTP отвечает `ok`, остальные пути HTTP редиректят на `https://itscout.ru` |
| Основной пользовательский сценарий | Вручную: `https://itscout.ru` → «Демо-вход» → «Кандидат» (кабинет с категорией и грейдом) и «Работодатель» (потребность, подборка кандидатов, приглашение). Автоматически: job `e2e` в CI или локально `make e2e` (без make: `cd e2e && npm ci && npx playwright install chromium && npx playwright test`; пароль служебного кандидата — переменная окружения `E2E_CANDIDATE_PASSWORD`, другой стенд — `E2E_BASE_URL=http://localhost`) | Демо-вход открывает оба кабинета без пароля (пока `DEMO_MODE=true`); все тесты Playwright зелёные |
| Логи и мониторинг | `gh workflow run server-ops.yml -f action=logs -f service=backend -f lines=200` (email и IP маскируются, access-логи отброшены); полные логи — по SSH `cd /opt/itscout/app && $DC logs --tail 200 backend` (также `web`, `db`, `keycloak`, `fsp-mock`, `mail`, `backup`) | Нет `Traceback`, ошибок Alembic, `backup failed`; Caddy без ошибок выпуска сертификата для `itscout.ru` |

**Критерий завершения:** обязательны зелёный прогон «CI / Deploy» целиком (включая `deploy` с `healthy` и `e2e`), ответ health `{"status":"ok","db":true,...}` и ручной проход демо-входа за кандидата и работодателя, если изменение видно в демо. Успешное развёртывание подтверждает участник команды ITScout, сделавший push. Для стенда эксперта — health `ok` на `http://localhost/api/v1/health` и вход «Демо-вход» → «Кандидат» / «Работодатель».

## 5. Откат

**Когда выполнять откат:** job `deploy` упал на smoke-тесте или health не возвращается к `"db":true`; job `e2e` упал и причина в новой версии, а не в тесте; на проде сломан демо-сценарий. Решение принимается не позже 15 минут после обнаружения; перед показом жюри — немедленно.

**Предыдущая рабочая версия:** SHA предыдущего успешного прогона «CI / Deploy» в `master` (`gh run list --workflow ci.yml --branch master --status success --limit 2 --json headSha`) или известная хорошая точка, отмеченная тегом git (например, `pre-redesign`). Отдельных хранимых артефактов нет: образы пересобираются из кода, поэтому возврат кода означает возврат версии. Данные — бэкапы в томе `itscout_backups` (`backup.sh list`).

| № | Действие / команда | Ожидаемый результат |
| ---: | --- | --- |
| 1 | Остановить поступление новых версий: не вливать в `master` ничего, кроме отката; сообщить команде. Если сломан только один сервис, временно помогает `gh workflow run server-ops.yml -f action=restart -f service=<сервис>` | Новых деплоев нет; причина записана (лог `action=logs`) |
| 2 | Только если откатываемый коммит содержит миграцию БД — до возврата кода, пока на сервере ещё лежит новая миграция: снять бэкап (`$DC exec -T backup sh /usr/local/bin/backup.sh once`), затем по SSH `cd /opt/itscout/app && $DC exec -T backend alembic downgrade <ревизия_до_миграции>` (или `-1`) и сверить `$DC exec -T backend alembic current`. У всех миграций в `backend/migrations/versions` есть `downgrade()`, но часть из них удаляет данные (например, экспресс-попытки теста, пользователей-экспертов, строки индекса поиска без подтверждённого грейда). Через «Server ops» этот шаг недоступен — нужен SSH | Схема БД на ревизии предыдущей версии. Если пропустить шаг, после возврата кода backend не стартует: в БД останется ревизия, файла которой в коде уже нет |
| 3 | Если downgrade невозможен или данные повреждены — восстановление из бэкапа строго по [deploy.md §5.4](deploy.md) и только с подтверждения команды: свежий бэкап текущего состояния (`backup.sh once`) → `$DC stop backend` → `pg_restore --clean --if-exists --no-owner` из выбранного `db-<время>.dump` → при необходимости архив `uploads-<время>.tar.gz` → `$DC start backend` | Данные и схема соответствуют моменту бэкапа и совместимы с предыдущей версией кода |
| 4 | Вернуть код прямым коммитом поверх `master`: `git pull --rebase --autostash`, `git revert --no-edit <sha_плохого_коммита>` (несколько коммитов — `git revert --no-edit <старый_sha>^..<новый_sha>`; к тегу — `git revert --no-commit pre-redesign..HEAD`, затем `git commit`), `git push`. `git push --force` и `git reset --hard` по `master` запрещены (AGENTS.md) | Запущен «CI / Deploy», который выкладывает предыдущее состояние кода тем же путём, что и обычный деплой (раздел 3.1, шаги 4–8) |
| 5 | Повторить контрольные проверки раздела 4 | Health `{"status":"ok","db":true,...}`, `deploy` и `e2e` зелёные, демо-вход работает — прежняя версия обслуживает запросы |

**Что делать, если откат не удался:** прекратите дальнейшие действия на проде, не удаляйте тома (`pgdata`, `uploads`, `backups`) и бэкапы, не выполняйте `docker compose down -v`, `docker system prune`, reseed. Снимите состояние (`action=status`, `action=logs` по `backend` и `db`) и передайте вопрос команде ITScout в рабочий канал команды; дальнейшие шаги (повторное восстановление из более раннего бэкапа, ручное вмешательство по SSH) — только по её решению. Любое ручное вмешательство на сервере затем повторяется в `infra/` и `docs/deploy.md`, иначе следующий деплой его затрёт.
