# Процедура валидации и результаты

Валидация проверяет критерии ТЗ к тестированию и подбору — согласованность, дискриминативность, соответствие эталону, устойчивость к утечке заданий, корректность категоризации и качество выдачи — **на том же коде, что работает в продукте**. Полный отчёт с таблицами и графиками генерируется командой `make validate` в [`docs/validation/report.md`](validation/report.md), сырые метрики — [`docs/validation/metrics.json`](validation/metrics.json). Здесь — устройство процедуры и главные результаты (seed 2026, 2 000 кандидатов, 7 299 попыток теста).

## 1. Как устроена процедура

```mermaid
flowchart LR
  cfg["validation/config.yaml<br/>параметры популяции"] --> pop
  pop["Популяция 2 000:<br/>θ_true, истинный грейд,<br/>профиль по темам, стек,<br/>резюме с шумом, ФСП"] --> sim
  sim["Модель ответа 3PL<br/>+ σ_b экземпляра"] --> eng
  eng["Движок продукта:<br/>Planner MST, рендер,<br/>EAP, решение о грейде"] --> path["Путь калибровки §6.3:<br/>вниз при провале,<br/>вверх при «уверенно»"]
  path --> m1["Метрики теста"]
  pop --> match["matching/scoring.py<br/>15 потребностей"] --> m2["Метрики подбора"]
  m1 & m2 --> rep["report.md, metrics.json,<br/>PNG-графики"]
```

- **Тот же движок.** Тест собирается и оценивается кодом `backend/app/modules/testing/engine`, подбор — `matching/scoring.py`, специализация по опросу — `survey.service.score_specializations`. БД и HTTP не участвуют, прогон детерминирован по seed.
- **Популяция.** 2 000 синтетических кандидатов по 5 специализациям. У каждого — истинная способность θ_true (смесь распределений по грейдам), истинный грейд — старший грейд, чей порог не выше θ_true, профиль по темам (отклонения σ = 0,3 от θ), истинный стек, резюме с шумом (лишние и пропущенные навыки), заявленный грейд с ошибкой (20% завышают, 10% занижают), история ФСП у 35%.
- **Модель ответа.** 3PL от способности по теме задания плюс отклонение сложности конкретного экземпляра (σ_b = 0,15). Движок о профиле по темам и σ_b не знает — это проверка устойчивости к нарушению его модели.
- **Путь кандидата.** Тест на заявленный грейд, вниз при провале, один раз вверх при «пройден уверенно». Для согласованности каждый проходит путь дважды с разными seed — другие шаблоны и экземпляры.
- **Подбор.** 15 потребностей (по 3 на специализацию). Истинная релевантность 0–3 строится только из истинных специализации, грейда и стека; сравниваются выдача ITScout и базовые линии.

Штраф соседнего грейда в подборе усилен (0,6 → 0,3). Эффект: доля ложно прошедших при утечке ключей — 14% вместо 25%, общих экземпляров у двух попыток — 0,1% вместо 1,1%, P@5 выдачи — 0,75 вместо 0,68, перерост в «общем топе» — 15% вместо 29%.

## 3. Соответствие эталону и согласованность

Ошибки категоризации — только соседние грейды: это кандидаты, чья способность лежит у порога, где погрешности измерения хватает, чтобы оказаться по другую сторону. Вдали от порогов категория повторяется в 87,6% случаев, решение «пройден / не пройден» — в 89,9%.

## 4. Дискриминативность и точность

Информационная функция теста максимальна около порогов Middle и Senior, где принимается решение. У порогов Intern и Junior максимум смещён вправо: в заданиях с выбором ответа угадывание сдвигает максимум информации выше сложности задания, а самые лёгкие шаблоны лежат около −1,8. Поэтому больше всего ошибок — на уровнях «нет категории» и Intern.

## 5. Устойчивость к утечке

Сценарий: 400 кандидатов ниже Middle сдают тест на Middle, 30% ключей слиты. Для фиксированного теста слиты 30% ответов единой формы; для ITScout — 30% шаблонов банка вместе с 50 экземплярами каждого.

| Сценарий | Прошли тест | Завышение θ̂ |
|---|---|---|
| Фиксированный тест, честно | 14,2% | 0,01 |
| Фиксированный тест, утечка | 67,8% | 0,68 |
| Адаптивный тест без параметризации, утечка | 61,5% | 0,64 |
| ITScout с параметризацией, утечка | 13,8% | 0,01 |

Сами по себе банк и адаптивность от утечки не защищают — защищает параметризация шаблонов. Прирост ложно прошедших: 54 п.п. у фиксированного теста против 1 п.п. у ITScout. Медианная вероятность того, что экземпляр задания совпадёт с одним из 50 слитых, — 3,2%.

## 6. Подбор

| Способ ранжирования | P@5 | P@10 | nDCG@10 | перерост@10 |
|---|---|---|---|---|
| ITScout: выдача по категориям (по умолчанию) | 0,75 | 0,65 | 0,79 | 7% |
| ITScout: «общий топ» по score | 0,69 | 0,57 | 0,74 | 15% |
| категория по тесту + ключевые слова | 0,77 | 0,74 | 0,85 | 9% |
| заявленный грейд + ключевые слова | 0,71 | 0,66 | 0,80 | 9% |
| только ключевые слова резюме | 0,29 | 0,27 | 0,45 | 26% |

1. **Тест как фильтр точнее резюме:** категория по тесту + ключевые слова даёт P@5 0,77 против 0,71 у заявленного грейда и 0,29 у одних ключевых слов.
2. **Выдача ITScout** в 2,6 раза точнее ключевых слов и почти не уступает варианту «категория + ключевые слова»: внутри категории score упорядочивает ещё и по силе подтверждённого профиля (θ̂, ФСП, свежесть), а синтетическая истина знает только специализацию, грейд и стек и за силу профиля не поощряет. Правильность порядка внутри категории проверяет экспертная разметка (раздел 8).
3. **«Общий топ»** уступает группировке: сильный кандидат соседнего грейда может обогнать точного. После усиления штрафа соседнего грейда разрыв сократился (P@5 0,69 против 0,75, перерост 15%), группировка по категориям остаётся режимом по умолчанию.

## 7. Слабые места и что с ними делать

Пороги, blueprint'ы, веса и движок по результатам прогона **автоматически не меняются** — рекомендации отчёта (раздел 11):

| Наблюдение | Рекомендация |
|---|---|
| Трёхуровневое решение (не / пройден / уверенно) повторяется в 62% | показывать «уверенно» как предложение попробовать грейд выше, а надёжность оценивать по итоговой категории; до 8 доп. заданий у порога дают повтор категории 77% вместо 74% |
| Выше порога экспозиции 25% — до 17% шаблонов отдельных тем (frontend) | пополнять темы с самой большой квотой шаблонами около порогов Junior и Middle |
| Максимум информации теста на Intern смещён от порога | добавить задания с открытым числовым ответом (без угадывания) и b от −2,4 до −1,8 |
| Порядок внутри категории синтетикой не проверяется | экспертная разметка 100 пар «потребность — кандидат» до дальнейших изменений весов |

## 8. Что не измерено автоматически

- **Реальная калибровка.** Симуляция проверяет механику при заданной модели ответов; параметры шаблонов на живых людях уточняются через пилотные слоты (≈ 400 ответов на шаблон до статуса `active`).
- **Пороги грейдов** — стартовые экспертные значения; окончательные задаются процедурой modified Angoff.
- **Экспертная оценка подбора.** План: участник команды и 2–3 приглашённых ИТ-специалиста размечают 100 пар «потребность — карточка кандидата» по шкале 0–3 → корреляция Спирмена с ранжированием ITScout и P@5. Функции метрик готовы (`validation/stats.py`), разметка требует людей.
- **Разбор резюме** (precision и recall полей), открытый вопрос о подходе и поведенческие сигналы (уход со вкладки, время ответа) в симуляции не участвуют.

## 9. Воспроизведение

```bash
make validate                                         # Linux, WSL, CI; ~7–8 минут
cd backend && uv run python ../validation/run.py      # то же без make
cd backend && uv run python ../validation/run.py --size 500 --seed 7 --out /tmp/v   # другой прогон
```

Smoke-тест процедуры на маленькой популяции (`backend/tests/test_validation.py`) проверяет в CI, что метрики считаются и детерминированы.
